# 판단 패턴 역색인

문제 속 상황·표현에서 정답 방향을 거꾸로 찾는 표. 덱 각 도메인 끝의 "판단 패턴" 슬라이드(26, 50, 69, 91번)를 넓힌 것이다.

## 도메인 1　AI 기초 및 활용 능력

| 문제 속 상황·표현 | 정답 방향 | 노트 |
|---|---|---|
| 규칙으로 명확히 정의할 수 있다 / 항상 같은 결과가 필요 | 규칙 기반 자동화(AI 불필요) | [[규칙 기반 자동화]] |
| 예측·분류가 목적인데 생성형 AI를 쓰려 한다 | 기존 ML로 충분한지 먼저 검토 | [[생성형 AI]] |
| 결과가 나쁘다 / 특정 집단에 치우친다 | 모델 교체 전에 데이터 품질(특히 대표성) 점검 | [[데이터 품질]] |
| 이전 결과에 따라 다음 행동을 고르고 여러 시스템을 조작 | AI 에이전트 | [[AI 에이전트]] |
| 질문에 답만 하면 된다(사내 규정 Q&A) | RAG 어시스턴트(에이전트는 과잉) | [[검색 증강 생성(RAG)]] |
| 에이전트에게 더 많은 자율성을 준다 | 최소 권한 + 사람 승인 지점 + 작업 로그 | [[AI 에이전트]] |
| 사내 최신 정보로 답하고 싶다 / 출처를 보여주고 싶다 | RAG | [[검색 증강 생성(RAG)]] |
| 일관된 문체·형식, 특정 전문 작업 | 미세 조정(먼저 프롬프트 검토) | [[미세 조정]] |
| 우선 저비용으로 출력을 개선하고 싶다 | 프롬프트 엔지니어링 | [[프롬프트 엔지니어링]] |
| 출력 형식·판단 기준을 맞추고 싶다 | 퓨샷(예시 제시) | [[프롬프트 엔지니어링]] |
| 프롬프트 품질이 담당자마다 다르다 | 프롬프트 템플릿 공유·재사용 | [[프롬프트 엔지니어링]] |
| 도입 후 시간이 지나며 정확도가 떨어진다 | 모델 드리프트 → 지속적 모니터링과 재학습 | [[모델 드리프트]] |
| 사기 수법이 바뀌어 탐지율이 떨어졌다 | 개념 드리프트 → 재학습 | [[모델 드리프트]] |
| 미승인 AI 도구 사용이 멈추지 않는다 | 대체 도구 + 분류 목록 공개 + 신청 절차 + 기술적 차단 | [[섀도 AI]] |
| 긴 문서에서 답변이 누락된다 / 비용·응답 시간 증가 | 컨텍스트 윈도우·토큰 제약 → 분할·요약·RAG | [[토큰과 컨텍스트 윈도우]] |
| 부서 간 "AI" 용어 인식이 다르다 | 통합 어휘(ISO/IEC 23053 등) | [[ISO-IEC 23053]] |
| AI 경영 시스템 인증을 받고 싶다 | ISO/IEC 42001 | [[ISO-IEC 42001]] |

## 도메인 2　AI 전략 및 비즈니스 가치 창출

| 문제 속 상황·표현 | 정답 방향 | 노트 |
|---|---|---|
| "AI로 무엇을 할 수 있나"에서 출발하는 선택지 | 오답. 비즈니스 목표에서 거꾸로 | [[문제 중심 AI 전략]] |
| 목표가 "업무 효율화"처럼 모호하다 | 측정 가능한 KPI까지 구체화 | [[문제 중심 AI 전략]] |
| 핵심 차별화, 고유 데이터 활용 | 구축 | [[구축-구매-파트너]] |
| 범용 업무, 빠른 도입, 역량 부족 | 구매(역량도 키우려면 파트너) | [[구축-구매-파트너]] |
| 관리형 서비스로 요구를 충족할 수 있다 | 관리형 우선(Bedrock/Quick). SageMaker AI 자체 모델은 필요할 때만 | [[Bedrock vs SageMaker AI vs Quick vs Marketplace]] |
| 여러 AI 후보 중 무엇부터? | 가치·실현 가능성·지속 가능성·전략적 조정 → 퀵 윈 | [[AI 이니셔티브 우선순위]] |
| 성공 기준 미달, 전략과 불일치 | 종료하고 자원 재배분(매몰 비용 무시) | [[규모 조정·일시 중지·종료]] |
| 가치는 크지만 규제가 불확실 | 일시 중지 | [[규모 조정·일시 중지·종료]] |
| 처리 건수가 적고 원인이 프로세스에 있다 | AI를 쓰지 않는다 | [[AI가 적합하지 않은 경우]] |
| 기존 업무를 AI로 전환한다 | 병행 운영, 단계적 전환, 롤백 계획 | [[AI 전환 고려 사항]] |
| 다른 AI 플랫폼으로 옮긴다 | 성능 비교 + 프롬프트·평가 재수행 | [[AI 전환 고려 사항]] |
| AI 효과를 정확히 보여주고 싶다 | 구현 전에 기준 지표 설정 | [[기준 지표]] |
| 고객 만족도·직원 생산성을 KPI에 넣고 싶다 | 무형적 이점 → 설문·대리 지표로 측정 | [[핵심 성과 지표(KPI)]] |
| 파일럿을 계속할지 판단하고 싶다 | 선행 지표(채택률, 사용 빈도 등) | [[선행 지표]] |
| 예상보다 AI 비용이 크게 나왔다 | TCO(데이터 준비·통합·운영·교육·거버넌스) 누락 점검 | [[총소유비용(TCO)]] |
| 사용량 예측이 어려운 초기·파일럿 | 사용량 기반(온디맨드) | [[AWS AI 가격 책정 구조]] |
| 대량·안정적 사용으로 비용을 줄이고 싶다 | 약정형(절감형 플랜, 프로비저닝된 처리량) | [[절감형 플랜]] |
| 도입 전에 비용을 추정하고 싶다 | AWS 요금 계산기 | [[AWS 요금 계산기]] |
| 실제 비용을 분석·예측하고 싶다 | AWS Cost Explorer | [[AWS Cost Explorer]] |
| 경쟁사가 따라 하기 어렵게 하고 싶다 | 고유 데이터 × 업무 통합 × 조직 역량(데이터 플라이휠) | [[지속 가능한 경쟁 우위]] |
| 효율화를 넘어 새 수익원을 만들고 싶다 | 비즈니스 모델 혁신(서비스화 등) | [[AI 비즈니스 모델 혁신]] |
| 규제가 엄격한 산업의 AI 투자 | 거버넌스 먼저, 저위험 용도부터 단계적으로 | [[산업 성숙도별 AI 투자]] |

## 도메인 3　AI 거버넌스 및 책임 있는 AI 리더십

| 문제 속 상황·표현 | 정답 방향 | 노트 |
|---|---|---|

| 특정 속성의 승인율만 낮다 | 공정성 → 속성별 결과 측정, 데이터 편향 시정 | [[책임 있는 AI 차원]] |
| 결과의 이유를 설명해 달라 | 설명 가능성 | [[책임 있는 AI 차원]] |
| AI가 쓴 글임을 사용자가 모른다 | 투명성 → AI 사용 명시 | [[투명성 vs 설명 가능성]] |
| 비즈니스 목표를 위해 원칙을 잠시 접자 | 오답. 위험 비례로 원칙과 목표 양립 | [[책임 있는 AI 절충]] |
| 빨리 출시해야 하지만 안전도 필요 | 영향 범위를 제한한 단계적 배포 | [[책임 있는 AI 절충]] |
| 대출·채용·의료 등 영향이 큰 판단 | 사람의 감시(HITL)와 설명 가능성 | [[사람의 감시]] |
| 챗봇이 부적절한 발언 / 금지 주제 | 가드레일(콘텐츠 필터, 거부 주제) | [[가드레일]] |
| 사실과 다른 답변이 나온다 | RAG, 근거성 검사, 출처 제시, 사람의 확인 | [[할루시네이션]] |
| 거버넌스 체계를 만든다 | 부서 간 위원회 + 각 AI의 책임자 1명 | [[AI 거버넌스 위원회]] |
| IT 부서(또는 법무)만 결정하는 거버넌스 | 오답. 부서 간 대표성 필요 | [[AI 거버넌스 위원회]] |
| 규제 대상 업무에 AI 도입 | 법무·규정 준수를 초기부터, 지속적 검토 | [[규정 준수 위험]] |
| 권한 밖의 사내 정보가 답변에 포함됐다 | 액세스 제어(권한을 반영한 검색) | [[액세스 제어와 데이터 보안]] |
| 관리형이면 보안은 AWS 책임 | 오답. 데이터·액세스·사용은 고객 책임 | [[AWS 공동 책임 모델]] |
| 모든 AI에 같은 강도의 심사 | 오답. 위험 분류에 따른 비례적 거버넌스 | [[비례적 거버넌스]] |
| 채용 심사 AI(EU AI 법 기준) | 고위험 → 적합성 평가, 사람의 감시, 기록 보관 | [[AI 위험 분류 프레임워크]] |
| 프로덕션 AI에 문제가 생겼을 때 대비 | 임계값·알림, 인시던트 대응, 정기 검토, 롤백·중지 | [[프로덕션 위험 모니터링]] |
| 시간이 지나며 특정 그룹에 편향이 생겼다 | 바이어스 드리프트 지속 모니터링 | [[바이어스 드리프트]] |

| 사용자가 AI 출력을 그대로 믿는다 | 과도한 의존 → 한계 명시, 사용자 교육, 사람 확인 | [[3.3 엔터프라이즈 AI 위험과 완화]] |
