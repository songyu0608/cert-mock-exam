# 브랜치 보호 규칙과 룰셋

> [!summary] 한 줄 정의
> 중요 브랜치에 PR 리뷰 승인, 상태 확인 통과, 서명 커밋, 선형 이력 등을 강제하는 규칙. 룰셋은 여러 개를 겹쳐 적용할 수 있는 더 유연한 방식이다.

**English** Branch protection rules and rulesets

## 시험 트리거
- "main에 리뷰 없이 병합되는 걸 막고 싶다"
- "테스트가 통과해야만 병합"
- "강제 푸시와 브랜치 삭제 금지"

## 핵심
- 브랜치 보호 설정: 필요한 승인 수(오래된 승인 무효화, 코드 소유자 리뷰 필수, 마지막 푸시 승인), 상태 확인 필수, 대화 해결 필수, 서명된 커밋, 선형 이력, 병합 큐, 배포 성공 필수, 브랜치 잠금, 우회 금지, 푸시 제한.
- 강제 푸시·삭제는 기본으로 허용되지 않는다. fnmatch 패턴(예: *release*). 한 브랜치에는 브랜치 보호 규칙 하나만 적용.
- 룰셋: 이름 있는 규칙 목록. 여러 룰셋이 겹치면 규칙을 합치고 가장 엄격한 것이 적용(예: 3명 vs 2명 → 3명). 활성·비활성 전환, 우회 목록, 읽기 권한자도 열람, 커밋 메타데이터 규칙. 리포지토리당 최대 75개.
- 푸시 룰셋: 파일 경로·확장자·크기로 비공개·내부 리포지토리 푸시를 막는다. 조직 단위 다중 리포지토리 룰셋은 Enterprise.
- 요금제: Free는 공개 리포지토리, Pro·Team·Enterprise는 비공개 리포지토리에서도. 관리는 Admin(또는 "리포지토리 규칙 편집" 사용자 지정 역할).

## 오답 함정
> [!warning] 오답이 되기 쉬운 선택지
> - 한 브랜치에 브랜치 보호 규칙 여러 개를 겹쳐 쓴다는 선택지 → 하나만. 겹치려면 룰셋
> - GitHub Free 개인 계정의 비공개 리포지토리에 보호 브랜치를 쓴다는 선택지 → Pro 이상
