# GitHub 플로

> [!summary] 한 줄 정의
> 브랜치 생성 → 변경·커밋 → 풀 리퀘스트 → 리뷰 반영 → 병합 → 브랜치 삭제로 이어지는 가벼운 브랜치 기반 협업 흐름.

**English** GitHub flow

## 시험 트리거
- "기본 브랜치에 직접 커밋하지 않고 변경을 제안"
- "리뷰 후 병합한 다음 할 일"
- "작업 중 피드백을 일찍 받고 싶다"

## 핵심
- 1) 브랜치 만들기: 기본 브랜치에 영향 없이 작업. 짧고 설명적인 이름(예: increase-test-timeout).
- 2) 변경하기: 브랜치에서 수정하고 설명적인 메시지로 커밋·푸시. 병합 전까지 기본 브랜치에 반영되지 않는다.
- 3) 풀 리퀘스트 만들기: 피드백 요청. 완성 전이면 초안(draft)으로 연다.
- 4) 리뷰 코멘트 반영: 커밋을 더 푸시하면 PR이 자동으로 갱신된다.
- 5) 병합: 승인 후 병합. 코멘트와 커밋 이력은 PR에 남는다.
- 6) 브랜치 삭제: 작업 완료를 알리고 오래된 브랜치 재사용을 막는다. 삭제해도 PR·커밋 이력은 남고 복원할 수 있다.

## 오답 함정
> [!warning] 오답이 되기 쉬운 선택지
> - 병합 후 브랜치를 지우면 PR 이력도 사라진다는 선택지 → PR과 커밋 이력은 남는다
> - 리뷰를 받으려면 작업을 끝내야 한다는 선택지 → 초안 PR로 일찍 피드백을 받는다
