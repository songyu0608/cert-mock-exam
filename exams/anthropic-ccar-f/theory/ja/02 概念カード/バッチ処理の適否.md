# バッチ処理の適否

> [!summary] 一行定義
> 待つ必要のない処理（夜間レポート、週次監査、夜間のテスト生成）はバッチ、開発者が結果を待つ処理（マージ前チェック）は同期API。

**English** When to use batch processing

## 出題のきっかけ
- 「コスト削減のために全部バッチにしよう」
- 「マージ前に必ず完了しなければならない」
- 「30時間のSLA」

## 要点
- バッチ＝50%削減、**最大24時間**、**レイテンシSLAなし**。→ [[Message Batches API]]
- マージ前チェックのようなブロッキングの処理 → **同期APIを維持**。
- SLAの計算：24時間のバッチ処理で30時間のSLAを保証するには**4時間間隔**で提出（ガイドの例。計算の根拠は解釈：提出待ち最大4時間＋処理最大24時間＝28時間 ≤ 30時間）。
- 失敗の処理：custom_idで失敗した文書だけを特定し、修正して（例：大きすぎる文書をチャンクに分割）再提出。
- 大量処理の前に**サンプルセットでプロンプトを磨き**、初回の成功率を上げる。

## 誤答の落とし穴
> [!warning] 誤答になりやすい選択肢
> - 「両方バッチにしてステータスをポーリング」→ マージ前チェックは待つ必要があるので不適
> - 「バッチ結果の順序の問題を避けるため両方リアルタイムを維持」→ custom_idで対応付けできるので誤解
> - 「バッチ＋遅ければリアルタイムにフォールバック」→ 不要な複雑さ
