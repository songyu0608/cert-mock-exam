# フラッシュカード 分野 2　ツール設計とMCP統合

#flashcards/ccar-f/d2

形式：`質問::答え`（Spaced Repetitionプラグイン）。プラグインがなくても1行ずつ読めばよい。

## 概念の確認
LLMがツールを選ぶとき主に頼るものは？::ツールの説明
ツールの説明に含めるべき4つは？::入力形式、クエリの例、エッジケース、類似ツールとの境界
汎用的なanalyze_documentを、ガイドはどう分割する例を挙げている？::extract_data_points、summarize_content、verify_claim_against_source
ガイドが区別するエラー4種は？::一時的、検証、ビジネス、権限
無駄なリトライを防ぐためにエラーレスポンスに含めるブール値は？::isRetryable（ビジネス違反はretriable: false）
検索がタイムアウトしたとき、空の結果を成功として返してはいけない理由は？::アクセスの失敗が隠れ、コーディネーターがリトライや代替手段を判断できない
統合エージェントの検証ラウンドトリップを減らしつつ信頼性を保つ方法は？::単純な事実確認用にスコープを絞ったverify_factを与え、複雑な検証はコーディネーター経由にする
Jira統合のためにカスタムMCPサーバーを新たに作るのはガイド上正しい？::正しくない。標準的な統合にはコミュニティサーバーを使う
不慣れなコードベースを理解する推奨手順は？::Grepでエントリーポイントを探す → Readでimportをたどって追跡
モデルに必ず何らかのツールを呼ばせるtool_choiceの値は？::"any"
extract_metadataを最初に実行させるには？::tool_choice: {"type": "tool", "name": "extract_metadata"}
MCPツールが失敗をエージェントに伝えるフラグは？::isError
チーム共有のMCPサーバーの設定ファイルは？::プロジェクトスコープの.mcp.json
.mcp.jsonでトークンをコミットしない方法は？::${GITHUB_TOKEN}のような環境変数の展開
データベーススキーマの一覧を探索呼び出しなしでエージェントに見せるには？::MCPリソースとして公開する
関数のすべての呼び出し元を探すツールは？::Grep
名前のパターンでファイルを探すツールは？::Glob
Editが一意なテキストを見つけられないときは？::Readで全体を読み、Writeで書き直す

## 状況 → 判断
状況：似た2つのツールをよく取り違える（最初の一手） → 正解の方向は？::ツールの説明を拡充
状況：説明がほぼ同じ2つのツール → 正解の方向は？::名前変更＋説明の修正
状況：汎用のanalyze_documentがすべてを担う → 正解の方向は？::目的別のツールに分割
状況：よく書けたツールの説明が無視される → 正解の方向は？::システムプロンプト内のキーワード指示を確認
状況："Operation failed"だけを返す → 正解の方向は？::errorCategory・isRetryable・説明
状況：ポリシー違反のエラー → 正解の方向は？::isRetryable: false＋顧客向けの説明
状況：検索結果が0件 → 正解の方向は？::有効な空の結果（成功）。アクセスの失敗と区別
状況：ツールを18個持つエージェントの選択ミス → 正解の方向は？::役割に必要なツールだけ
状況：統合エージェントの頻繁な単純検証 → 正解の方向は？::スコープを絞ったverify_fact
状況：必ずツールを呼び出させる → 正解の方向は？::tool_choice: "any"
状況：特定のツールを先に → 正解の方向は？::tool_choiceの強制選択
状況：チーム共有のMCPサーバー → 正解の方向は？::.mcp.json＋${ENV}
状況：個人用・試験用のMCPサーバー → 正解の方向は？::~/.claude.json
状況：エージェントがMCPツールではなくGrepを使う → 正解の方向は？::MCPツールの説明を詳しく
状況：Jiraとの連携 → 正解の方向は？::コミュニティMCPサーバー
状況：何があるかを知るための探索的な呼び出しを繰り返す → 正解の方向は？::MCPリソースでカタログを公開
状況：すべての呼び出し元を探す → 正解の方向は？::Grep
状況：**/*.test.tsxのファイルを探す → 正解の方向は？::Glob
状況：Editが一意なテキストを見つけられない → 正解の方向は？::Read＋Write
