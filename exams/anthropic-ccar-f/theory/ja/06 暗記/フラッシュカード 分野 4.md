# フラッシュカード 分野 4　プロンプトエンジニアリングと構造化出力

#flashcards/ccar-f/d4

形式：`質問::答え`（Spaced Repetitionプラグイン）。プラグインがなくても1行ずつ読めばよい。

## 概念の確認
「控えめに判断せよ」で精度が上がらないとき、代わりに何をする？::報告するカテゴリとスキップするカテゴリを具体的に定義する
誤検知の多いカテゴリが開発者の信頼を損なうとき、ガイドの対処は？::そのカテゴリを一時的に無効化し、プロンプトを改善する
曖昧なシナリオ向けのfew-shotの例は何件で、何を示す？::2-4件。その行動を選んだ理由（代替案との比較）まで
形式の多様な文書で必須フィールドが空になるときの対策は？::形式の異なる文書から正しく抽出したfew-shotの例を追加
スキーマ準拠の構造化出力を最も確実に得る方法は？::JSONスキーマを付けたツール使用（tool_use）
厳密なJSONスキーマでも防げないエラーは？::意味的なエラー（合計の不一致、フィールドの配置ミス）
総額の不一致を自ら検出させるには、どのフィールドを合わせて抽出する？::stated_totalとcalculated_total
ソースにない値をモデルが捏造するのを防ぐスキーマ設計は？::そのフィールドを任意（nullable）にする
拡張可能なカテゴリをenumで表すパターンは？::"other"＋詳細文字列フィールド
検証失敗後の再リクエストに含めるべき3つは？::元の文書、失敗した抽出結果、具体的な検証エラー
リトライが効果を持たない代表的なケースは？::必要な情報がソースにないとき（例：提供されていない外部文書にしかない）
誤検知パターンを分析するためにレビュー結果に追加するフィールドは？::detected_pattern
マージ前チェックと夜間の技術的負債レポートのうち、バッチに向くのは？::夜間の技術的負債レポートだけ
24時間のバッチ処理で30時間のSLAを保証するには、提出間隔は？::4時間
複数ファイルを一度にレビューして結果がばらつく根本原因は？::注意の分散
その解決策の構成は？::ファイル単位のローカルパス＋別のファイル横断の統合パス
Message Batches APIのコスト・処理時間・SLAは？::50%削減、最大24時間、レイテンシSLAなし
バッチのリクエストとレスポンスを対応付けるフィールドは？::custom_id
バッチAPIでできないことは？::1つのリクエスト内でのマルチターンのツール呼び出し
曖昧な値を表すenum値の例は？::"unclear"
Pydanticの検証失敗後、再リクエストに含めるのは汎用メッセージか具体的なエラーか？::具体的な検証エラー

## 状況 → 判断
状況：「控えめに」と指示しても誤検知 → 正解の方向は？::具体的なカテゴリ基準
状況：誤検知のせいで開発者が無視する → 正解の方向は？::該当カテゴリを一時的に無効化して改善
状況：重大度の分類が毎回違う → 正解の方向は？::レベルごとのコード例
状況：出力形式が毎回違う → 正解の方向は？::few-shotの例
状況：曖昧なケースの判断を教える → 正解の方向は？::2-4件の例＋選んだ理由
状況：JSONがときどき壊れる → 正解の方向は？::tool_use＋JSONスキーマ
状況：スキーマは通ったのに合計が合わない → 正解の方向は？::意味的エラー → 別途検証（calculated_total）
状況：ソースにない値を捏造する → 正解の方向は？::nullableフィールド
状況：分類が曖昧な値 → 正解の方向は？::enumの"unclear"／"other"＋詳細
状況：検証失敗後の再リクエスト → 正解の方向は？::元の文書＋失敗した抽出＋具体的なエラー
状況：外部の文書にしかない情報 → 正解の方向は？::リトライは無意味
状況：却下された指摘のパターン分析 → 正解の方向は？::detected_pattern
状況：マージ前チェックのコスト削減 → 正解の方向は？::同期のまま（バッチは不可）
状況：夜間レポートのコスト削減 → 正解の方向は？::Message Batches API
状況：バッチの一部が失敗 → 正解の方向は？::custom_idで失敗分だけ修正して再提出
状況：生成したセッションで自分のコードをレビュー → 正解の方向は？::独立したインスタンス
状況：14ファイルのPRのレビューがばらつく → 正解の方向は？::ファイル単位のパス＋統合パス
