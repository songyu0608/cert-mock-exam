# 公式サンプル問題12問

## [[シナリオ1 カスタマーサポート解決エージェント]]

### 問題 1

本番環境のデータによると、12%のケースでエージェントがget_customerを完全にスキップし、顧客が申告した名前だけを使ってlookup_orderを呼び出しており、その結果、アカウントの誤認や誤った返金がときどき発生しています。この信頼性の問題に最も効果的に対処できる変更はどれですか。

- **A.** get_customerが検証済みの顧客IDを返すまで、lookup_orderとprocess_refundの呼び出しをブロックする、プログラムによる前提条件を追加する。
- **B.** システムプロンプトを強化し、あらゆる注文操作の前にget_customerによる顧客確認が必須であることを明記する。
- **C.** 顧客が自分から注文の詳細を伝えてきた場合でも、エージェントが常に最初にget_customerを呼び出す様子を示すfew-shotの例を追加する。
- **D.** 各リクエストを分析し、そのリクエストタイプに適したツールのサブセットだけを有効にするルーティング分類器を実装する。

> [!success]- 正解と解説
> **A**. 重要なビジネスロジックのために特定のツール実行順序が必要な場合（返金処理の前に顧客の本人確認を行うなど）、プログラムによる強制は、プロンプトベースのアプローチでは得られない決定論的な保証を提供します。選択肢BとCは、LLMが確率的に指示に従うことに依存しており、エラーが金銭的な影響をもたらす場合には不十分です。選択肢Dはツールの順序ではなくツールの利用可否に対処するもので、実際の問題とは異なります。
>
> → [[プログラムによる強制]]

### 問題 2

本番環境のログによると、ユーザーが注文について尋ねたとき（例：「注文#12345を確認して」）、エージェントはlookup_orderではなくget_customerを頻繁に呼び出しています。どちらのツールも説明が最小限で（「顧客情報を取得する」／「注文の詳細を取得する」）、似た形式の識別子を受け付けます。ツール選択の信頼性を高めるための、最も効果的な最初の一手はどれですか。

- **A.** システムプロンプトに、正しいツール選択パターンを示すfew-shotの例を追加する。注文関連のクエリがlookup_orderにルーティングされる例を5-8件含める。
- **B.** 各ツールの説明を拡充し、対応する入力形式、クエリの例、エッジケース、類似ツールとの使い分けを説明する境界を含める。
- **C.** 各ターンの前にユーザー入力を解析し、検出したキーワードと識別子のパターンに基づいて適切なツールを事前に選択するルーティング層を実装する。
- **D.** 2つのツールを、任意の識別子を受け付けて問い合わせ先のバックエンドを内部で判断する単一のlookup_entityツールに統合する。

> [!success]- 正解と解説
> **B**. ツールの説明は、LLMがツールを選択する際に用いる主要な仕組みです。説明が最小限だと、モデルは類似したツールを区別するためのコンテキストを得られません。選択肢Bは、少ない労力で大きな効果が得られる修正によって、この根本原因に直接対処します。few-shotの例（A）は、根本的な問題を解決しないままトークンのオーバーヘッドを増やします。ルーティング層（C）は過剰な設計であり、LLMの自然言語理解を迂回してしまいます。ツールの統合（D）はアーキテクチャ上の選択として妥当ですが、当面の問題が不十分な説明である以上、「最初の一手」に見合う以上の労力がかかります。
>
> → [[ツールの説明]]

### 問題 3

エージェントの初回解決率は55%で、目標の80%を大きく下回っています。ログによると、エージェントは単純なケース（写真の証拠がある標準的な破損品交換）をエスカレーションする一方で、ポリシーの例外対応が必要な複雑な状況を自律的に処理しようとしています。エスカレーションの判断精度を改善する最も効果的な方法はどれですか。

- **A.** システムプロンプトに明示的なエスカレーション基準を追加し、エスカレーションすべき場合と自律的に解決すべき場合を示すfew-shotの例を添える。
- **B.** 各応答の前にエージェントに確信度スコア（1-10）を自己申告させ、確信度がしきい値を下回った場合はリクエストを自動的に人間に回す。
- **C.** 過去のチケットで学習させた別の分類器モデルをデプロイし、メインのエージェントが処理を始める前に、どのリクエストにエスカレーションが必要かを予測する。
- **D.** 感情分析を実装して顧客の不満の度合いを検出し、否定的な感情がしきい値を超えた場合に自動的にエスカレーションする。

> [!success]- 正解と解説
> **A**. few-shotの例を添えて明示的なエスカレーション基準を追加することは、判断の境界が不明確であるという根本原因に直接対処します。これは、インフラストラクチャを追加する前に取るべき、問題に見合った最初の対応です。選択肢Bは、LLMが自己申告する確信度のキャリブレーションが不十分であるため、うまくいきません。エージェントはすでに、難しいケースで誤って自信を持っているからです。選択肢Cは過剰な設計であり、プロンプトの最適化をまだ試していない段階で、ラベル付きデータとMLインフラストラクチャを必要とします。選択肢Dはまったく別の問題を解決するものです。感情は、実際の課題であるケースの複雑さとは相関しません。
>

- **A.** プロジェクトリポジトリ内の.claude/commands/ディレクトリ

> **A**. プロジェクトスコープのカスタムスラッシュコマンドは、リポジトリ内の.claude/commands/ディレクトリに保存します。これらのコマンドはバージョン管理され、開発者がリポジトリをクローンまたはプルすると、全員が自動的に利用できるようになります。選択肢B（~/.claude/commands/）は、バージョン管理で共有されない個人用コマンドのためのものです。選択肢C（CLAUDE.md）は、コマンド定義ではなく、プロジェクトの指示とコンテキストのためのものです。選択肢Dは、Claude Codeに存在しない設定の仕組みを説明しています。

### 問題 5

チームのモノリシックなアプリケーションをマイクロサービスに再構築する担当になりました。これには数十のファイルにわたる変更が伴い、サービスの境界とモジュールの依存関係についての判断が必要です。どのアプローチを取るべきですか。

- **A.** プランモードに入り、変更を加える前にコードベースを調査して依存関係を把握し、実装アプローチを設計する。
- **B.** 直接実行で開始して段階的に変更を加え、実装を進める中で自然なサービス境界が見えてくるようにする。
- **C.** 各サービスをどのように構成すべきかを正確に記した包括的な事前指示を与えたうえで、直接実行を使用する。
- **D.** 直接実行モードで開始し、実装中に予期しない複雑さに直面した場合にのみプランモードに切り替える。

> [!success]- 正解と解説
> **A**. プランモードは、大規模な変更、複数の有効なアプローチ、アーキテクチャ上の判断を伴う複雑なタスクのために設計されています。これはまさに、モノリスからマイクロサービスへの再構築に必要なものです。変更に踏み切る前に、コードベースの調査と設計を安全に行えます。選択肢Bは、依存関係の発見が遅れた場合に、コストのかかる手戻りが生じるリスクがあります。選択肢Cは、コードを調査せずに正しい構成をすでに知っていることを前提としています。選択肢Dは、複雑さが後から現れるかもしれないものではなく、要件の時点ですでに明示されていることを無視しています。
>
> → [[プランモード]]

### 問題 6

コードベースには、コーディング規約の異なる複数の領域があります。Reactコンポーネントはフックを用いた関数型スタイル、APIハンドラーは特定のエラー処理を伴うasync/await、データベースモデルはリポジトリパターンに従います。テストファイルはテスト対象のコードと並べてコードベース全体に分散しており（例：Button.tsxの隣にButton.test.tsx）、場所に関係なくすべてのテストを同じ規約に従わせたいと考えています。Claudeがコード生成時に正しい規約を自動的に適用するようにする、最も保守しやすい方法はどれですか。

- **A.** .claude/rules/に、globパターンを指定するYAMLフロントマター付きのルールファイルを作成し、ファイルパスに基づいて規約を条件付きで適用する
- **B.** すべての規約をルートのCLAUDE.mdファイルに領域ごとの見出しを付けて集約し、どのセクションが該当するかの推測をClaudeに任せる
- **C.** コードの種類ごとに.claude/skills/にスキルを作成し、そのSKILL.mdファイルに該当する規約を含める
- **D.** 各サブディレクトリに、その領域固有の規約を記した個別のCLAUDE.mdファイルを配置する

> [!success]- 正解と解説
> **A**. 選択肢Aが正解である理由は、globパターン（例：**/*.test.tsx）を指定した.claude/rules/を使うと、ディレクトリの場所に関係なく、ファイルパスに基づいて規約を自動的に適用できるためです。これは、コードベース全体に分散したテストファイルには不可欠です。選択肢Bは明示的なマッチングではなく推測に頼るため、信頼性に欠けます。選択肢Cは、スキルを手動で呼び出すか、Claudeがスキルの読み込みを選択することに頼る必要があり、ファイルパスに基づく決定論的な「自動」適用という要件と矛盾します。選択肢Dは、CLAUDE.mdファイルがディレクトリに紐づくため、多数のディレクトリに分散したファイルを容易には扱えません。
>

### 問題 7

「AIがクリエイティブ産業に与える影響」というトピックでシステムを実行したところ、各サブエージェントは正常に完了していることがわかりました。ウェブ検索エージェントは関連する記事を見つけ、文書分析エージェントは論文を正しく要約し、統合エージェントは一貫性のある出力を生成しています。しかし、最終レポートはビジュアルアートしか扱っておらず、音楽、執筆、映画制作が完全に抜け落ちています。コーディネーターのログを調べると、トピックが「デジタルアート制作におけるAI」「グラフィックデザインにおけるAI」「写真におけるAI」という3つのサブタスクに分解されていました。最も可能性の高い根本原因はどれですか。

- **A.** 統合エージェントに、他のエージェントから受け取った調査結果のカバレッジの欠落を特定するための指示が不足している。
- **B.** コーディネーターエージェントのタスク分解が狭すぎるため、サブエージェントへの割り当てがトピックの関連領域をすべてカバーできていない。
- **C.** ウェブ検索エージェントのクエリが十分に網羅的ではなく、クリエイティブ産業のより多くのセクターをカバーするよう拡張する必要がある。
- **D.** 文書分析エージェントが、過度に厳しい関連性基準のために、ビジュアル以外のクリエイティブ産業に関するソースを除外している。

> [!success]- 正解と解説
> **B**. コーディネーターのログが根本原因を直接示しています。「クリエイティブ産業」をビジュアルアートのサブタスク（デジタルアート、グラフィックデザイン、写真）だけに分解し、音楽、執筆、映画を完全に省いています。サブエージェントは割り当てられたタスクを正しく実行しており、問題は割り当てられた内容にあります。選択肢A、C、Dは、割り当てられた範囲内で正しく動作している下流のエージェントに誤って原因を求めています。

### 問題 8

ウェブ検索サブエージェントが、複雑なトピックの調査中にタイムアウトします。この失敗の情報をコーディネーターエージェントにどのように戻すかを設計する必要があります。インテリジェントな復旧を最もよく可能にするエラー伝播のアプローチはどれですか。

- **A.** 失敗の種類、試行したクエリ、部分的な結果、考えられる代替アプローチを含む構造化されたエラーコンテキストをコーディネーターに返す。
- **B.** サブエージェント内に指数バックオフによる自動リトライロジックを実装し、すべてのリトライを使い切った後にのみ、汎用的な「検索を利用できません」というステータスを返す。
- **C.** サブエージェント内でタイムアウトをキャッチし、成功とマークした空の結果セットを返す。
- **D.** タイムアウト例外を、リサーチワークフロー全体を終了させるトップレベルのハンドラーにそのまま伝播させる。

> [!success]- 正解と解説
> **A**. 構造化されたエラーコンテキストは、修正したクエリでリトライするか、代替アプローチを試すか、部分的な結果で続行するかといった、インテリジェントな復旧の判断に必要な情報をコーディネーターに与えます。選択肢Bの汎用的なステータスは、価値のあるコンテキストをコーディネーターから隠し、十分な情報に基づく判断を妨げます。選択肢Cは、失敗を成功としてマークすることでエラーを握りつぶし、復旧を一切できなくするうえ、リサーチの出力が不完全になるリスクがあります。選択肢Dは、復旧戦略が成功する可能性があるにもかかわらず、ワークフロー全体を不必要に終了させます。

### 問題 9

テスト中に、統合エージェントが調査結果をまとめる際、特定の主張を検証する必要が頻繁に生じることがわかりました。現在は、検証が必要になると統合エージェントがコーディネーターに制御を戻し、コーディネーターがウェブ検索エージェントを呼び出し、その結果を添えて統合を再度呼び出します。これによりタスクごとに2-3回のラウンドトリップが追加され、レイテンシが40%増加します。評価によると、これらの検証の85%は単純なファクトチェック（日付、名前、統計）で、15%はより深い調査が必要です。システムの信頼性を維持しながらオーバーヘッドを削減する最も効果的なアプローチはどれですか。

- **A.** 統合エージェントに、単純な照会用にスコープを限定したverify_factツールを与え、複雑な検証は引き続きコーディネーター経由でウェブ検索エージェントに委任する。
- **B.** 統合エージェントに検証の必要事項をすべて蓄積させ、処理パスの最後にまとめてコーディネーターに返させる。コーディネーターはそれらを一括でウェブ検索エージェントに送る。
- **C.** 統合エージェントにすべてのウェブ検索ツールへのアクセスを与え、コーディネーターを経由するラウンドトリップなしに、あらゆる検証の必要に直接対応できるようにする。
- **D.** ウェブ検索エージェントに、統合エージェントが検証を必要としそうな内容を見越して、最初の調査中に各ソースの周辺コンテキストを余分に先回りしてキャッシュさせる。

> [!success]- 正解と解説
> **A**. 選択肢Aは最小権限の原則を適用し、85%を占める一般的なケース（単純な事実確認）に必要なものだけを統合エージェントに与えつつ、複雑なケースについては既存の連携パターンを維持します。選択肢Bのバッチ化のアプローチは、統合のステップがそれ以前に検証された事実に依存する場合があるため、ブロッキングの依存関係を生みます。選択肢Cは統合エージェントに過剰な権限を与え、関心の分離に反します。選択肢Dは投機的なキャッシュに頼っており、統合エージェントが何を検証する必要があるかを確実には予測できません。
>
> → [[ツールの配分と最小権限]]

## [[シナリオ5 継続的インテグレーションのためのClaude Code]]

### 問題 10

パイプラインスクリプトでclaude "Analyze this pull request for security issues"を実行していますが、ジョブがいつまでも応答しません。ログによると、Claude Codeは対話的な入力を待っています。自動化されたパイプラインでClaude Codeを実行する正しいアプローチはどれですか。

- **A.** -pフラグを追加する：claude -p "Analyze this pull request for security issues"
- **B.** コマンドを実行する前に環境変数CLAUDE_HEADLESS=trueを設定する
- **C.** stdinを/dev/nullからリダイレクトする：claude "Analyze this pull request for security issues" < /dev/null
- **D.** --batchフラグを追加する：claude --batch "Analyze this pull request for security issues"

> [!success]- 正解と解説
> **A**. -p（または--print）フラグは、Claude Codeを非対話モードで実行するための、ドキュメントに記載された方法です。プロンプトを処理して結果をstdoutに出力し、ユーザー入力を待たずに終了します。これはまさにCI/CDパイプラインに必要な動作です。その他の選択肢は、存在しない機能（CLAUDE_HEADLESS環境変数、--batchフラグ）を参照しているか、Claude Codeのコマンド構文に適切に対応していないUnixの回避策を使用しています。
>
> → [[-pフラグ]]

### 問題 11

チームは自動分析のAPIコストを削減したいと考えています。現在、リアルタイムのClaude呼び出しが2つのワークフローを支えています。(1)開発者がマージする前に完了しなければならない、ブロッキングのマージ前チェック、(2)翌朝のレビューのために夜間に生成される技術的負債レポートです。マネージャーは、50%のコスト削減を理由に、両方をMessage Batches APIに切り替えることを提案しています。この提案をどのように評価すべきですか。

- **A.** 技術的負債レポートにのみバッチ処理を使用し、マージ前チェックにはリアルタイム呼び出しを維持する。
- **B.** 両方のワークフローをバッチ処理に切り替え、ステータスのポーリングで完了を確認する。
- **C.** バッチ結果の順序の問題を避けるため、両方のワークフローでリアルタイム呼び出しを維持する。
- **D.** 両方をバッチ処理に切り替え、バッチに時間がかかりすぎる場合はリアルタイムにフォールバックするタイムアウトを設ける。

### 問題 12

あるプルリクエストが、在庫追跡モジュール全体で14ファイルを変更しています。すべてのファイルをまとめて分析する単一パスのレビューでは、結果に一貫性がありません。一部のファイルには詳細なフィードバックがある一方で他のファイルには表面的なコメントしかなく、明らかなバグが見逃され、あるファイルではあるパターンを問題として指摘しながら同じPR内の別の箇所では同一のコードを承認するといった、矛盾したフィードバックも見られます。レビューをどのように再構成すべきですか。

- **A.** 焦点を絞ったパスに分割する：各ファイルを個別に分析してローカルな問題を調べ、その後、ファイル間のデータフローを調べる、統合に焦点を当てた別のパスを実行する。
- **B.** 自動レビューを実行する前に、大きなPRを3-4ファイルの小さな提出単位に分割することを開発者に義務付ける。
