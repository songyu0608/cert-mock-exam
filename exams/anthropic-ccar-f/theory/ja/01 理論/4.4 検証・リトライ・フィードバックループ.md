# タスク 4.4　抽出品質のための検証、リトライ、フィードバックループを実装する

**English** Implement validation, retry, and feedback loops for extraction quality

分野 4　プロンプトエンジニアリングと構造化出力 (20%)

抽出結果を検証し、リトライとフィードバックで品質を上げる方法を問う。

> [!tip] 判断の要点
> - 再リクエストに元の文書＋失敗した抽出＋具体的な検証エラー
> - 情報がソースになければリトライは無意味
> - calculated_totalとstated_total、conflict_detected、detected_pattern

## 必要な知識（Knowledge of）

1. エラーフィードバック付きリトライ：リトライ時に具体的な検証エラーをプロンプトに追加し、モデルを修正へと導くこと
2. リトライの限界：必要な情報がそもそもソース文書に存在しない場合（形式や構造のエラーの場合とは異なり）、リトライは効果がないこと
3. フィードバックループの設計：どのコード構造が指摘事項を引き起こすかを追跡し（detected_patternフィールド）、却下パターンの体系的な分析を可能にすること
4. 意味的な検証エラー（値の合計が合わない、フィールドの配置が誤っている）とスキーマ構文エラー（ツール使用によって排除される）の違い

> [!quote]- English 公式ガイド原文
> 1. Retry-with-error-feedback: appending specific validation errors to the prompt on retry to guide the model toward correction
> 2. The limits of retry: retries are ineffective when the required information is simply absent from the source document (vs format or structural errors)
> 3. Feedback loop design: tracking which code constructs trigger findings (detected_pattern field) to enable systematic analysis of dismissal patterns
> 4. The difference between semantic validation errors (values don't sum, wrong field placement) and schema syntax errors (eliminated by tool use)

## 必要なスキル（Skills in）

1. モデルが自己修正できるように、元の文書、失敗した抽出結果、具体的な検証エラーを含むフォローアップリクエストを実装する
2. リトライが効果を持たない場合（例：提供されていない外部文書にしか情報が存在しない）と成功する場合（形式の不一致、構造的な出力エラー）を見極める
3. 構造化された指摘事項にdetected_patternフィールドを追加し、開発者が指摘事項を却下した際の誤検知パターンの分析を可能にする
4. 自己修正のための検証フローを設計する：不一致を検出するために"stated_total"とあわせて"calculated_total"を抽出し、整合しないソースデータに対して"conflict_detected"ブール値を追加する

> [!quote]- English 公式ガイド原文
> 1. Implementing follow-up requests that include the original document, the failed extraction, and specific validation errors for model self-correction
> 2. Identifying when retries will be ineffective (e.g., information exists only in an external document not provided) versus when they will succeed (format mismatches, structural output errors)
> 3. Adding detected_pattern fields to structured findings to enable analysis of false positive patterns when developers dismiss findings
> 4. Designing self-correction validation flows: extracting "calculated_total" alongside "stated_total" to flag discrepancies, adding "conflict_detected" booleans for inconsistent source data

## このタスクのカード
- [[誤検知と開発者の信頼]] — 誤検知の多いカテゴリは、正確なカテゴリへの信頼まで損なう。そうしたカテゴリは一時的に無効化し、プロンプトを改善する。
- [[構文エラーと意味的エラー]] — ツール使用＋厳密なスキーマはJSONの構文エラーをなくすが、合計の不一致やフィールドの取り違えといった意味的なエラーは防げない。
- [[検証とリトライのループ]] — 検証に失敗したら、元の文書・失敗した抽出結果・具体的な検証エラーを含めて再リクエストし、モデルに自己修正させる。
- [[リトライの限界]] — 必要な情報がソースにまったくなければリトライは効果がない。効果があるのは形式・構造のエラーだけ。
- [[detected_patternによるフィードバックループ]] — 構造化されたレビュー結果ごとに、どのコード構造が指摘を引き起こしたかを記録し、開発者が却下した指摘のパターンを体系的に分析する。
- [[Pydanticによる検証]] — 抽出結果のスキーマ・意味の検証に使うライブラリ。検証エラーをそのままリトライのリクエストに含める。
