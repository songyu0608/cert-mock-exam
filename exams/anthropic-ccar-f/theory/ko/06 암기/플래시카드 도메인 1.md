# 플래시카드 도메인 1　에이전트 아키텍처와 오케스트레이션

#flashcards/ccar-f/d1

형식: `질문::답` (Spaced Repetition 플러그인). 플러그인이 없어도 한 줄씩 읽으면 된다.

## 개념 확인
에이전트 루프를 계속할지 끝낼지 판단하는 값은?::stop_reason ("tool_use"면 계속, "end_turn"이면 종료)
도구 실행 결과는 어디에 넣어 다음 요청을 보내나?::대화 기록(메시지 목록)에 추가
가이드가 안티패턴으로 꼽은 루프 종료 방식 3가지는?::자연어 신호 파싱, 임의 반복 상한을 주된 종료 수단으로 사용, 어시스턴트 텍스트 유무로 완료 판단
허브 앤 스포크에서 서브에이전트 간 통신을 코디네이터로 모으는 이유 3가지는?::관찰 가능성, 일관된 오류 처리, 통제된 정보 흐름
"AI가 창작 산업에 주는 영향" 보고서가 시각 예술만 다뤘고, 코디네이터가 디지털 아트·그래픽 디자인·사진으로만 나눴다. 원인은?::코디네이터의 작업 분해가 너무 좁음
서브에이전트가 코디네이터의 대화 기록을 자동으로 상속하나?::아니다. 필요한 내용을 프롬프트에 명시적으로 넣어야 한다
에이전트 간에 출처를 보존하며 결과를 넘기려면?::콘텐츠와 메타데이터를 구조화된 형식으로 분리해 전달
서브에이전트를 병렬로 실행하려면 Task 호출을 어떻게 내보내나?::코디네이터의 한 응답 안에 여러 개
멀티 에이전트 반복 개선 루프에서 빈틈을 평가하는 주체는?::코디네이터
신원 확인 없이 환불이 진행되는 문제를 가장 확실히 막는 방법은?::검증된 고객 ID가 나올 때까지 후속 도구 호출을 막는 프로그래밍 방식 선행 조건
프롬프트 지시만으로 업무 순서를 지키게 할 때의 한계는?::확률적이라 실패율이 0이 아님
구조화된 인계 요약에 들어가는 항목 예 4가지는?::고객 ID, 근본 원인, 환불 금액, 권장 조치
여러 문제가 섞인 고객 요청의 처리 순서는?::항목별 분해 → 공유 컨텍스트로 병렬 조사 → 하나의 해결책으로 종합
예측 가능한 다면 코드 리뷰에 맞는 분해 패턴은?::프롬프트 체이닝(고정 순차 파이프라인)
"레거시 코드에 포괄적 테스트 추가" 같은 열린 작업의 분해 순서는?::구조 파악 → 영향 큰 영역 식별 → 우선순위 계획 → 발견에 따라 조정
이전 도구 결과가 대부분 오래됐다면 재개와 새 시작 중 무엇이 낫나?::구조화된 요약을 주입한 새 세션
stop_reason "tool_use"와 "end_turn"의 처리는?::tool_use면 도구 실행 후 계속, end_turn이면 종료
코디네이터가 서브에이전트를 호출하려면 allowedTools에 무엇이 있어야 하나?::"Task"
AgentDefinition에 들어가는 3가지는?::설명, 시스템 프롬프트, 도구 제한
여러 MCP 도구의 날짜 형식을 모델이 보기 전에 통일하는 훅은?::PostToolUse
기준 금액 초과 환불을 반드시 막으려면?::나가는 도구 호출을 가로채는 훅으로 차단하고 에스컬레이션으로 돌림
공통 코드베이스 분석에서 두 테스트 전략을 나눠 탐색하려면?::fork_session

## 상황 → 판단
상황: 루프를 언제 끝낼지 → 정답 방향은?::stop_reason == "end_turn"
상황: "완료"라는 말·반복 상한·텍스트 유무로 종료 → 정답 방향은?::안티패턴. stop_reason 기준
상황: 서브에이전트끼리 직접 통신 → 정답 방향은?::코디네이터 경유(허브 앤 스포크)
상황: 서브에이전트는 모두 성공했는데 보고서가 일부 영역만 → 정답 방향은?::코디네이터의 분해가 너무 좁음
상황: 종합 에이전트가 앞 단계 결과를 모름 → 정답 방향은?::결과 전체를 프롬프트에 명시적으로 전달
상황: 코디네이터가 서브에이전트를 못 부름 → 정답 방향은?::allowedTools에 "Task"
상황: 서브에이전트를 빨리 돌리고 싶다 → 정답 방향은?::한 응답에 Task 호출 여러 개
상황: 코디네이터 프롬프트를 어떻게 쓰나 → 정답 방향은?::절차 대신 연구 목표·품질 기준
상황: 신원 확인 전 환불·한도 초과 환불을 반드시 막기 → 정답 방향은?::프로그래밍 방식 강제(선행 조건·훅)
상황: MCP 도구마다 날짜·상태 코드 형식이 다름 → 정답 방향은?::PostToolUse 훅으로 정규화
상황: 대화 기록을 못 보는 상담원에게 넘김 → 정답 방향은?::구조화된 인계 요약(ID, 원인, 금액, 권장 조치)
상황: 한 메시지에 여러 문제 → 정답 방향은?::분해 → 병렬 조사 → 통합
상황: 예측 가능한 다면 리뷰 → 정답 방향은?::프롬프트 체이닝
상황: 레거시 코드에 포괄적 테스트 추가 → 정답 방향은?::동적 적응형 분해
상황: 어제 조사 이어 가기 → 정답 방향은?::--resume <session-name>
상황: 같은 분석에서 두 방식 비교 → 정답 방향은?::fork_session
상황: 이전 도구 결과가 오래됨 → 정답 방향은?::요약을 주입한 새 세션
