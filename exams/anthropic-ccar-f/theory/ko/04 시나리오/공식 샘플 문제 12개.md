### 문제 1

운영 데이터를 보면 12%의 경우 에이전트가 get_customer를 아예 건너뛰고 고객이 말한 이름만으로 lookup_order를 호출해, 가끔 계정을 잘못 식별하고 환불을 잘못 처리한다. 이 신뢰성 문제를 가장 효과적으로 해결하는 변경은?

- **A.** get_customer가 검증된 고객 ID를 반환할 때까지 lookup_order와 process_refund 호출을 막는 프로그래밍 방식 선행 조건을 추가한다.
- **B.** 주문 작업 전에 get_customer로 고객을 확인하는 것이 필수라고 시스템 프롬프트에 명시한다.
- **C.** 고객이 주문 정보를 먼저 말해도 에이전트가 항상 get_customer를 먼저 호출하는 퓨샷 예시를 추가한다.
- **D.** 각 요청을 분석해 요청 유형에 맞는 도구만 켜 주는 라우팅 분류기를 구현한다.

> [!success]- 정답과 해설
> **A**. 업무상 중요한 도구 순서(환불 전 신원 확인)는 프로그래밍 방식 강제가 결정론적으로 보장한다. B와 C는 확률적 준수에 기대므로 금전 피해가 있는 상황에는 부족하다. D는 도구 순서가 아니라 도구 가용성을 다루므로 실제 문제가 아니다.
>

### 문제 2

운영 로그를 보면 사용자가 주문을 물을 때("주문 #12345 확인해 줘") 에이전트가 lookup_order 대신 get_customer를 자주 호출한다. 두 도구의 설명은 짧고("고객 정보를 조회합니다" / "주문 정보를 조회합니다") 받는 식별자 형식도 비슷하다. 도구 선택 신뢰성을 높이는 가장 효과적인 첫 단계는?

- **A.** 주문 관련 쿼리가 lookup_order로 가는 예시 5~8개를 담은 퓨샷 예시를 시스템 프롬프트에 추가한다.
- **B.** 각 도구 설명에 처리하는 입력 형식, 예시 쿼리, 엣지 케이스, 비슷한 도구 대신 언제 써야 하는지에 대한 경계를 넣는다.
- **C.** 매 턴 전에 사용자 입력을 파싱하고 키워드와 식별자 패턴으로 도구를 미리 고르는 라우팅 레이어를 구현한다.
- **D.** 두 도구를 아무 식별자나 받아 내부에서 백엔드를 고르는 lookup_entity 하나로 합친다.

> [!success]- 정답과 해설
> **B**. LLM이 도구를 고르는 주된 수단은 도구 설명이다. B는 근본 원인을 적은 노력으로 바로 고친다. A는 근본 문제를 고치지 않고 토큰만 늘린다. C는 과잉 설계이며 LLM의 자연어 이해를 우회한다. D는 유효한 설계일 수 있지만 "첫 단계"로는 노력이 크다.
>

### 문제 3

에이전트의 첫 접촉 해결률이 55%로 목표 80%에 크게 못 미친다. 로그를 보면 사진 증거가 있는 표준 파손 교체 같은 단순한 사례는 넘기고, 정책 예외가 필요한 복잡한 상황은 스스로 처리하려 한다. 에스컬레이션 보정을 가장 효과적으로 개선하는 방법은?

- **A.** 언제 넘기고 언제 스스로 해결하는지 보여 주는 퓨샷 예시와 함께 명시적 에스컬레이션 기준을 시스템 프롬프트에 추가한다.
- **B.** 응답마다 에이전트가 확신도(1~10)를 스스로 보고하게 하고 임계값 아래면 자동으로 사람에게 보낸다.
- **C.** 과거 티켓으로 학습한 별도 분류 모델을 배포해 메인 에이전트가 처리하기 전에 에스컬레이션 여부를 예측한다.
- **D.** 감정 분석으로 고객 불만 수준을 감지해 부정 감정이 임계값을 넘으면 자동으로 넘긴다.

> [!success]- 정답과 해설
> **A**. 근본 원인은 판단 경계가 불명확한 것이다. 명시적 기준과 퓨샷 예시가 인프라를 더하기 전의 알맞은 첫 대응이다. B: LLM 자체 확신도는 보정이 나쁘고 이미 어려운 사례에서 과신하고 있다. C: 프롬프트 개선도 안 해 보고 레이블 데이터와 ML 인프라를 요구하는 과잉 설계. D: 감정은 사례 복잡도와 상관이 없다.
>

### 문제 4

팀의 표준 코드 리뷰 체크리스트를 실행하는 /review 슬래시 명령을 만들려 한다. 저장소를 clone하거나 pull한 모든 개발자가 쓸 수 있어야 한다. 명령 파일을 어디에 만들어야 하나?

- **A.** 프로젝트 저장소의 .claude/commands/ 디렉터리
- **B.** 각 개발자 홈 디렉터리의 ~/.claude/commands/
- **C.** 프로젝트 루트의 CLAUDE.md 파일
- **D.** commands 배열이 있는 .claude/config.json 파일

> [!success]- 정답과 해설
> **A**. 프로젝트 범위 명령은 저장소의 .claude/commands/에 둔다. 버전 관리되어 clone·pull하면 모두 쓸 수 있다. B는 공유되지 않는 개인 명령. C의 CLAUDE.md는 지시와 컨텍스트용이지 명령 정의용이 아니다. D는 Claude Code에 없는 구성 방식이다.

### 문제 5

팀의 모놀리식 애플리케이션을 마이크로서비스로 재구성하는 일을 맡았다. 수십 개 파일에 걸친 변경과 서비스 경계·모듈 의존성에 대한 결정이 필요하다. 어떤 접근을 택해야 하나?

- **A.** 플랜 모드로 들어가 코드베이스를 탐색하고 의존성을 이해하고 구현 방식을 설계한 뒤 변경한다.
- **B.** 직접 실행으로 시작해 점진적으로 바꾸면서 구현이 자연스러운 서비스 경계를 드러내게 한다.
- **C.** 서비스마다 구조를 정확히 적은 포괄적인 사전 지시와 함께 직접 실행한다.
- **D.** 직접 실행으로 시작하고 예상치 못한 복잡도가 나오면 그때 플랜 모드로 바꾼다.

> [!success]- 정답과 해설
> **A**. 플랜 모드는 대규모 변경, 여러 유효한 접근법, 아키텍처 결정이 걸린 작업을 위한 것이다. B는 늦게 의존성을 발견해 재작업 위험이 크다. C는 탐색 없이 올바른 구조를 안다고 가정한다. D는 복잡도가 이미 요구 사항에 드러나 있다는 점을 무시한다.
>

### 문제 6

코드베이스 영역마다 규칙이 다르다. React 컴포넌트는 훅을 쓰는 함수형, API 핸들러는 특정 오류 처리가 있는 async/await, DB 모델은 리포지토리 패턴을 따른다. 테스트 파일은 테스트 대상 옆에 흩어져 있고(Button.tsx 옆 Button.test.tsx), 위치와 관계없이 모든 테스트가 같은 규칙을 따르게 하고 싶다. Claude가 코드 생성 시 올바른 규칙을 자동으로 적용하게 하는 가장 유지 보수하기 좋은 방법은?

- **A.** 파일 경로에 따라 규칙을 조건부로 적용하는 glob 패턴을 YAML frontmatter에 지정한 규칙 파일을 .claude/rules/에 만든다.
- **B.** 모든 규칙을 루트 CLAUDE.md에 영역별 제목으로 모으고 어느 절이 적용되는지는 Claude의 추론에 맡긴다.
- **C.** 코드 유형마다 .claude/skills/에 스킬을 만들어 SKILL.md에 관련 규칙을 넣는다.
- **D.** 하위 디렉터리마다 그 영역의 규칙을 담은 CLAUDE.md를 둔다.

> [!success]- 정답과 해설
> **A**. glob 패턴(예: **/*.test.tsx)을 쓴 .claude/rules/는 디렉터리 위치와 관계없이 파일 경로로 규칙을 자동 적용한다. B는 명시적 매칭이 아니라 추론에 의존한다. C는 수동 호출이거나 Claude가 로드할지 판단해야 하므로 "자동" 적용과 맞지 않는다. D는 CLAUDE.md가 디렉터리에 묶여 있어 곳곳에 흩어진 파일을 다루기 어렵다.
>

### 문제 7

"AI가 창작 산업에 주는 영향" 주제로 시스템을 돌렸다. 서브에이전트는 모두 성공했다(웹 검색 에이전트는 관련 기사를 찾고, 문서 분석 에이전트는 논문을 정확히 요약하고, 종합 에이전트는 일관된 결과를 냈다). 그런데 최종 보고서는 시각 예술만 다루고 음악, 글쓰기, 영화 제작이 빠졌다. 코디네이터 로그를 보니 주제를 "디지털 아트 제작의 AI", "그래픽 디자인의 AI", "사진의 AI" 세 하위 작업으로 나눴다. 가장 가능성 높은 근본 원인은?

- **A.** 종합 에이전트에 받은 결과의 커버리지 빈틈을 찾는 지시가 없다.
- **B.** 코디네이터의 작업 분해가 너무 좁아 서브에이전트 배정이 주제의 관련 영역을 모두 덮지 못했다.
- **C.** 웹 검색 에이전트의 쿼리가 충분히 포괄적이지 않아 더 많은 창작 산업 분야로 넓혀야 한다.
- **D.** 문서 분석 에이전트가 지나치게 엄격한 관련성 기준 때문에 시각 외 창작 산업 출처를 걸러 냈다.

> [!success]- 정답과 해설
> **B**. 코디네이터 로그가 근본 원인을 그대로 보여 준다. "창작 산업"을 시각 예술 하위 작업으로만 나눠 음악·글쓰기·영화를 뺐다. 서브에이전트는 배정받은 일을 정확히 했고 문제는 배정 자체다. A, C, D는 정상 동작한 하위 에이전트를 탓한다.
>

### 문제 8

복잡한 주제를 조사하던 웹 검색 서브에이전트가 타임아웃됐다. 이 실패 정보가 코디네이터로 어떻게 흘러가야 하나? 지능적인 복구를 가장 잘 가능하게 하는 오류 전파 방식은?

- **A.** 실패 유형, 시도한 쿼리, 부분 결과, 가능한 대안을 담은 구조화된 오류 컨텍스트를 코디네이터에 반환한다.
- **B.** 서브에이전트 안에 지수 백오프 재시도를 구현하고, 모두 실패하면 일반적인 "search unavailable" 상태만 반환한다.
- **C.** 서브에이전트 안에서 타임아웃을 잡아 성공으로 표시한 빈 결과를 반환한다.
- **D.** 타임아웃 예외를 최상위 핸들러로 바로 올려 연구 워크플로 전체를 종료한다.

> [!success]- 정답과 해설
> **A**. 구조화된 오류 컨텍스트가 있어야 코디네이터가 쿼리를 바꿔 재시도할지, 다른 방법을 쓸지, 부분 결과로 진행할지 정할 수 있다. B의 일반 상태는 맥락을 숨긴다. C는 실패를 성공으로 표시해 복구를 막고 불완전한 결과를 만든다. D는 복구할 수 있는데도 전체를 끝낸다.

### 문제 9

테스트 중 종합 에이전트가 결과를 합치며 특정 주장을 자주 검증해야 한다. 지금은 검증이 필요하면 종합 에이전트가 코디네이터에 제어를 돌려주고, 코디네이터가 웹 검색 에이전트를 부른 뒤 결과와 함께 종합을 다시 호출한다. 작업당 왕복이 2~3번 늘고 지연이 40% 증가한다. 평가 결과 검증의 85%는 단순 사실 확인(날짜, 이름, 통계)이고 15%는 깊은 조사가 필요하다. 신뢰성을 유지하면서 부담을 줄이는 가장 효과적인 방법은?

- **A.** 종합 에이전트에 단순 조회용 범위 좁은 verify_fact 도구를 주고, 복잡한 검증은 계속 코디네이터를 거쳐 웹 검색 에이전트에 위임한다.
- **B.** 종합 에이전트가 검증 필요 항목을 모아 패스 끝에 코디네이터에 한꺼번에 돌려주고, 코디네이터가 웹 검색 에이전트에 일괄 전달한다.
- **C.** 종합 에이전트에 모든 웹 검색 도구를 줘 코디네이터를 거치지 않고 모든 검증을 직접 처리하게 한다.
- **D.** 웹 검색 에이전트가 처음 조사할 때 출처마다 주변 맥락을 미리 넉넉히 캐시해 둔다.

> [!success]- 정답과 해설
> **A**. A는 최소 권한 원칙을 적용해 85%의 흔한 경우에 필요한 것만 주고, 복잡한 경우는 기존 조정 패턴을 유지한다. B는 앞선 검증 사실에 의존하는 단계가 막힌다. C는 과잉 권한으로 관심사 분리를 깬다. D는 무엇이 필요할지 예측할 수 없는 추측성 캐시다.
>

## [[시나리오 5 CI용 Claude Code]]

### 문제 10

파이프라인 스크립트가 claude "Analyze this pull request for security issues"를 실행하는데 작업이 무한정 멈춘다. 로그를 보면 Claude Code가 대화형 입력을 기다리고 있다. 자동화 파이프라인에서 Claude Code를 실행하는 올바른 방법은?

- **A.** -p 플래그 추가: claude -p "Analyze this pull request for security issues"
- **B.** 실행 전에 환경 변수 CLAUDE_HEADLESS=true 설정
- **C.** stdin을 /dev/null에서 받기: claude "..." < /dev/null
- **D.** --batch 플래그 추가: claude --batch "..."

> [!success]- 정답과 해설
> **A**. -p(--print)가 문서화된 비대화형 실행 방법이다. 프롬프트를 처리해 stdout에 출력하고 입력을 기다리지 않고 종료한다. B와 D는 없는 기능이고, C는 Claude Code의 명령 구문을 제대로 다루지 못하는 Unix 우회책이다.

### 문제 11

자동 분석의 API 비용을 줄이려 한다. 지금은 실시간 호출이 두 워크플로를 돌린다. (1) 개발자가 병합하기 전에 끝나야 하는 병합 전 검사, (2) 다음 날 아침 검토용으로 밤에 만드는 기술 부채 보고서. 관리자가 50% 절감을 위해 둘 다 Message Batches API로 바꾸자고 제안한다. 어떻게 평가해야 하나?

- **A.** 기술 부채 보고서만 배치로 바꾸고 병합 전 검사는 실시간 호출을 유지한다.
- **B.** 둘 다 배치로 바꾸고 완료 여부를 상태 폴링으로 확인한다.
- **C.** 배치 결과 순서 문제를 피하려고 둘 다 실시간을 유지한다.
- **D.** 둘 다 배치로 바꾸고 너무 오래 걸리면 실시간으로 대체하는 타임아웃을 둔다.

### 문제 12

한 PR이 재고 추적 모듈의 파일 14개를 바꿨다. 모든 파일을 함께 분석하는 단일 패스 리뷰가 일관되지 않은 결과를 낸다. 어떤 파일은 자세히, 어떤 파일은 피상적으로 다루고, 명백한 버그를 놓치고, 한 파일에서 문제라고 한 패턴을 같은 PR의 다른 파일에서는 통과시킨다. 리뷰를 어떻게 재구성해야 하나?

- **A.** 집중 패스로 나눈다. 파일마다 개별로 로컬 문제를 분석한 뒤, 파일 간 데이터 흐름을 보는 별도 통합 패스를 돌린다.
- **B.** 자동 리뷰 전에 개발자가 큰 PR을 3~4개 파일씩 작은 PR로 나누게 한다.
- **C.** 14개 파일에 충분히 주의를 기울이도록 컨텍스트 윈도우가 더 큰 상위 모델로 바꾼다.
- **D.** 전체 PR에 독립 리뷰 패스를 세 번 돌려 두 번 이상 나온 문제만 표시한다.

> [!success]- 정답과 해설
> **A**. 근본 원인은 많은 파일을 한꺼번에 처리하며 생기는 주의 분산이다. 파일별 분석으로 깊이를 고르게 하고, 통합 패스로 파일 간 문제를 잡는다. B는 시스템 개선 없이 개발자에게 부담을 넘긴다. C는 큰 컨텍스트가 주의 품질 문제를 풀지 못한다는 점을 오해한다. D는 간헐적으로만 잡히는 실제 버그를 합의 조건으로 억누른다.
