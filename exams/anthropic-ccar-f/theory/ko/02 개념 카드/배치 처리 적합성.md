# 배치 처리 적합성

> [!summary] 한 줄 정의
> 기다릴 필요가 없는 작업(야간 보고서, 주간 감사, 야간 테스트 생성)은 배치, 개발자가 기다리는 작업(병합 전 검사)은 동기 API.

**English** When to use batch processing

## 시험 트리거
- "비용을 줄이려고 모두 배치로 바꾸자"
- "병합 전에 반드시 끝나야 한다"
- "30시간 SLA"

## 핵심
- 배치 = 50% 절감, **최대 24시간**, **지연 SLA 없음**. → [[Message Batches API]]
- 병합 전 검사처럼 기다리는 작업 → **동기 API 유지**.
- SLA 계산: 24시간 처리로 30시간 SLA를 보장하려면 **4시간 간격**으로 제출(가이드 예시. 계산 근거는 해석: 제출 대기 최대 4시간 + 처리 최대 24시간 = 28시간 ≤ 30시간).
- 실패 처리: custom_id로 실패 문서만 골라 고쳐서(예: 너무 긴 문서 분할) 재제출.
- 대량 처리 전 **샘플 세트로 프롬프트를 다듬어** 첫 처리 성공률을 높인다.

## 오답 함정
> [!warning] 오답이 되기 쉬운 선택지
> - "둘 다 배치로 바꾸고 상태 폴링" → 병합 전 검사는 기다려야 하므로 부적합
> - "배치 결과 순서 문제 때문에 둘 다 실시간 유지" → custom_id로 짝지을 수 있으니 오해
> - "배치 + 늦으면 실시간 대체" → 불필요한 복잡도
