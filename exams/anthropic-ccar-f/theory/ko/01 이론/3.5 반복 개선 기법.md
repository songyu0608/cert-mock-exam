# 태스크 3.5　점진적 개선을 위한 반복 개선 기법을 적용한다

**English** Apply iterative refinement techniques for progressive improvement  
**日本語** 段階的な改善のために反復的な改良手法を適用する

도메인 3　Claude Code 구성과 워크플로 (20%)

Claude Code 결과를 원하는 방향으로 다듬는 피드백 방법을 묻는다.

> [!tip] 핵심 판단
> - 입출력 예시 2~3개
> - 테스트를 먼저 쓰고 실패를 공유하며 반복
> - 인터뷰 패턴, 얽힌 문제는 한 번에·독립 문제는 순차로

## 알아야 할 지식 (Knowledge of)

1. 산문 설명이 일관되지 않게 해석될 때, 기대하는 변환을 전달하는 가장 효과적인 방법은 구체적인 입력/출력 예시라는 점
2. 테스트 주도 반복: 테스트 스위트를 먼저 쓰고, 테스트 실패를 공유하며 반복해 점진적으로 개선하기
3. 인터뷰 패턴: 구현 전에 Claude가 질문하게 해 개발자가 예상하지 못한 고려 사항을 드러내기
4. 모든 문제를 한 메시지에 담을 때(서로 얽힌 문제)와 하나씩 고칠 때(독립된 문제)의 구분

> [!quote]- English 공식 가이드 원문
> 1. Concrete input/output examples as the most effective way to communicate expected transformations when prose descriptions are interpreted inconsistently
> 2. Test-driven iteration: writing test suites first, then iterating by sharing test failures to guide progressive improvement
> 3. The interview pattern: having Claude ask questions to surface considerations the developer may not have anticipated before implementing
> 4. When to provide all issues in a single message (interacting problems) versus fixing them sequentially (independent problems)

> [!quote]- 日本語 公式ガイド
> 1. 文章による説明が一貫性なく解釈される場合に、期待する変換を伝える最も効果的な方法としての具体的な入出力の例
> 2. テスト駆動の反復：先にテストスイートを作成し、テストの失敗を共有しながら反復して段階的な改善を導くこと
> 3. インタビューパターン：実装の前に、開発者が想定していなかった可能性のある考慮事項を洗い出すために、Claudeに質問させること
> 4. すべての問題を単一のメッセージで提示すべき場合（相互に影響する問題）と、順番に修正すべき場合（独立した問題）の見極め

## 할 수 있어야 할 기술 (Skills in)

1. 자연어 설명으로 결과가 일관되지 않을 때 구체적인 입력/출력 예시 2~3개로 변환 요구 사항 명확히 하기
2. 구현 전에 기대 동작, 엣지 케이스, 성능 요구 사항을 다루는 테스트 스위트를 쓰고 테스트 실패를 공유하며 반복하기
3. 익숙하지 않은 도메인에서 구현 전에 인터뷰 패턴으로 설계 고려 사항(예: 캐시 무효화 전략, 실패 모드) 드러내기
4. 엣지 케이스 처리를 고치기 위해 예시 입력과 기대 출력을 담은 구체적인 테스트 케이스 제공(예: 마이그레이션 스크립트의 null 값)
5. 수정이 서로 영향을 주면 얽힌 여러 문제를 한 번의 자세한 메시지로 다루고, 독립된 문제는 순차적으로 반복하기

> [!quote]- English 공식 가이드 원문
> 1. Providing 2-3 concrete input/output examples to clarify transformation requirements when natural language descriptions produce inconsistent results
> 2. Writing test suites covering expected behavior, edge cases, and performance requirements before implementation, then iterating by sharing test failures
> 3. Using the interview pattern to surface design considerations (e.g., cache invalidation strategies, failure modes) before implementing solutions in unfamiliar domains
> 4. Providing specific test cases with example input and expected output to fix edge case handling (e.g., null values in migration scripts)
> 5. Addressing multiple interacting issues in a single detailed message when fixes interact, versus sequential iteration for independent issues

> [!quote]- 日本語 公式ガイド
> 1. 自然言語による説明では一貫しない結果になる場合に、2-3個の具体的な入出力の例を提示して変換の要件を明確にする
> 2. 実装の前に、期待される動作、エッジケース、パフォーマンス要件をカバーするテストスイートを作成し、その後テストの失敗を共有しながら反復する
> 3. インタビューパターンを使用して、不慣れな領域でソリューションを実装する前に、設計上の考慮事項（例：キャッシュの無効化戦略、障害モード）を洗い出す
> 4. 入力例と期待される出力を伴う具体的なテストケースを提示して、エッジケースの処理を修正する（例：移行スクリプトにおけるnull値）
> 5. 修正が相互に影響する場合は、複数の相互に影響する問題を単一の詳細なメッセージで扱い、独立した問題の場合は順番に反復する

## 이 태스크의 카드
- [[반복 개선 기법]] — Claude Code 결과를 점진적으로 개선하는 4가지 기법: 구체적 입출력 예시, 테스트 주도 반복, 인터뷰 패턴, 얽힌 문제는 한 번에·독립 문제는 순차로.
