# 태스크 5.1　긴 상호 작용에서 중요한 정보를 보존하도록 대화 컨텍스트를 관리한다

**English** Manage conversation context to preserve critical information across long interactions  
**日本語** 長いやり取りを通じて重要な情報を保持するために会話コンテキストを管理する

도메인 5　컨텍스트 관리와 신뢰성 (15%)

긴 대화에서 중요한 정보가 사라지지 않게 하는 방법을 묻는다.

> [!tip] 핵심 판단
> - 거래 사실은 요약 밖의 case facts 블록으로
> - 중간 소실 → 핵심 요약을 앞에, 섹션 제목
> - 도구 출력은 쌓이기 전에 관련 필드만

## 알아야 할 지식 (Knowledge of)

1. 점진적 요약의 위험: 수치, 백분율, 날짜, 고객이 말한 기대 사항이 모호한 요약으로 뭉개진다
2. "중간 소실(lost in the middle)" 효과: 모델은 긴 입력의 처음과 끝은 잘 처리하지만 중간 부분의 내용을 빠뜨릴 수 있다
3. 도구 결과가 컨텍스트에 쌓이면서 관련도에 비해 과도하게 토큰을 쓰는 방식(예: 필요한 것은 5개인데 주문 조회마다 필드 40개 이상)
4. 대화의 일관성을 유지하려면 이후 API 요청에 전체 대화 기록을 전달해야 한다는 점

> [!quote]- English 공식 가이드 원문
> 1. Progressive summarization risks: condensing numerical values, percentages, dates, and customer-stated expectations into vague summaries
> 2. The "lost in the middle" effect: models reliably process information at the beginning and end of long inputs but may omit findings from middle sections
> 3. How tool results accumulate in context and consume tokens disproportionately to their relevance (e.g., 40+ fields per order lookup when only 5 are relevant)
> 4. The importance of passing complete conversation history in subsequent API requests to maintain conversational coherence

> [!quote]- 日本語 公式ガイド
> 1. 段階的な要約のリスク：数値、パーセンテージ、日付、顧客が述べた期待が曖昧な要約に圧縮されてしまうこと
> 2. 「lost in the middle」効果：モデルは長い入力の冒頭と末尾の情報は確実に処理するが、中間部分の指摘事項を見落とす場合があること
> 3. ツールの結果がコンテキストに蓄積し、関連性に見合わない量のトークンを消費する仕組み（例：関連するのは5個だけなのに、注文照会ごとに40+個のフィールドが返される）
> 4. 会話の一貫性を維持するために、後続のAPIリクエストで完全な会話履歴を渡すことの重要性

## 할 수 있어야 할 기술 (Skills in)

1. 거래 사실(금액, 날짜, 주문 번호, 상태)을 요약된 기록 밖의 지속적인 "사례 사실(case facts)" 블록으로 뽑아 매 프롬프트에 포함하기
2. 여러 이슈를 다루는 세션에서 구조화된 이슈 데이터(주문 ID, 금액, 상태)를 별도 컨텍스트 계층으로 추출해 유지하기
3. 장황한 도구 출력이 컨텍스트에 쌓이기 전에 관련 필드만 남기기(예: 주문 조회에서 반품 관련 필드만 유지)
4. 위치 효과를 줄이기 위해 집계 입력의 맨 앞에 핵심 결과 요약을 두고, 상세 결과는 명시적인 섹션 제목으로 정리하기
5. 하위 단계의 정확한 종합을 위해 서브에이전트가 구조화된 출력에 메타데이터(날짜, 출처 위치, 방법론 맥락)를 포함하게 하기
6. 하위 에이전트의 컨텍스트 예산이 작을 때, 상위 에이전트가 장황한 내용과 추론 과정 대신 구조화된 데이터(핵심 사실, 인용, 관련도 점수)를 반환하도록 바꾸기

> [!quote]- English 공식 가이드 원문
> 1. Extracting transactional facts (amounts, dates, order numbers, statuses) into a persistent "case facts" block included in each prompt, outside summarized history
> 2. Extracting and persisting structured issue data (order IDs, amounts, statuses) into a separate context layer for multi-issue sessions
> 3. Trimming verbose tool outputs to only relevant fields before they accumulate in context (e.g., keeping only return-relevant fields from order lookups)
> 4. Placing key findings summaries at the beginning of aggregated inputs and organizing detailed results with explicit section headers to mitigate position effects
> 5. Requiring subagents to include metadata (dates, source locations, methodological context) in structured outputs to support accurate downstream synthesis
> 6. Modifying upstream agents to return structured data (key facts, citations, relevance scores) instead of verbose content and reasoning chains when downstream agents have limited context budgets

> [!quote]- 日本語 公式ガイド
> 1. 取引に関する事実（金額、日付、注文番号、ステータス）を、要約された履歴の外に置かれ各プロンプトに含まれる永続的な「ケースの事実情報」ブロックに抽出する
> 2. 複数の問題を扱うセッションのために、構造化された問題データ（注文ID、金額、ステータス）を抽出して別のコンテキストレイヤーに永続化する
> 3. 冗長なツール出力がコンテキストに蓄積する前に、関連するフィールドのみに切り詰める（例：注文照会から返品に関連するフィールドのみを残す）
> 4. 位置による影響を軽減するために、集約した入力の冒頭に主要な指摘事項の要約を配置し、詳細な結果を明示的なセクション見出しで整理する
> 5. 下流での正確な統合を支えるために、サブエージェントに対して構造化出力にメタデータ（日付、情報源の場所、方法論上のコンテキスト）を含めることを要求する
> 6. 下流のエージェントのコンテキスト予算が限られている場合に、冗長なコンテンツや推論チェーンではなく構造化データ（主要な事実、引用、関連性スコア）を返すように上流のエージェントを変更する

## 이 태스크의 카드
- [[사례 사실 블록]] — 금액·날짜·주문 번호·상태 같은 거래 사실을 요약된 기록 밖의 고정 블록으로 뽑아 매 프롬프트에 넣는 방법. 점진적 요약이 숫자를 뭉개는 문제를 막는다.
- [[중간 소실 효과]] — 모델은 긴 입력의 처음과 끝은 잘 처리하지만 중간 부분의 내용을 빠뜨릴 수 있다.
- [[도구 출력 트리밍]] — 도구 결과는 관련도에 비해 토큰을 많이 쓴다(예: 주문 조회마다 필드 40개 이상 중 필요한 것은 5개). 컨텍스트에 쌓이기 전에 관련 필드만 남긴다.
