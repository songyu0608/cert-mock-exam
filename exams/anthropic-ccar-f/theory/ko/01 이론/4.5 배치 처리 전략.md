# 태스크 4.5　효율적인 배치 처리 전략을 설계한다

**English** Design efficient batch processing strategies  
**日本語** 効率的なバッチ処理戦略を設計する

도메인 4　프롬프트 엔지니어링과 구조화된 출력 (20%)

Message Batches API를 언제, 어떻게 쓰는지 묻는다.

> [!tip] 핵심 판단
> - 50% 절감, 최대 24시간, SLA 없음, 다중 턴 도구 호출 불가
> - 기다리는 작업(병합 전 검사)은 동기, 야간·주간 작업은 배치
> - custom_id로 실패분만 재제출, 샘플로 프롬프트를 먼저 다듬기

## 알아야 할 지식 (Knowledge of)

1. Message Batches API: 비용 50% 절감, 최대 24시간 처리 시간, 지연 시간 SLA 보장 없음
2. 배치 처리는 기다릴 필요가 없고 지연을 허용하는 작업(야간 보고서, 주간 감사, 야간 테스트 생성)에 맞고, 기다려야 하는 워크플로(병합 전 검사)에는 맞지 않다
3. 배치 API는 한 요청 안에서 여러 턴에 걸친 도구 호출을 지원하지 않는다(요청 도중 도구를 실행하고 결과를 돌려줄 수 없음)
4. 배치 요청과 응답을 짝짓기 위한 custom_id 필드

> [!quote]- English 공식 가이드 원문
> 1. The Message Batches API: 50% cost savings, up to 24-hour processing window, no guaranteed latency SLA
> 2. Batch processing is appropriate for non-blocking, latency-tolerant workloads (overnight reports, weekly audits, nightly test generation) and inappropriate for blocking workflows (pre-merge checks)
> 3. The batch API does not support multi-turn tool calling within a single request (cannot execute tools mid-request and return results)
> 4. custom_id fields for correlating batch request/response pairs

> [!quote]- 日本語 公式ガイド
> 1. Message Batches API：50%のコスト削減、最大24時間の処理ウィンドウ、レイテンシSLAの保証なし
> 2. バッチ処理は、ノンブロッキングでレイテンシを許容できるワークロード（夜間レポート、週次監査、夜間のテスト生成）に適しており、ブロッキングなワークフロー（マージ前チェック）には適していないこと
> 3. バッチAPIは、単一のリクエスト内でのマルチターンのツール呼び出しをサポートしていないこと（リクエストの途中でツールを実行して結果を返すことはできない）
> 4. バッチのリクエストとレスポンスのペアを対応付けるためのcustom_idフィールド

## 할 수 있어야 할 기술 (Skills in)

1. 워크플로의 지연 요구에 API 방식 맞추기: 기다려야 하는 병합 전 검사에는 동기 API, 야간·주간 분석에는 배치 API
2. SLA 제약에 맞춰 배치 제출 주기 계산하기(예: 24시간 배치 처리로 30시간 SLA를 보장하려면 4시간 간격 제출)
3. 배치 실패 처리: custom_id로 식별한 실패 문서만 알맞게 고쳐 다시 제출(예: 컨텍스트 한도를 넘은 문서를 청크로 분할)
4. 대량 배치 전에 샘플 세트로 프롬프트를 다듬어 첫 처리 성공률을 높이고 반복 재제출 비용 줄이기

> [!quote]- English 공식 가이드 원문
> 1. Matching API approach to workflow latency requirements: synchronous API for blocking pre-merge checks, batch API for overnight/weekly analysis
> 2. Calculating batch submission frequency based on SLA constraints (e.g., 4-hour windows to guarantee 30-hour SLA with 24-hour batch processing)
> 3. Handling batch failures: resubmitting only failed documents (identified by custom_id) with appropriate modifications (e.g., chunking documents that exceeded context limits)
> 4. Using prompt refinement on a sample set before batch-processing large volumes to maximize first-pass success rates and reduce iterative resubmission costs

> [!quote]- 日本語 公式ガイド
> 1. ワークフローのレイテンシ要件にAPIのアプローチを合わせる：ブロッキングなマージ前チェックには同期API、夜間や週次の分析にはバッチAPI
> 2. SLAの制約に基づいてバッチ送信の頻度を計算する（例：24時間のバッチ処理で30時間のSLAを保証するための4時間のウィンドウ）
> 3. バッチの失敗に対処する：失敗した文書（custom_idで特定）のみを、適切な修正（例：コンテキスト制限を超えた文書のチャンク分割）を加えて再送信する
> 4. 大量のバッチ処理を行う前にサンプルセットでプロンプトを改良し、初回の成功率を最大化して、反復的な再送信のコストを削減する

## 이 태스크의 카드
