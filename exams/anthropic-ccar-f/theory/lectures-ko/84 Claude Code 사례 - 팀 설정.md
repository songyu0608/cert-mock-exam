# 84. Claude Code 사례: 팀 설정

이번 섹션에서 ShopAssist 팀은 CLAUDE.md 파일, 규칙, 커맨드, 스킬로 자기 작업에 맞게 Claude Code를 설정했습니다. 넘어가기 전에, 시험이 이런 설정을 어떻게 묻는지 봅니다.

이번 점검은 **한 개발자에게는 되고 나머지 모두에게는 안 되는** Claude Code 설정에 관한 것입니다. 시험의 코드 생성 시나리오가 바로 우리 같은 팀입니다. 그리고 오답은 대개 **맞는 설정을 틀린 파일에 넣습니다.**

## 첫 번째 결정: 레오의 테스트만 이상하다

리포지토리에는 오래된 결제(billing) 모듈이 있습니다. 레거시 코드이고, 이제 팀에서 이 코드를 완전히 이해하는 사람이 없습니다. 가장 최근에 합류한 레오는 누가 이 모듈을 바꾸기 전에 테스트를 추가해야 합니다. 레오가 Claude Code에 요청합니다. 돌아온 테스트는 틀린 테스트 프레임워크를 쓰고, 팀의 가짜 결제 서비스가 아니라 실제 결제 서비스를 호출합니다. 몇 년째 이 프로젝트에서 일한 마리아에게는 Claude Code가 절대 이렇게 하지 않습니다.

**무엇이 필요할까요?** 여기서는 아무도 보장을 요구하지 않습니다. 첫 단계가 필요하고, 그것은 **규칙이 어디에 있는지 알아내는 것**입니다.

**그럴듯한 오답**은 마리아가 자기 규칙 사본을 레오에게 보내, 레오의 홈 폴더에 두게 하는 것입니다. 이 방법은 실패합니다. 두 사본은 서서히 어긋나고, 다음 신규 개발자도 같은 문제를 겪습니다.

**가장 좋은 선택**은 memory 커맨드로 시작합니다. 이 커맨드는 세션이 로드한 메모리 파일을 나열합니다.

| 실행한 사람 | `/memory` 결과 |
| --- | --- |
| 레오 | 프로젝트 CLAUDE.md만. 그 안에 테스트 규칙이 없음 |
| 마리아 | 프로젝트 파일 + 홈 폴더의 사용자 수준 파일. 규칙은 이 파일에 있음 |

사용자 수준 파일은 그 주인에게만 닿고, 버전 관리는 이 파일을 공유하지 않습니다. 그래서 팀 규칙을 풀 리퀘스트로 프로젝트 CLAUDE.md에 옮깁니다. 머지 후 레오가 memory 커맨드를 다시 실행하면 규칙이 로드된 것이 보입니다.

> 제품 참고: `/context`로도 무엇이 로드됐는지 볼 수 있습니다(강의 슬라이드 기준).

### 두 번째 수: 곳곳의 테스트 파일

이 결정에는 두 번째 수가 있습니다. 테스트 파일은 결제, 환불, 채팅 창 등 여러 폴더에서 자기 코드 옆에 있습니다. 약 40개 폴더에 흩어져 있다고 가정합니다.

**그럴듯한 오답**은 그 폴더마다 테스트 규칙을 담은 CLAUDE.md를 두는 것입니다. 이 방법은 실패합니다. 디렉터리 파일은 폴더 하나에 속하므로 사본이 40개 생기고, 새 폴더마다 하나씩 더 필요합니다.

**가장 좋은 선택**은 rules 폴더에 `paths` 필드가 있는 규칙 파일 **하나**를 두는 것입니다. 그 glob 패턴은 어느 폴더에 있든 모든 테스트 파일과 일치합니다. 규칙은 Claude Code가 일치하는 파일로 작업할 때만 로드됩니다.

세부 사항이 하나 더 있습니다. 결제 모듈의 CLAUDE.md는 공유 금액 처리 표준을 `@` 기호와 경로로 import합니다. 그래서 표준은 파일 하나에만 있습니다.

```markdown
# Billing module
@standards/money-handling.md
The shared money standard is imported,
not copied into this file.
Other billing notes go here.
```

**규칙**: 팀 규칙은 프로젝트 파일에 둡니다. 여러 폴더에 흩어진 한 파일 유형의 규칙은 경로별 규칙에 둡니다.

## 두 번째 결정: 마리아만 쓸 수 있는 커맨드와 스킬

마리아는 릴리스 노트 커맨드도 만들었습니다. 머지된 풀 리퀘스트를 읽고 릴리스마다 노트 초안을 씁니다. 이 커맨드 파일은 마리아 홈 디렉터리의 commands 폴더에 있습니다. 마리아가 자리에 없으면 아무도 실행할 수 없습니다. 팀원들은 각자 요청을 직접 입력하고, 노트는 매번 다른 모양으로 나옵니다.

마리아에게는 로그 분석 스킬도 있습니다. 결제 모듈의 오류 로그를 읽고 무엇이 실패했는지 설명합니다. 한 번 실행하면 로그 약 2,000줄이 채팅에 출력된다고 가정합니다. 그 뒤로 대화에는 실제 작업을 위한 공간이 거의 남지 않습니다. 그리고 누군가 입력 없이 스킬을 부르면, 스킬은 어떤 로그를 읽을지 추측합니다.

**무엇이 필요할까요?** 이번에도 첫 단계가 필요하고, 이번에는 설정 안에 있습니다.

### 커맨드

**그럴듯한 오답**은 개발자마다 파일을 자기 홈 폴더에 복사하는 것입니다. 이 방법은 실패합니다. 버전 관리가 그 사본을 보지 못하고, 사본은 서로 어긋납니다.

**가장 좋은 선택**은 커맨드 파일을 리포지토리 `.claude` 폴더 안의 commands 폴더(`.claude/commands/`)에 두고 커밋하는 것입니다. 그러면 리포지토리를 clone하거나 pull하는 모든 사람이 같은 커맨드를 받습니다. 마리아가 자기 버전을 원하면, 홈 폴더에 **다른 이름으로** 둡니다. 그래야 마리아에게서 팀 커맨드를 대신하지 않습니다.

### 스킬

**그럴듯한 오답**은 스킬 지침에 "출력을 짧게 하라"를 넣는 것입니다. 이 방법은 실패합니다. 읽는 일은 여전히 메인 대화에서 일어납니다.

**가장 좋은 선택**은 스킬의 frontmatter에 있습니다.

```markdown
---
description: Explain errors in the billing logs
context: fork
argument-hint: "[date range of the logs]"
allowed-tools: Read, Grep
---
Read the logs and explain what failed.
```

| 키 | 효과 |
| --- | --- |
| `context: fork` | 스킬을 격리된 서브에이전트로 실행하므로, 짧은 결과만 돌아옵니다. |
| `argument-hint` | 로그의 날짜 범위처럼, 개발자가 어떤 입력을 줘야 하는지 알려 줍니다. |
| `allowed-tools` | 시험 기준으로, Read와 Grep처럼 읽기만 하는 도구로 스킬을 제한합니다. |

> 제품 참고: 현재 제품은 allowed-tools를 다르게 해석합니다. 나열한 도구를 미리 승인할 뿐, 아무것도 제한하지 않습니다(강의 슬라이드 기준). 시험에서는 allowed-tools가 스킬을 제한한다고 답합니다.

**규칙**: 공유 워크플로는 리포지토리에 두고, 노이즈가 많은 스킬은 포크에서 실행합니다.

## 정리

- 새 팀원에게 팀 규칙이 빠져 있으면, memory 커맨드로 사용자 수준을 확인하고 그 규칙을 프로젝트 CLAUDE.md로 옮깁니다.
- 여러 폴더에 흩어진 파일의 규칙은 폴더마다 CLAUDE.md를 두지 않고, paths glob이 있는 규칙에 둡니다.
- import로 공유 표준을 파일 하나에 둡니다.
- 팀 커맨드는 리포지토리 commands 폴더에 두고, 개인 변형은 다른 이름을 씁니다.
- 출력이 긴 스킬에는 context fork와 argument hint를 씁니다.

같은 규칙이 시험의 **CI 시나리오**에서도 통합니다. 거기서 Claude Code는 파이프라인에서 print의 약자인 `-p` 플래그로 실행되고, 키보드 앞에는 아무도 없습니다. 파이프라인 머신에는 개발자의 홈 폴더가 없으므로, 리포지토리에 있는 것만 로드합니다.

| 위치 | 파이프라인에서 |
| --- | --- |
| 리포지토리: CLAUDE.md, 규칙, 커맨드, 스킬 | 로드됨 |
| 내 홈 폴더: 개인 습관 | 없음 |

공유 지침, 커맨드, 스킬은 모두 리포지토리에 두고, 개인 습관만 홈 폴더에 두세요.
