# 91. CI 리뷰와 테스트를 위한 컨텍스트

이번 노트에서는 CI 실행이 쓸모 있는 리뷰와 테스트를 내고, 같은 말을 되풀이하지 않으려면 어떤 컨텍스트가 필요한지 살펴봅니다.

| 문제 | 결과 |
| --- | --- |
| 눈먼 실행 | 프로젝트를 볼 수 없으니 조언이 일반론에 그칩니다. |
| 반복하는 실행 | 같은 코멘트를 계속 올려서, 결국 개발자들이 읽지 않게 됩니다. |

## 일주일 뒤의 로그

팀의 리뷰 봇은 이제 ShopAssist의 모든 풀 리퀘스트에서 CI로 Claude Code를 실행합니다. print 플래그를 쓰므로 작업이 스스로 끝나고, 스키마를 쓰므로 모든 지적 사항이 JSON으로 돌아옵니다. 팀은 같은 작업에 변경마다 테스트를 제안하라는 일도 맡깁니다.

일주일 뒤, 로그에 세 가지 문제가 보입니다.

1. **틀린 프레임워크**: 제안된 테스트가 틀린 테스트 프레임워크를 쓰고, 일부는 실제 결제 서비스를 호출합니다.
2. **중복 테스트**: 제안된 테스트 상당수가 이미 존재합니다.
3. **반복되는 코멘트**: 개발자가 새 커밋을 push할 때마다 리뷰가 같은 코멘트를 다시 올립니다.

가장 중요한 원칙은 **CI 실행은 기억 없이 시작한다**는 것입니다. 실행은 리포지토리와 프롬프트만 보고, 그 밖에는 아무것도 보지 못합니다. 누구의 대화 기록도 닿지 않습니다. 그래서 실행이 알아야 할 것은 모두 리포지토리나 프롬프트에서 와야 합니다.

| 출처 | 실행이 보나? |
| --- | --- |
| 리포지토리: 커밋된 파일 | 봄 |
| 프롬프트: 스크립트가 보내는 텍스트 | 봄 |
| 대화 기록 | 보지 못함 |

이번 노트에서는 출처 세 가지를 봅니다. 프로젝트 CLAUDE.md, 기존 테스트 파일, 이전 지적 사항입니다.

## 1. 프로젝트 CLAUDE.md

Claude Code는 개발자 책상에서와 똑같이 CI에서도 이 파일을 읽습니다. CI 머신에는 개발자의 홈 폴더가 없으므로, 개인 파일은 절대 닿지 않습니다. **커밋된 것만 중요합니다.**

그래서 프로젝트 파일에 네 종류의 컨텍스트를 담습니다.

| 종류 | 내용 |
| --- | --- |
| 테스트 표준 | 테스트 프레임워크, 테스트 파일이 있는 곳 |
| 가치 있는 테스트의 기준 | ShopAssist에서 가치 있는 테스트는 돈이 오가거나 결정을 바꾸는 동작을 확인합니다. 500달러 한도, 30일 반품 기간, 배송일이 없는 주문이 예입니다. 가치가 낮은 테스트는 저장된 필드를 반환하기만 하는 함수처럼 사소한 것을 확인합니다. |
| 사용 가능한 픽스처 | **픽스처**는 테스트가 재사용할 수 있는 미리 만든 테스트 데이터나 가짜 서비스입니다. 가짜 결제 서비스, 주문이 두 개인 샘플 고객이 있습니다. |
| 리뷰 기준 | 버그와 보안 문제를 보고하고, 사소한 스타일은 건너뜁니다. |

```markdown
# Testing standards
- Framework: pytest; test files in a tests folder
# Valuable tests
- Check behavior that moves money or changes a decision:
  $500 limit, 30-day return window, no delivery date
- Skip trivial tests, such as returning a stored field
# Fixtures
- fake payment service
- sample customer with two orders
# Review criteria
- Report bugs and security problems; skip minor style
```

이 파일이 있으면 제안된 테스트가 우리 프레임워크와 가짜 결제 서비스를 쓰고, 환불과 에스컬레이션 경로에 집중합니다.

대신 테스트 프롬프트를 더 길게 써서 모든 것을 다루길 바라면 안 됩니다. 표준은 커밋된 파일 하나에 두고, 모든 실행이 그 파일을 읽습니다.

## 2. 기존 테스트

풀 리퀘스트 하나가 부분 환불을 추가합니다. 작업은 100달러 전액 환불이 성공하는지 확인하는 테스트를 제안합니다. 그 테스트는 이미 있습니다. Claude는 테스트 스위트를 본 적이 없어서 몰랐습니다.

그래서 CI 스크립트가 이제 변경된 코드의 테스트 파일을 Claude에 줍니다. 프롬프트는 이렇게 말합니다. 이 시나리오들은 이미 다뤄졌으니, 빠진 시나리오만 제안하라.

이제 제안이 달라집니다. 300달러짜리 부분 환불 두 건이 같은 주문에 들어옵니다. 한도가 그 합계에도 적용될까요? 이 질문에 답하는 기존 테스트가 없으므로, 이 테스트는 실제로 가치를 더합니다.

## 3. 이전 지적 사항

리뷰마다 새 세션으로 하는 새 실행입니다. 그래서 "같은 말 반복하지 마"는 아무 의미가 없습니다. 실행은 자기가 전에 무엇을 말했는지 볼 수 없습니다. 그 지침만 추가하면 안 됩니다.

해결책은 실행에 이전 지적 사항을 주는 것입니다. 지난 노트에서 이미 리뷰마다 JSON으로 저장했습니다. 다음 실행에서 스크립트가 그 지적 사항을 새 diff 옆에 프롬프트로 넣습니다. 지침은 이렇습니다. 새로운 이슈나 아직 고쳐지지 않은 이슈만 보고하라. 이미 고쳐진 이슈는 다시 보고하지 마라.

어떻게 동작하는지 봅시다. 첫 실행이 이슈 A, B, C를 찾았다고 가정합니다. 개발자가 A와 B를 고치고 새 커밋을 push합니다.

| 두 번째 실행 | 결과 |
| --- | --- |
| 이전 지적 사항 없음 | A, B, C 코멘트를 모두 다시 올리고, 어쩌면 D도 |
| 이전 지적 사항 포함 | C는 아직 열림, D는 새 이슈로 보고. 고친 A와 B는 조용함 |

두 번째 보호 장치로, 스크립트는 같은 줄에 이미 있는 코멘트를 건너뛸 수도 있습니다.

이 모든 것은 **강제가 아니라 컨텍스트**라는 점을 기억하세요. Claude가 무엇을 보고하고 제안할지 방향을 잡아 줄 뿐입니다. 반드시 통과해야 하는 테스트는 여전히 일반 CI 검사로 실행합니다.

## 정리

- CI 실행에는 기억이 없으므로, 컨텍스트는 리포지토리와 프롬프트에서 와야 합니다.
- 프로젝트 CLAUDE.md는 테스트 표준, 가치 있는 테스트의 기준, 픽스처, 리뷰 기준을 담습니다.
- 테스트 생성에는 기존 테스트 파일을 주어, 빠진 시나리오만 제안하게 합니다.
- 새 커밋 뒤의 재실행에는 이전 지적 사항을 주어, 새로운 이슈나 아직 고쳐지지 않은 이슈만 보고하게 합니다.

Claude Code를 파이프라인에서 실행하기 전에, 실행이 스스로 볼 수 없는 것이 무엇인지 물어보세요. 그리고 프로젝트 파일, 기존 테스트, 자신의 이전 지적 사항을 주세요. 다음 노트에서는 Claude Code를 CI 리뷰어로 직접 실행해 봅니다.
