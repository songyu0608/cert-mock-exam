# 101. 시험 범위 밖: 트레이스로 Claude 애플리케이션 디버깅

ShopAssist는 이제 답하기 전에 스토어의 헬프센터를 검색할 수 있습니다. 이번 노트는 디버깅을 다룹니다. 디버깅은 Claude 애플리케이션이 잘못된 정확한 단계를 찾는 일입니다. 눈에 띄는 해결책이 엉뚱한 곳에 있는 경우가 많기 때문에 중요합니다.

> 이 주제는 시험에 나오지 않습니다. 실제 시스템을 운영하기 위한 배경 지식입니다.

## 장면

ShopAssist는 몇 달째 운영 중입니다. Agent SDK 위에서 돌아가고, 스토어의 MCP 서버가 제공하는 도구 4개를 씁니다. 한 고객이 문의합니다. 지난주에 재킷을 반품했고, 환불이 어떻게 됐는지 묻습니다. ShopAssist는 환불이 아직 대기 중이라고 답합니다. 그런데 스토어의 결제 기록에는 3일 전에 환불이 지급된 것으로 나옵니다. 고객은 헷갈려서 스토어에 다시 연락합니다.

첫 번째 아이디어는 프롬프트를 바꾸는 것입니다. 예를 들어 환불 상태에 관한 줄을 새로 넣습니다. 이렇게 해도 아무것도 고쳐지지 않을 수 있습니다. 용의자는 넷입니다.

| 용의자 | 질문 |
| --- | --- |
| 프롬프트 문구 | 환불 문장을 새로 넣어도 소용없을 수 있음 |
| 도구 선택 | Claude가 잘못된 도구를 골랐나? |
| 도구 데이터 | 도구가 틀린 데이터를 돌려줬나? |
| 우리 코드 | 데이터는 맞았는데 우리 코드가 잘못 읽었나? |

이것들은 서로 다른 문제이고, 각각 다른 해결책이 필요합니다.

> 가장 중요한 점: 실제 동작이 기대와 처음으로 달라지는 단계를 찾으세요. 그다음 그 레이어를 고치세요.

세 가지를 살펴봅니다. 첫째, 트레이스. 둘째, 실패가 시작될 수 있는 레이어. 셋째, 실패 유형에 따라 달라지는 복구.

## 첫째: 트레이스

트레이스는 최종 답을 만든 모든 단계의 기록입니다. 에이전트의 경우 트레이스는 이미 아는 루프를 따라갑니다. 우리 코드가 요청을 보내고 Claude가 응답합니다. Claude가 도구를 요청하면 우리 코드가 실행합니다. 결과가 돌아가고, Claude가 다시 응답합니다.

이 케이스의 트레이스를 위에서부터 순서대로 읽고, 처음으로 잘못돼 보이는 단계에서 멈춥니다.

1. **요청**: 성공했나? 의도한 모델, 시스템 프롬프트, 전체 대화를 썼나? 여기서는 그렇습니다.
2. **Claude의 응답**: Claude는 `get_customer`를 요청했고, 이어서 맞는 주문으로 `lookup_order`를 요청했습니다. 맞는 도구에 유효한 입력입니다.
3. **도구 실행**: 주문 서비스는 맞는 주문과 확인된 고객을 받았고, 응답했습니다.
4. **도구 결과**: 원본 결과에서 환불 상태는 숫자이고, 그 숫자는 refunded를 뜻합니다. 그런데 Claude는 원본 결과를 보지 못했습니다. 우리의 `PostToolUse` 훅이 Claude가 읽기 전에 상태 코드를 단어로 바꿉니다. 훅의 코드 표가 오래됐습니다. refunded 코드를 몰라서 기본값으로 "pending"을 씁니다. Claude는 받은 것을 근거로 올바르게 답했습니다.

```text
주문 서비스 → 우리 훅: refund_status: 3 (refunded)
우리 훅 → Claude: refund_status: pending
Claude → 고객: answer: still pending
```

그러니 처음으로 잘못된 단계는 우리 코드에 있는 훅입니다. 해결책은 훅의 표를 고치고 모든 상태 코드에 대한 테스트를 추가하는 것입니다. 모르는 코드는 추측이 아니라 오류가 되어야 합니다.

```python
STATUS_WORDS = {
    1: "requested",
    2: "pending",
    3: "refunded",
}
def to_word(code):
    if code not in STATUS_WORDS:
        raise ValueError(f"unknown status {code}")
    return STATUS_WORDS[code]
```

프롬프트를 바꿔서는 이것을 고칠 수 없습니다. 더 나쁘게는, 몇몇 케이스에서 증상만 숨기고 버그는 그대로 남길 수 있습니다.

## 둘째: 레이어

모든 실패를 같은 방식으로 읽고, 트레이스가 어느 레이어를 볼지 알려 줍니다.

| 레이어 | 실패의 예 |
| --- | --- |
| 통합 | API가 오류를 돌려줌: 잘못된 키, 속도 제한, 잘못된 요청, 서버 문제. Claude는 답하지 않았으므로 모델은 문제가 아님 |
| 우리 도구와 코드 | 데이터베이스 쿼리가 깨짐, 권한이 빠짐, 맞는 응답의 엉뚱한 필드를 읽음 |
| 컨텍스트 | Claude가 오래된 도구 결과나 이전 작업에서 남은 사실을 받음. 요청은 성공하고 도구도 동작하지만 Claude는 잘못된 그림으로 추론함 |
| 프롬프트나 도구 설명 | 지시가 불명확하거나, 규칙이 빠졌거나, 예시가 잘못된 방향을 가리킴 |

도구와 컨텍스트가 맞는데 Claude가 잘못된 도구를 골랐다면, 그때 프롬프트나 도구 설명을 봅니다. 그러니 프롬프트 변경은 괜찮지만, 트레이스가 프롬프트를 실패 원인으로 보여 줄 때만입니다.

### 좋은 로그

이 모든 것에는 좋은 로그가 필요합니다. 케이스마다 애플리케이션이 보낸 것과 Claude가 돌려준 것을 기록합니다. 어떤 도구가 실행됐고 무엇을 돌려줬는지도 기록합니다. 이 기록이 없으면 디버깅은 추측일 뿐입니다.

하지만 요청과 도구 결과에는 고객 데이터가 들어 있을 수 있습니다. 그러니 실패를 찾을 만큼만 기록하고, 나머지는 가립니다. 고객의 이메일, 카드 번호, API 키가 로그에 전부 그대로 나타나서는 안 됩니다.

```json
{
  "sent": {"messages": 4, "system": "v12"},
  "claude": {"tool_use": "lookup_order"},
  "tool_ran": "lookup_order",
  "tool_result": {"refund_status": 3},
  "customer_email": "a***@example.com",
  "card": "**** **** **** 4242",
  "api_key": "sk-ant-****"
}
```

## 셋째: 복구

올바른 대응은 실패 유형에 따라 다릅니다.

| 실패 유형 | 대응 |
| --- | --- |
| 일시적 실패(속도 제한, 너무 바쁜 서버) | 저절로 사라질 수 있음. API의 `retry-after` 헤더만큼 기다린 뒤 재시도 |
| 잘못된 요청 | 그대로 다시 보내면 또 실패함. 요청을 고침 |
| 권한 실패 | 재시도가 아니라 승인이나 사람이 필요함 |
| 파싱이나 훅의 버그 | 코드를 고치고 테스트를 추가 |
| 낡은 컨텍스트 | 새 데이터가 필요함. 주문을 다시 조회하거나 깨끗한 상태에서 새로 시작 |
| 프롬프트 문제 | 프롬프트를 바꿈 |

수정한 뒤에는 테스트 세트를 다시 돌려, 그 수정이 다른 케이스를 깨뜨리지 않게 합니다.

## 정리

- 트레이스는 요청부터 최종 답까지의 모든 단계를 기록합니다.
- 순서대로 읽고, 기대와 처음으로 다른 단계에서 멈춥니다.
- 그 단계가 레이어를 알려 줍니다. 통합, 도구나 우리 코드, 컨텍스트, 또는 프롬프트입니다.
- 실패를 진단할 만큼 기록하고, 고객 데이터와 비밀은 가립니다.
- 일시적 실패만 재시도하고, 나머지는 원인이 된 레이어에서 고칩니다.

그러니 애플리케이션이 뭔가를 틀렸을 때 프롬프트를 다시 쓰는 것부터 시작하지 마세요. 트레이스를 읽고, 처음으로 잘못된 단계를 찾고, 그 레이어를 고치세요.

다음 노트에서는 시험 범위 밖의 또 다른 주제를 다룹니다. Claude가 읽는 콘텐츠 안에 숨은 지침입니다.
