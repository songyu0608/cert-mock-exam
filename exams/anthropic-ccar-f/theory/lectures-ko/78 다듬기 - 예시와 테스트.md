# 78. 다듬기: 예시와 테스트

지난 노트에서는 Explore 서브에이전트가 노이즈 많은 검색을 메인 대화 밖에 두는 것을 봤습니다.

이번 노트에서는 설명한 변경을 Claude Code가 계속 잘못 이해할 때 무엇을 해야 하는지 살펴봅니다. 설명을 새로 할 때마다 라운드가 하나 더 들고, 다음 답이 또 다른 방식으로 틀릴 수도 있습니다.

## 다시 시도할 때마다 새로운 방식으로 실패한다

ShopAssist는 모든 환불을 상점 데이터베이스의 레코드로 저장합니다. 옛 레코드는 옛 형식이고, 팀은 이를 새 형식으로 옮기는 중입니다. 한 개발자가 Claude Code에 **마이그레이션 스크립트**를 써 달라고 합니다. 마이그레이션 스크립트는 저장된 데이터를 한 형식에서 다른 형식으로 바꾸는 프로그램입니다.

요청 내용은 이렇습니다. 금액은 센트로 저장하고, 날짜는 연, 월, 일로 쓰고, 상태 코드는 단어로 바꿔라. 돌아온 스크립트는 틀렸습니다. 개발자가 더 자세히 다시 설명합니다. 두 번째도, 세 번째도 틀립니다. 매번 틀린 부분이 다릅니다.

가장 중요한 원칙은 **설명이 여러 방식으로 읽힌다면, 설명을 멈추고 보여 준다**는 것입니다.

| 도구 | 내용 |
| --- | --- |
| 예시 | 입력과 출력 쌍 |
| 테스트 먼저 | 코드보다 먼저 작성 |
| 정확한 사례 하나 | 엣지 케이스용 |

## 1. 예시

무엇이 잘못됐는지 봅시다.

```text
# an old refund record
{
  "amount": "12",
  "date": "03/09/2026",
  "status": 7
}
# 3 March or 9 September?
# 12 dollars or 12 cents?
```

- 옛 날짜는 숫자 두 개로 적혀 있습니다. 3월 9일일까요, 9월 3일일까요? "연, 월, 일"이라는 말은 알려 주지 않습니다.
- 12달러인 옛 금액은 그냥 `"12"`로 저장돼 있습니다. Claude Code는 이것을 12센트로 바꿨습니다.

우리에게는 분명한 설명이었지만, 두 가지로 읽을 수 있었습니다.

그래서 문장을 더 붙이지 않습니다. 대신 구체적인 예시를 두세 개 줍니다. 각 예시는 옛 레코드와, 그것이 되어야 할 정확한 새 레코드를 보여 줍니다.

```text
# each example: an old record and the exact new record
# 1. the day comes first
{"date": "03/09/2026"} → {"date": "2026-09-03"}
# 2. twelve dollars is 1200 cents
{"amount": "12"} → {"amount_cents": 1200}
# 3. status code 7 is a word
{"status": 7} → {"status": "refunded"}
```

첫 예시는 날짜를 9월 3일로 보여 주므로 일과 월의 순서가 정해집니다. 두 번째는 `"12"`가 1,200센트가 되는 것을, 세 번째는 상태 코드 7이 단어 `"refunded"`가 되는 것을 보여 줍니다.

**예시는 두 가지로 읽을 수 없습니다.** 프롬프트의 few-shot 예시에서 본 것과 같은 생각입니다. 여기서는 코드 변경을 고정합니다.

| 방법 | 결과 |
| --- | --- |
| 네 번째, 더 긴 설명 | 말이 늘어도 같은 빈틈이 남고, 새 빈틈이 생길 수 있습니다. |
| 구체적인 입력·출력 예시 | 시험 기준으로, 글로 쓴 설명이 일관되지 않은 결과를 낼 때 가장 효과적인 해결책입니다. |

## 2. 테스트 먼저

예시는 주요 사례를 보여 줍니다. 테스트는 모든 사례를 매번 확인합니다. 그래서 Claude Code가 스크립트를 쓰기 전에 테스트 스위트를 먼저 씁니다. **테스트 스위트**는 함께 실행되는 테스트 묶음입니다. 우리 스위트는 세 가지를 다룹니다.

- **기대 동작**: 예시가 테스트가 됩니다.
- **엣지 케이스**: 금액 0이나 알 수 없는 상태 코드 같은 특이한 레코드입니다.
- **성능**: 실제 테이블에 레코드가 200만 개 있다고 가정합니다. 그래서 한 테스트는 표본 1만 개를 변환하고, 몇 초 안에 끝나야 합니다.

```python
def test_examples():
    assert convert(OLD_1) == NEW_1
    assert convert(OLD_2) == NEW_2
def test_edge_cases():
    assert convert(ZERO_AMOUNT)["amount_cents"] == 0
    assert convert(UNKNOWN_STATUS)["status"] == "unknown"
def test_ten_thousand_records():
    with max_seconds(5):
        convert_all(SAMPLE_10K)
```

그다음 Claude Code가 스크립트를 쓰고 Bash로 테스트를 실행합니다. 이제 반복합니다.

1. 일부 테스트가 실패합니다.
2. 실패마다 테스트가 보고한 그대로 공유합니다. 입력, 기대 출력, 실제 출력입니다.
3. Claude Code가 그 사례를 고치고 스위트를 다시 실행합니다.
4. 라운드마다 실패하는 테스트가 줄어듭니다.

그래서 작업이 언제 끝났는지는 눈으로 판단하지 않고 테스트가 알려 줍니다.

"아직 틀렸어, 고쳐 줘"라고만 답하면 안 됩니다. Claude Code는 어떤 사례가 실패했는지 볼 수 없으므로, 이미 맞던 코드를 바꿀 수도 있습니다. **정확한 실패가 정확한 목표가 됩니다.**

## 3. 엣지 케이스에는 정확한 사례 하나

몇 라운드 뒤 문제가 하나 남습니다. 일부 옛 환불은 상품이 배송되기 전에 지급됐습니다. 이들의 배송일은 비어 있고, 이 값을 null이라고 합니다. 스크립트는 그 자리를 오늘 날짜로 채웁니다.

```text
# an old refund, paid before the item was delivered
{"id": "RF-1042", "delivered_at": null, "amount": "12"}
# what the script wrote
{"id": "RF-1042", "delivered_at": "2026-10-14", "amount_cents": 1200}
# a made-up date: the 30-day return window starts on the wrong day
# "handle missing dates properly" - today? a default? skip the record?
```

이것은 ShopAssist의 규칙을 어깁니다. **ShopAssist는 주문에서 읽지 않은 배송일을 말하지 않습니다.** 지어낸 날짜 때문에 30일 반품 기간이 엉뚱한 날에 시작됩니다.

"빠진 날짜를 제대로 처리하라" 같은 메모는 다시 모호합니다. "제대로"는 오늘 날짜일 수도, 기본 날짜일 수도, 레코드를 건너뛰는 것일 수도 있습니다. 그래서 구체적인 테스트 사례 하나를 추가합니다. 입력은 배송일이 null인 옛 레코드이고, 기대 출력은 배송일이 똑같이 null이고 나머지 필드는 평소처럼 변환된 새 레코드입니다.

```python
# one specific test for one edge case
def test_null_delivery_date_stays_null():
    old = {"id": "RF-1042", "delivered_at": None, "amount": "12"}
    expected = {"id": "RF-1042", "delivered_at": None, "amount_cents": 1200}
    assert convert(old) == expected
# run it: the failure shows exactly where the output differs
# fix that one path - the test stays in the suite
```

Claude Code는 테스트를 실행해 자기 출력이 어디서 다른지 정확히 봅니다. 그리고 그 경로 하나만 고칩니다. 테스트는 스위트에 남으므로, 버그가 조용히 되돌아오지 못합니다.

## 정리

- Claude Code가 글로 쓴 설명을 여러 방식으로 읽으면, 구체적인 입력·출력 예시를 두세 개 줍니다.
- 코드보다 테스트를 먼저 씁니다. 테스트는 기대 동작, 엣지 케이스, 성능을 다룹니다.
- 라운드마다 코드를 개선하고, 실패마다 입력, 기대 출력, 실제 출력을 공유합니다.
- null 값 같은 엣지 케이스에는 정확한 입력과 정확한 기대 출력을 가진 구체적인 테스트 사례 하나를 추가합니다.

Claude Code가 변경을 잘못 이해하면 다시 설명하지 마세요. 예시로 보여 주고, 테스트로 확인하세요. 다음 노트에서는 작업이 시작되기 전에 Claude Code가 우리에게 질문하게 합니다.
