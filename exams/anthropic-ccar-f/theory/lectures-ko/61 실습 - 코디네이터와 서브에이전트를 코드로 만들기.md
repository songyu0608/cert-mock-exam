# 61. 실습: 코디네이터와 서브에이전트를 코드로 만들기

한 고객이 주문 금액이 두 번 결제됐다고 문의합니다. 이 메시지 하나에는 주문 확인과 결제 수정이라는 두 종류의 일이 섞여 있습니다. 앞에서는 루프와 도구 몇 개로 에이전트 하나를 만들었습니다. 모든 도구와 모든 지침을 가진 에이전트 하나는 점점 헷갈리고 비싸집니다. 그래서 이번 노트에서는 일을 코디네이터 하나와 작은 에이전트 둘에 나눕니다.

## 전체 흐름

1. 고객 메시지가 코디네이터에게 갑니다.
2. 코디네이터에게는 데이터 도구가 없으므로, 할 수 있는 일은 위임뿐입니다.
3. 코디네이터가 주문 에이전트에게 주문 확인을 맡기고 짧은 보고를 받습니다.
4. 코디네이터가 결제 에이전트에게 결제 수정을 맡기면서 그 보고 내용을 넘깁니다.
5. 결제 에이전트가 한 일을 보고하면, 코디네이터가 고객에게 답합니다.

아래에서 위로 만들어 갑니다. 에이전트를 실행하는 코드, 주문 에이전트, 결제 에이전트, 마지막으로 코디네이터 순서입니다.

## 준비: 공통 설정과 도구를 만드는 헬퍼

빈 파일 `coordinator.py`에 늘 쓰던 설정을 붙여 넣습니다. `json`, `.env`의 키, 클라이언트, 모델 이름입니다. 세 에이전트 모두 같은 모델을 씁니다. 여기에 `FUNCTIONS`라는 빈 딕셔너리를 한 줄 추가합니다. 루프 스크립트의 매핑처럼 도구 이름을 Python 함수에 연결합니다. 각 에이전트 부분이 자기 함수를 여기에 추가합니다.

에이전트들에게 필요한 도구는 모두 다섯 개이고, 도구 정의마다 여러 줄이 필요합니다. 그래서 도구 하나를 만드는 작은 헬퍼부터 둡니다. `make_tool`은 이름, 설명, 입력 필드를 받아, 도구 정의에서 익숙한 모양을 돌려줍니다. 이름, 설명, 입력 스키마가 있고, 입력은 객체이며 속성은 전달한 필드입니다. 모든 필드는 필수입니다.

아래는 스크립트 설명에 맞춘 예시이며, 원본 코드와 세부 표현은 다를 수 있습니다.

```python
FUNCTIONS = {}

def make_tool(name, description, fields):
    return {
        "name": name,
        "description": description,
        "input_schema": {
            "type": "object",
            "properties": fields,
            "required": list(fields),
        },
    }
```

쓰기 전에 확인해 봅니다. 주문 ID 필드 하나로 `lookup_order` 도구를 만들어 출력하면 익숙한 모양이 나옵니다. 전달한 필드는 모두 필수이므로 주문 ID가 `required` 목록에 들어 있습니다. Claude가 기대하는 모양 그대로이니 테스트 줄은 지웁니다.

## 모든 에이전트가 쓰는 `run_agent`

이제 모든 에이전트가 실행하는 부분입니다. `run_agent`는 이름, 시스템 프롬프트, 도구 목록, 할 일(task)을 받습니다. 흐름 속의 각 에이전트는 이 함수 하나에 인수만 다르게 준 것입니다.

- 대화는 할 일을 담은 사용자 메시지 하나로 시작합니다. **모든 에이전트는 빈 대화로 시작하고, 이 할 일만 압니다.** 이 점이 중요합니다.
- 나머지는 앞에서 만든 루프와 같습니다. 다른 점은 이 에이전트의 시스템 프롬프트와 도구를 보낸다는 것뿐입니다.
- 새로 추가하는 줄이 하나 있습니다. 도구를 실행한 직후, 대괄호 안에 에이전트 이름을 넣고 도구와 입력을 출력합니다. 그래서 어느 에이전트가 무엇을 하는지 볼 수 있습니다.
- 결과를 Claude에 돌려주고 루프가 다시 돕니다. 루프가 끝나면 마지막 답의 블록을 돌며 텍스트를 돌려줍니다.

## 주문 에이전트

주문 에이전트의 데이터는 `ORDERS` 딕셔너리입니다. 주문이 하나 있습니다. 45일 전에 배송된 60달러짜리 램프입니다. `lookup_order`는 주문을 돌려주고, 그런 주문이 없으면 오류를 돌려줍니다. 이 함수를 이름과 함께 매핑에 추가합니다.

주문 에이전트의 도구는 헬퍼로 만든 `lookup_order` 하나뿐이고, 입력은 문자열 주문 ID입니다. 주문 에이전트 자체는 자기 인수를 넣은 `run_agent`일 뿐입니다.

| 항목 | 내용 |
| --- | --- |
| 이름 | `order` |
| 시스템 프롬프트 | 주문을 확인하고 상품, 상태, 배송 후 경과 일수를 한 문장으로 보고한다. |
| 도구 | 주문 도구만 |
| 할 일 | 이 주문을 확인하라. |

다음으로 넘어가기 전에 이 에이전트만 따로 실행해 봅니다. 스크립트가 주문 에이전트에게 할 일을 주고, 에이전트는 Claude에 무엇을 할지 묻습니다. 주문 에이전트가 `lookup_order`를 호출했고, 출력 줄은 대괄호 안의 에이전트 이름으로 시작합니다. 이어서 한 문장 보고가 나옵니다. 45일 전에 배송된 램프입니다. 첫 번째 에이전트가 혼자 잘 동작하니 테스트 줄은 지웁니다.

## 결제 에이전트

결제 에이전트의 데이터는 주문별 결제 내역을 담은 두 번째 딕셔너리 `CHARGES`입니다. 램프 주문에는 첫날 결제된 60달러 결제가 두 건 있습니다. 이것이 중복 결제입니다.

- `list_charges`는 주문의 결제 내역을 돌려주고, 없으면 빈 목록을 돌려줍니다.
- `refund_charge`는 주문 ID와 금액을 받습니다. 실제로는 환불하지 않고, 환불한 내용을 돌려주기만 합니다. 실제 스토어라면 여기서 결제 시스템을 호출합니다.

두 함수를 각자 이름으로 매핑에 추가해서, Claude가 요청하면 루프가 찾을 수 있게 합니다.

결제 에이전트의 도구는 같은 헬퍼로 만든 두 개입니다. `list_charges`는 주문 ID를 받고, `refund_charge`는 주문 ID와 숫자인 금액을 받습니다. 주문 에이전트는 아무것도 환불할 수 없다는 점에 주목하세요. 그 도구가 아예 없기 때문입니다.

결제 에이전트는 더 많은 것을 받습니다. 주문 ID와, 알아야 할 사실들입니다.

| 항목 | 내용 |
| --- | --- |
| 이름 | `billing` |
| 시스템 프롬프트 | 결제 문제를 해결한다. 중복 결제만 환불하고, 한 일을 한 문장으로 보고한다. |
| 도구 | 결제 도구 |
| 할 일 | 먼저 사실을 적고, 이 주문의 결제 내역을 확인해 중복이 있으면 바로잡으라고 요청한다. |

이 에이전트도 램프, 60달러라는 짧은 사실 두 가지를 주고 따로 실행해 봅니다. 결제 에이전트는 사실과 할 일을 받아 자기 루프를 시작합니다. 주문의 결제 내역을 조회하고, 그중 60달러 한 건을 환불합니다. 같은 결제 두 건을 찾아 한 건을 환불했다고 보고합니다.

서브에이전트가 다른 에이전트가 아는 것을 볼 수 있다고 생각하기 쉽습니다. 볼 수 없습니다. 서브에이전트는 받은 할 일 텍스트만 가지고 빈 상태로 시작합니다. 여기서 사실은 테스트 줄에서 왔습니다. 실제 흐름에서는 코디네이터가 넘겨줘야 합니다. 그러니 두 번째 테스트 줄도 지웁니다.

## 코디네이터: 에이전트를 도구처럼 부르기

마지막은 코디네이터입니다. 요령은 이렇습니다. **코디네이터에게 각 에이전트는 도구일 뿐입니다.** Claude가 결제 에이전트라는 도구를 요청하면 루프가 결제 에이전트 함수를 실행하고, 그 함수가 에이전트 하나를 통째로 실행합니다. 그 보고가 도구 결과로 코디네이터에게 돌아옵니다. 그래서 먼저 두 에이전트 함수를 다른 도구 함수처럼 매핑에 추가합니다.

| 코디네이터의 도구 | 설명 | 입력 |
| --- | --- | --- |
| 주문 에이전트 | 주문을 확인한다. | 주문 ID |
| 결제 에이전트 | 주문의 결제 내역을 확인해 바로잡는다. 이미 알고 있는 주문 사실을 함께 넘긴다. | 주문 ID, 텍스트로 된 사실 |

결제 에이전트 설명의 마지막 문장이 코디네이터에게 아는 것을 넘기라고 알려 줍니다.

> **시험 참고**: 여기서는 위임 기능을 평범한 도구로 직접 만들었습니다. Claude Agent SDK에는 이런 도구가 내장되어 있습니다. 시험 가이드는 이 도구를 Task라고 부르고, 현재 릴리스에서는 Agent라고 부릅니다. 시험에서는 가이드의 이름을 쓰세요.

코디네이터 자체도 같은 `run_agent` 함수입니다.

| 항목 | 내용 |
| --- | --- |
| 이름 | `coordinator` |
| 시스템 프롬프트 | 데이터 도구가 없으므로 두 에이전트에게 위임하고, 각자에게 필요한 것을 넘기고, 고객에게 두 문장으로 답한다. |
| 도구 | 두 에이전트 |
| 할 일 | 고객의 메시지: 이 주문 금액이 두 번 결제됐어요. 고쳐 주세요. |

답은 앞에 `ShopAssist`라는 이름을 붙여 출력합니다.

## 시스템 전체 실행하기

여러 에이전트가 출력하므로 터미널을 넉넉하게 키우고 실행합니다.

1. 코디네이터가 고객 메시지로 시작합니다. 데이터 도구가 없으니 위임만 할 수 있습니다.
2. 첫 줄은 주문 에이전트에서 나옵니다. 주문을 조회했습니다. 그다음에야 코디네이터의 줄이 나옵니다. 주문 에이전트를 호출했다는 줄입니다.
3. 결제 에이전트가 결제 내역을 조회하고, 60달러 한 건을 환불합니다.
4. 그다음 코디네이터가 결제 에이전트를 호출한 줄이 나옵니다. 넘긴 사실을 보세요. 램프와 배송 후 45일입니다. 결제 에이전트는 코디네이터가 호출에 적어 줬기 때문에 이 사실을 알았습니다.
5. 마지막으로 ShopAssist가 같은 결제 두 건을 찾아 중복된 한 건을 환불했다고 고객에게 답합니다.

**왜 이런 순서로 출력될까요?** 루프는 도구가 실행된 뒤에 한 줄을 출력하는데, 여기서는 그 도구가 에이전트 하나 전체입니다. 그래서 주문 에이전트의 작업 줄이 먼저 나오고, 그 에이전트가 끝난 뒤에 코디네이터의 호출 줄이 나옵니다.

정리하면 이렇습니다. 코디네이터가 주문 에이전트에게 위임했고, 주문 에이전트는 주문을 조회해 45일 전에 배송된 램프라고 보고했습니다. 코디네이터는 그 사실을 결제 에이전트에게 넘겼고, 결제 에이전트는 같은 결제 두 건을 찾아 한 건을 환불하고 보고했습니다. 코디네이터는 두 보고를 바탕으로 고객에게 답했습니다.

## 정리

- 서브에이전트마다 좁은 일과 그 일에 필요한 도구만 줍니다.
- 서브에이전트에게 필요한 컨텍스트는 할 일에 담아 넘깁니다.
- 고객 응대는 코디네이터가 맡습니다.
