# 93. CI 사례: 파이프라인과 컨텍스트

지난 강의들에서 팀의 리뷰 봇은 CI로 옮겨 갔습니다. 이제 Claude Code는 ShopAssist의 모든 풀 리퀘스트를 리뷰하고 테스트를 제안합니다.

다음으로 넘어가기 전에, 시험이 파이프라인에서 Claude Code를 실행하는 문제를 어떻게 묻는지 살펴봅니다. 이번 점검은 두 가지 결정을 다룹니다. 첫째는 작업이 어떻게 실행되는가이고, 둘째는 실행마다 어떤 컨텍스트를 받는가입니다. 시험의 CI 시나리오가 바로 우리 봇의 이야기이기 때문에 중요합니다. 시험의 오답은 증상만 다루고 원인은 그대로 두는 경우가 많습니다.

## 첫 번째 결정: 작업이 어떻게 실행되나

첫 번째 증상입니다. 새 파이프라인 작업이 풀 리퀘스트마다 리뷰 프롬프트로 Claude Code를 시작합니다. 이 작업이 모든 풀 리퀘스트에서 파이프라인이 강제 종료할 때까지 1시간 동안 실행된다고 해 봅시다. 가끔 팀원이 같은 명령을 직접 실행하면, 게시 스크립트는 산문 한 문단을 받습니다. 스크립트는 거기서 파일이나 줄을 찾지 못하므로 코멘트를 하나도 게시하지 않습니다.

**무엇이 필요할까요?** 작업은 매번 스스로 끝나야 합니다. 스크립트도 모든 결과를 읽을 수 있어야 합니다. 그러니 더 나은 단어 선택이 아니라, 작업이 실행되는 방식에서 나오는 보장이 필요합니다.

**그럴듯한 오답**은 두 가지입니다.

1. **셸 타임아웃**으로 10분 뒤에 Claude Code를 멈춥니다. 이 방법은 실패합니다. 이제 작업이 끝나기는 하지만, 리뷰가 하나도 없는 실패로 끝납니다. Claude Code는 입력을 기다리고 있었고, 타임아웃은 그 기다림을 짧게 만들 뿐입니다.
2. **프롬프트에 "JSON으로 답해"를 추가합니다.** 이것도 실패합니다. Claude는 지침을 대부분 따르지만 매번 따르지는 않습니다. 산문 답변 하나가 스크립트를 깨뜨립니다.

```bash
# Fix 2: ask for JSON in the prompt
claude "Review this pull request. Answer in JSON."
# Most runs: JSON
# One run: a prose paragraph
#   the script cannot parse it
```

어느 해결책도 작업이 실행되는 방식을 바꾸지 못합니다. 기다림이 짧아질 뿐이고, JSON은 요청이지 보장이 아닙니다.

**가장 좋은 선택**은 print 플래그인 `-p`입니다. 프롬프트를 실행하고, 결과를 쓰고, 종료합니다. 여기에 플래그 두 개를 더합니다. `--output-format json`과 `--json-schema`입니다. 스키마는 지적 사항(finding)의 목록을 기술합니다. 지적 사항마다 파일, 줄, 심각도, 메시지, 수정 제안이 있습니다.

```json
{ "type": "object", "properties": { "findings": {
  "type": "array", "items": { "type": "object",
    "properties": {
      "file": { "type": "string" },
      "line": { "type": "integer" },
      "severity": { "type": "string" },
      "message": { "type": "string" },
      "fix": { "type": "string" } } } } } }
```

이제 모든 결과가 파싱됩니다. 스크립트는 그 줄이 diff에 포함되는지 확인한 뒤, 각 지적 사항을 해당 코드 줄에 코멘트로 게시합니다.

### 두 번째 수: 재실행

이 결정에는 두 번째 수가 있습니다. 이제 작업은 끝나지만, 개발자가 새 커밋을 push하면 리뷰가 같은 코멘트를 다시 게시합니다. 첫 실행이 이슈 4개를 찾았고, 개발자가 그중 3개를 고쳤다고 해 봅시다. 두 번째 실행은 4개를 모두 다시 게시합니다.

**그럴듯한 오답**은 프롬프트에 "이전 코멘트를 반복하지 마"를 추가하는 것입니다. 실행마다 새 세션이므로 실패합니다. 이전에 무슨 말을 했는지 볼 수 없습니다.

**가장 좋은 선택**은 이전에 한 말을 실행에 주는 것입니다. 스크립트는 실행마다 지적 사항을 JSON으로 저장합니다. 다음 실행에서는 그것을 새 diff와 함께 프롬프트에 넣습니다. 지침은 새로 생겼거나 아직 고쳐지지 않은 이슈만 보고하라고 말합니다. 이제 두 번째 실행은 열린 이슈 1개를 보고하고, 고친 이슈 3개는 조용히 지나갑니다.

> **규칙**: `-p`는 작업을 끝내고, 스키마는 프로그램이 읽을 수 있는 출력을 주고, 이전 지적 사항은 재실행이 같은 말을 반복하지 않게 합니다.

### 작업 실행 방식에 대해 하나 더

Message Batches API는 비용이 절반이지만 최대 24시간이 걸릴 수 있고, 지연 시간 보장이 없습니다. 그래서 팀의 주간 코드 감사에만 맞습니다. 개발자가 기다리는, 머지를 막는 리뷰에는 절대 맞지 않습니다.

| 작업 | 배치가 맞나 |
| --- | --- |
| 주간 코드 감사 | 맞음. 비용이 절반이고, 아무도 기다리지 않음 |
| 머지를 막는 리뷰 | 절대 아님. 개발자가 기다리는데 배치는 최대 24시간이 걸릴 수 있음 |

## 두 번째 결정: 실행마다 어떤 컨텍스트를 받나

같은 작업이 변경마다 테스트도 제안합니다. 제안의 절반쯤은 이미 테스트 스위트에 있다고 해 봅시다. 나머지 중 일부는 틀린 테스트 프레임워크를 쓰거나, 실제 결제 서비스를 호출합니다.

**무엇이 필요할까요?** 여기서는 아무도 보장을 요구하지 않습니다. 첫 단계가 필요하고, 그 단계는 컨텍스트에 속합니다.

**그럴듯한 오답**은 "기존 테스트를 확인하고, 절대 중복을 제안하지 마"라고 말하는 더 긴 프롬프트입니다. 이 방법은 실패합니다. Claude는 받은 적 없는 테스트 파일을 확인할 수 없습니다. 이 지침은 실행이 볼 수 없는 것을 요구합니다. 실행은 diff만 봅니다.

**가장 좋은 선택**은 두 부분으로 이루어집니다.

1. **스크립트가 변경된 코드의 기존 테스트 파일을 Claude에게 줍니다.** 프롬프트는 빠진 시나리오만 제안하라고 말합니다.
2. **프로젝트 CLAUDE.md에 테스트 표준을 둡니다.** 프레임워크, 가짜 결제 서비스 같은 픽스처, 그리고 무엇이 가치 있는 테스트인지가 여기에 들어갑니다. ShopAssist에서 가치 있는 테스트는 500달러 한도나 30일 기간을 다룹니다. 그냥 반환되기만 하는 필드를 다루는 테스트가 아닙니다. CI 머신에는 개발자의 홈 폴더가 없으므로, 커밋된 파일만 실행에 도달합니다.

> **규칙**: 중복 테스트를 막으려면 실행에 기존 테스트를 보여 주고, 팀의 표준은 리포지토리에 두세요.

## 정리

| 요점 | 내용 |
| --- | --- |
| `-p` 사용 | 없으면 Claude Code가 사람을 기다리고 CI 작업이 멈춤 |
| JSON 스키마 | `--output-format json`과 `--json-schema`로, 스크립트가 줄마다 게시할 수 있는 지적 사항을 받음 |
| 이전 지적 사항 | 재실행은 새로 생겼거나 아직 고쳐지지 않은 이슈만 보고 |
| 기존 테스트 | 테스트 생성에 기존 테스트 파일을 주고, CLAUDE.md가 표준과 픽스처를 담음 |
| 배치 | 아무도 기다리지 않는 작업에만 |

같은 규칙은 시험의 리서치 시나리오에도 적용됩니다. 서브에이전트는 CI 실행처럼 기록 없이 시작합니다. 그래서 코디네이터는 완전한 조사 결과를 구조화된 형태로 프롬프트에 넣어 넘깁니다.

Claude가 사람 없이 실행될 때는 실행이 스스로 끝나게 하고, 프로그램이 읽을 수 있는 출력을 요청하세요. 그리고 스스로 볼 수 없는 것은 모두 컨텍스트로 주세요.
