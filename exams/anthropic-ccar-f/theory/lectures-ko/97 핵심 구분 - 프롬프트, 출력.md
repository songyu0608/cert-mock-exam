# 97. 핵심 구분: 프롬프트, 출력

지난 두 노트에서는 ShopAssist와 팀의 Claude Code 설정을 시험의 눈으로 돌아봤습니다.

이번에는 시험의 네 번째 도메인인 프롬프트와 출력을 같은 방식으로 봅니다. 시험이 오답 선택지로 바꾸는 프롬프트, 출력, 리뷰의 구분을 다룹니다. 이 도메인은 시험의 5분의 1이기 때문에 중요합니다. 게다가 이 도메인의 오답 선택지는 신중하고 합리적으로 들립니다.

> 가장 중요한 점: 오답 선택지는 강도, 크기, 어조를 바꿉니다. 정답 선택지는 이름 붙인 범주, 예시, 스키마, 새 리뷰어 같은 구조를 더합니다.

세 그룹을 차례로 봅니다. 첫째, 프롬프트. 둘째, 출력. 셋째, 리뷰.

## 첫 번째 그룹: 프롬프트

### 첫 번째 쌍: 명시적 기준 대 모호한 신중함

개발자들이 더 이상 읽지 않던 팀의 리뷰 봇을 떠올려 보세요. "보수적으로 해"와 "확신이 높은 지적 사항만 보고해"는 오답입니다. 이런 지침을 받으면 Claude는 한계가 어디인지 추측해야 합니다. 또 노이즈에 대해서도 매우 확신할 수 있습니다.

정답은 버그와 보안 문제처럼 보고할 것을 이름으로 대는 것입니다. 사소한 스타일과 국소적인 패턴처럼 건너뛸 것도 이름으로 댑니다. 심각도 수준마다 정의와 코드 예시를 붙입니다. 노이즈가 많은 범주는 잠시 끄고 고칩니다.

```python
REVIEW_PROMPT = """
Report: bugs, security problems.
Skip: minor style, local patterns.
Severity (definition + example each):
- critical: query built from user input
- minor: unused import
"""
DISABLED = ["naming"]  # noisy, fix first
```

### 두 번째 쌍: 퓨샷 예시 대 더 큰 목소리

자세한 지침을 줘도 실행마다 결과가 다를 때가 있습니다. 대문자나 "you MUST"는 Claude가 이미 가끔만 따르는 규칙을 되풀이할 뿐입니다. 더 큰 모델도 도움이 되지 않습니다.

정답은 표적을 정한 예시 2~4개입니다.

- **완전한 예시** 하나가 형식을 고정합니다.
- **애매한 경우**의 예시는 다른 합리적인 선택지에 맞서는 추론을 보여 줍니다.
- **대조 쌍**은 괜찮은 코드를, 그것과 닮은 실제 문제 옆에 둡니다.

```text
<example name=complete>
  Finding: SQL built from user input
  Severity: critical, fix: parameterised query
</example>
<example name=unclear-case>
  Looks like a bug, but the retry is intended:
  not reported, the other choice is valid.
</example>
<example name=contrast>
  OK: local helper tmp | Problem: unchecked input
```

추출에서는 예시가 서로 다른 레이아웃을 다룹니다. 그러면 값이 비어서 오거나 지어낸 값으로 오는 일이 멈춥니다.

## 두 번째 그룹: 출력

### 첫 번째 쌍: 스키마 대 부탁

"유효한 JSON만 돌려줘"는 대부분 통하지만 매번 통하지는 않습니다. 시험에서 정답은 JSON 스키마를 쓰는 도구 사용입니다. 현재 코드에서는 strict tool use나 structured outputs를 씁니다.

```python
# a schema: the shape is enforced
tools = [{
    "name": "record_invoice",
    "strict": True,
    "input_schema": INVOICE_SCHEMA,
}]
```

모든 문서가 도구 호출을 만들어야 할 수도 있습니다. 이때 시험의 정답은 `tool_choice` any이거나, 먼저 실행돼야 하는 단계에 도구를 강제하는 것입니다. 현재 Opus, Sonnet, Fable 모델은 둘 다 오류로 거부합니다. 그래서 내 코드에서는 auto에 strict 도구를 쓰고 그 도구를 이름으로 부르는 지침을 더하거나, structured outputs를 씁니다.

```python
# Current code: auto + strict tool + named in the instruction
tool_choice={"type": "auto"},
tools=[{"name": "record_invoice", "strict": True, ...}],
system="Call record_invoice for every document."
```

> 제품 참고: 시험의 정답은 any 또는 강제 도구이고, 현재 모델에서는 auto, strict 도구, 지침 조합을 씁니다. (강의 슬라이드 기준)

스키마는 형태를 보장할 뿐 의미는 보장하지 않습니다. 그래서 계산한 합계와 문서에 적힌 총액은 여전히 내 코드가 비교합니다.

### 두 번째 쌍: nullable 필드 대 필수 필드

원본에 값이 없을 수 있다면, 필수 필드는 지어낸 값을 부릅니다. 그런 필드는 nullable로 만듭니다. 원본이 모호한 곳에는 "unclear"를 더하거나, 세부 필드와 함께 "other"를 더합니다.

```python
INVOICE_SCHEMA = {
    "total": {"type": "number"},
    "po_number": {"type": ["string", "null"]},
    "category": {"enum": ["hardware", "software",
                            "unclear", "other"]},
    "category_detail": {"type": ["string", "null"]},
}
```

### 세 번째 쌍: 표적 재시도 대 "다시 해 봐"

좋은 재시도는 원본 문서, 실패한 출력, 정확한 검증 오류를 함께 보냅니다. 재시도는 형식과 구조를 고칩니다. 하지만 원본에 없는 정보를 찾아낼 수는 없습니다. 값이 아무도 보내지 않은 문서에 있다면, 멈추고 그 문서를 요청합니다.

### 네 번째 쌍: 배치 대 바로 응답하는 일반 호출

Message Batches API는 비용이 절반입니다. 하지만 최대 24시간이 걸릴 수 있고, 지연 시간 보장이 없습니다. 야간 감사와 주간 보고서에 맞습니다. 개발자가 기다리는, 머지를 막는 검사에는 절대 맞지 않습니다. 그리고 배치 요청 안에서는 아무것도 도구를 실행하지 않습니다.

## 세 번째 그룹: 리뷰

### 첫 번째 쌍: 독립된 리뷰어 대 자기 리뷰

코드를 작성한 세션은 자기 추론을 그대로 갖고 있어서, 자기 선택을 거의 의심하지 않습니다. 비판적으로 보라고 말해도 달라지지 않습니다. 같은 인스턴스가 더 많이 생각해도 달라지지 않습니다. 시험은 이것을 extended thinking이라고 부릅니다. 정답은 새 컨텍스트를 가진 두 번째 인스턴스입니다.

### 두 번째 쌍: 나눈 패스 대 큰 패스 하나

큰 변경을 한 패스로 리뷰하면 얕은 코멘트가 나오고, 코멘트끼리 충돌하기도 합니다. 주의가 너무 얇게 퍼지기 때문입니다.

그럴듯하지만 실패하는 해결책이 여럿 있습니다.

- 더 큰 모델이나 더 큰 컨텍스트 창은 공간을 더할 뿐 주의를 더하지 않습니다.
- 풀 리퀘스트를 작게 나누도록 강제하면 일이 개발자에게 넘어갈 뿐입니다.
- 세 번 실행 중 두 번 일치한 지적 사항만 남기면 실제 버그가 빠집니다.

정답은 파일마다 패스 하나, 그다음 파일들을 가로지르는 통합 패스입니다. 검증 패스가 지적 사항마다 신뢰도 점수를 붙일 수 있습니다. 그 점수는 덜 확실한 지적 사항을 먼저 사람에게 보내며, 절대 버리지 않습니다.

## 정리

| 구분 | 정답 |
| --- | --- |
| 기준 | 신중함을 요구하지 말고, 보고할 것과 건너뛸 것을 이름으로 댐 |
| 예시 | 더 큰 목소리가 아니라 예시 2~4개 |
| 스키마 | 형태를 보장하고, 의미는 내 코드가 검사 |
| nullable과 재시도 | 없을 수 있는 값은 nullable, 재시도는 정확한 오류와 함께 |
| 배치 | 아무도 기다리지 않을 때만 |
| 리뷰 | 큰 변경에는 새 리뷰어와 나눈 패스 |

그러니 어떤 선택지가 프롬프트를 더 크게, 모델을 더 크게, 어조를 더 신중하게 만들기만 한다면 아마 오답입니다. 구조를 더하는 선택지를 고르세요.
