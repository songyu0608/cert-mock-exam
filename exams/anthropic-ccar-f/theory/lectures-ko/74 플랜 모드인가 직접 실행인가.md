# 74. 플랜 모드인가 직접 실행인가

이제 팀은 ShopAssist용 Claude Code 설정을 마쳤습니다. CLAUDE.md 파일, 규칙, 스킬, 공유 MCP 서버가 모두 들어 있습니다.

이번 노트에서는 Claude Code가 실제 작업을 어떻게 시작해야 하는지 살펴봅니다. 먼저 계획할지, 바로 변경할지입니다. 어느 쪽이든 잘못 고르면 시간을 낭비합니다. 한 줄 수정에 계획을 세우면 몇 분을 낭비하고, 계획 없이 광범위한 변경을 시작하면 며칠을 낭비할 수 있습니다.

## 같은 날 아침에 들어온 두 작업

**작업 1: 버그 보고.** 반품을 문의한 일부 고객에게 오류가 보입니다. 보고에는 **스택 트레이스**가 들어 있습니다. 스택 트레이스는 오류에 이르기까지 호출된 함수의 목록입니다. 트레이스는 한 파일의 한 함수를 가리킵니다. 30일 반품 기간을 계산하는 코드입니다. 주문에 아직 배송일이 없으면 이 함수에서 크래시가 납니다.

**작업 2: 라이브러리 마이그레이션.** ShopAssist는 날짜와 시간에 오래된 라이브러리를 씁니다. 이제 아무도 이 라이브러리를 관리하지 않으므로, 팀은 새 라이브러리로 바꾸려 합니다. 간단히 검색해 보니 오래된 라이브러리가 약 50개 파일에 쓰이고 있습니다.

가장 중요한 원칙은 **어떤 모드가 필요한지는 보통 시작하기 전에 작업이 알려 준다**는 것입니다.

| 작업 | 모드 |
| --- | --- |
| 범위가 넓거나, 가능한 방법이 여럿 | 먼저 계획 |
| 명확하고 작은 변경 | 바로 실행 |

이번 노트에서는 플랜 모드가 하는 일, 모드를 고르는 방법, 두 모드를 함께 쓰는 방법을 차례로 봅니다.

## 1. 플랜 모드

플랜 모드에서 Claude Code는 코드를 읽고 검색하지만, 파일은 하나도 바꾸지 않습니다. 탐색한 뒤 계획을 씁니다. 계획에는 어떤 파일을, 어떤 순서로 바꿀지, 무엇이 잘못될 수 있는지가 들어갑니다. 계획을 읽고 질문하거나 바꿀 수 있습니다. Claude Code는 **승인한 뒤에야** 수정을 시작합니다.

1. 나 → Claude Code: 플랜 모드로 작업을 맡김
2. Claude Code → 코드베이스: 읽고 검색함. 파일은 바뀌지 않음
3. Claude Code → 나: 계획(파일, 순서, 위험)
4. 나 → Claude Code: 질문 또는 변경, 그리고 승인

> 모드 전환은 Shift+Tab으로 합니다(강의 슬라이드 기준).

왜 도움이 될까요? 계획의 실수는 고치기 쌉니다.

| 고칠 것 | 드는 노력 |
| --- | --- |
| 잘못된 계획 | 몇 문장 |
| 파일 30개의 잘못된 수정 | 훨씬 오래 걸림 |

그래서 플랜 모드에서는 Claude Code가 안전하게 탐색하고, 무엇이든 바꾸기 전에 방식을 설계합니다. 비용이 큰 재작업을 막아 줍니다.

## 2. 모드를 고르는 방법

플랜 모드는 복잡한 작업을 위해 만들어졌습니다. 플랜 모드를 가리키는 신호는 네 가지입니다.

- 변경이 큽니다.
- 많은 파일을 건드립니다.
- 아키텍처 결정이 필요합니다.
- 타당한 방법이 여럿입니다.

예는 이렇습니다.

- 우리의 라이브러리 마이그레이션
- 큰 애플리케이션 하나를 작고 독립된 서비스 여러 개로 나누기
- 인프라가 서로 다른 두 연결 방식 중 고르기

마지막 예를 보겠습니다. 배송 파트너가 배송 추적 업데이트를 가지고 있습니다.

| 방식 | 필요한 것 |
| --- | --- |
| 푸시: 파트너가 업데이트를 생길 때마다 보냄 | 우리 쪽의 새 웹 주소, 업데이트를 보관할 큐 |
| 폴링: 우리 코드가 매시간 파트너 시스템에 물어봄 | 주기적으로 조회하는 코드 |

Claude Code는 코드를 쓰기 전에 두 방식을 모두 탐색해야 합니다.

**직접 실행**은 간단하고 범위가 분명한 변경에 씁니다. 스택 트레이스가 분명한 한 파일 버그 수정이 한 예이고, 한 함수에 검증 하나를 더하는 것이 또 다른 예입니다. 예를 들어 배송일이 미래가 아닌지 확인하는 것입니다. 오늘 아침의 버그가 여기에 맞습니다. 파일, 함수, 원인을 모두 압니다. 계획을 세워 봐야 스택 트레이스가 이미 말하는 내용을 되풀이할 뿐입니다.

```python
def check_delivery_date(delivery_date, today):
    if delivery_date is None:
        return None
    if delivery_date > today:
        raise ValueError("Delivery date is in the future")
    return delivery_date
```

### 잘못 시작하는 세 가지 방식

| 방식 | 문제 |
| --- | --- |
| 마이그레이션을 바로 시작하고 코드가 맞는 방식을 보여 주길 기대 | 코드 부분 사이의 숨은 연결이 늦게 드러나고, 반쯤 된 수정을 되돌려야 합니다. |
| 바로 시작했다가 "어려워지면" 플랜 모드로 전환 | 작업이 이미 어렵다고 말하고 있습니다. 파일 50개입니다. |
| 직접 실행 모드에서 길고 자세한 지침 | 코드를 탐색하지 않고 맞는 구조를 이미 안다고 가정합니다. |

**복잡하다는 것이 처음부터 분명하면, 바로 계획합니다.**

## 3. 두 모드를 함께

두 모드는 경쟁 관계가 아닙니다. 마이그레이션은 플랜 모드로 시작합니다.

1. Claude Code가 오래된 라이브러리를 쓰는 곳을 모두 찾고, 종류별로 묶습니다.
2. 순서를 제안합니다. 공유 날짜 헬퍼, 그다음 환불 서비스, 그다음 테스트입니다.
3. 우리가 계획을 승인합니다.
4. 직접 실행으로 전환하고, Claude Code가 승인된 계획을 단계별로 수행합니다.

계획은 조사를 맡고, 직접 실행은 작업을 맡습니다.

## 정리

- 플랜 모드는 많은 파일에 걸친 큰 변경, 아키텍처 결정, 타당한 방법이 여럿인 작업에 씁니다.
- 플랜 모드에서 Claude Code는 아무것도 수정하지 않고 탐색하고 제안하므로, 재작업이 작게 유지됩니다.
- 직접 실행은 스택 트레이스가 분명한 한 파일 버그 수정 같은, 명확하고 범위가 정해진 변경에 씁니다.
- 작업이 이미 복잡하다고 말하면, 문제가 생기길 기다리지 말고 지금 계획합니다.
- 좋은 워크플로는 조사를 계획하고, 승인된 계획을 직접 실행합니다.

모드를 고르기 전에 작업을 읽으세요. 넓거나 열려 있으면 먼저 계획하고, 작고 명확하면 바로 변경하세요. 다음 노트에서는 Claude Code가 코드를 찾고 바꿀 때 쓰는 내장 도구를 살펴보겠습니다.
