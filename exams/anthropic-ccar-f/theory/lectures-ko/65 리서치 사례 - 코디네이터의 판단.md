# 65. 리서치 사례: 코디네이터의 판단

이번 점검에서는 리서치 시스템이 영역을 놓치거나, 출처를 잃거나, 맡은 일에서 벗어날 때 리서치 코디네이터가 내려야 할 결정을 살펴봅니다. 시험의 리서치 시나리오는 각 실패가 어디서 시작되는지 묻습니다. 그 답은 코디네이터인 경우가 아주 많습니다.

이번에는 시험에 나오는 리서치 시스템을 그대로 씁니다. 이 시스템은 소프트웨어 팀을 위해 일합니다. 기술 주제에 관한 보고서를 쓰고, 보고서마다 출처를 밝힙니다.

## 첫 번째 결정: 모든 서브에이전트가 성공했는데 영역이 빠졌다

팀이 **오픈소스 패키지의 보안 위험**에 관한 보고서를 요청합니다. 분명하고 출처도 잘 붙은 보고서가 돌아옵니다. 모든 서브에이전트가 성공을 보고했습니다. 웹 검색은 기사를 찾았고, 문서 분석은 논문을 정확히 읽었고, 종합은 조사 결과를 합쳤고, 보고서 생성은 보고서를 썼습니다.

그런데 보고서는 한 영역만 다룹니다.

| 영역 | 보고서에서 |
| --- | --- |
| 취약점(패키지의 알려진 보안 버그) | 유일하게 다뤄짐 |
| 방치된 패키지(아무도 관리하지 않음) | 언급 없음 |
| 라이선스 위험 | 언급 없음 |
| 가짜 패키지(인기 패키지 이름을 베낌) | 놓침 |

**무엇이 필요할까요?** 여기서는 아무도 보장을 요구하지 않습니다. 원인을 바로잡는 첫 단계가 필요합니다.

**그럴듯한 오답**은 서브에이전트마다 결과 개수 한도를 올리는 것입니다. 웹 검색이 결과를 10개가 아니라 50개 돌려주게 합니다. 이 방법은 실패합니다. 코디네이터의 로그에는 세 하위 작업이 있습니다. JavaScript 패키지의 취약점, Python 패키지의 취약점, 패키지 취약점을 검사하는 도구입니다. 이 세 작업 안에서 결과를 늘려 봐야 취약점 기사만 더 늘어납니다. 서브에이전트는 요청받은 일을 정확히 했습니다. 문제는 무엇을 요청받았는가입니다.

**가장 좋은 선택**은 두 부분으로 이루어집니다.

1. **코디네이터의 분해를 고칩니다.** 무엇이든 위임하기 전에 주제의 주요 영역을 나열하고, 영역마다 담당자를 정확히 하나씩 둡니다.
2. **빠진 부분을 확인합니다.** 종합이 끝나면 코디네이터가 결론을 영역 목록과 비교합니다. 빠진 영역마다 검색과 문서 분석에 표적 질의를 보내고, 모든 영역에 출처가 붙은 조사 결과가 생길 때까지 종합을 다시 실행합니다.

여기에도 두 가지 동작 원리가 그대로 적용됩니다. 웹 검색과 문서 분석은 서로에게 의존하지 않으므로, 코디네이터는 한 응답에 Task 호출 두 개를 넣어 병렬로 실행합니다. 그리고 종합은 코디네이터의 기록을 보지 못하므로, 두 서브에이전트의 조사 결과를 전부 종합 프롬프트에 직접 넣습니다.

> **규칙**: 모든 서브에이전트가 성공했는데 영역 전체가 빠졌다면, 코디네이터의 분해를 고칩니다.

## 두 번째 결정: 핵심 출처를 열 수 없다

핵심 출처 하나가 PDF로 저장된 패키지 유지 관리에 관한 업계 설문 조사입니다. 그런데 파일이 손상되어 문서 분석 서브에이전트가 열 수 없습니다.

**무엇이 필요할까요?** 실행은 계속되어야 하고, 코디네이터는 다음에 무엇을 할지 고를 수 있을 만큼 정보를 받아야 합니다.

**그럴듯한 오답**은 오류를 잡아 빈 결과를 돌려주고 실행을 이어 가는 것입니다. 실패가 성공으로 숨겨지므로 틀린 답입니다. 코디네이터는 “이 설문 조사에는 조사 결과가 없음”으로 읽습니다. 그러면 종합은 빠진 데이터를 사실로 취급하고, 보고서는 아무도 읽지 않은 문서로 결론을 내립니다.

**가장 좋은 선택**은 국소 복구부터 시작합니다. 다운로드가 중간에 끊겼을 수 있으므로 서브에이전트가 파일을 한 번 더 불러옵니다. 그래도 실패한다고 가정해 보겠습니다. 이제 서브에이전트는 네 부분으로 된 구조화된 실패 컨텍스트를 돌려줍니다.

| 항목 | 내용 |
| --- | --- |
| 실패 유형 | 파일 손상, 1회 재시도 후에도 실패 |
| 시도한 것 | 설문 조사와, 거기에 던진 질문 |
| 일부 결과 | 오류 전까지 12쪽을 읽었다고 가정 |
| 대안 | 발행처의 웹 버전, 또는 작년 판 |

이 정보로 코디네이터가 결정합니다. 웹 검색에 웹 버전을 찾게 할 수도 있고, 일부 결과로 계속 진행할 수도 있습니다. 그러면 종합은 설문 조사를 읽을 수 없었으므로 그 영역을 빠진 부분으로 표시합니다.

> **규칙**: 실패한 곳에서 고칠 수 있는 것은 고치고, 나머지는 빈 결과가 아니라 빠짐없이 보고합니다.

## 세 번째 결정: 종합 서브에이전트가 직접 검색한다

팀은 시스템을 설정할 때 혹시 몰라 종합 서브에이전트에게 웹 검색 도구 전체를 줬습니다. 이제 종합은 직접 검색을 합니다. 계획에 없던 일반적인 소프트웨어 품질 기사를 끌어오고, 새로 찾은 결과 중 일부에는 날짜도 출처도 없습니다.

**무엇이 필요할까요?** 에이전트가 다른 에이전트의 일을 하고 있으므로, 첫 단계는 설정에서 해야 합니다.

**그럴듯한 오답**은 도구는 그대로 두고, 프롬프트에 꼭 필요할 때만 검색하라고 적는 것입니다. 이 방법은 실패합니다. 도구가 여전히 목록에 있으므로 역할 밖의 일을 계속 부추깁니다. 프롬프트 문구는 대부분의 경우 Claude를 이끌지만, 매번 그렇지는 않습니다.

**가장 좋은 선택**은 서브에이전트마다 역할에 맞게 도구를 제한하는 것입니다. 종합에게는 검색 도구를 주지 않습니다. 그런데 로그를 보니 종합이 한 검색의 대부분이 출시일이나 다운로드 수 같은 단순한 확인이었다고 가정해 보겠습니다. 이렇게 자주 나오는 단순한 필요를 위해 종합에게 범위를 좁힌 도구 `verify_fact` 하나를 줍니다. 이 도구는 주장 하나를 출처 하나와 대조합니다. 복잡한 검증은 여전히 코디네이터를 거쳐 웹 검색으로 보냅니다.

> **규칙**: 각 에이전트에게는 역할에 필요한 도구와, 자주 나오는 단순한 확인을 위한 좁은 도구 하나를 줍니다.

## 정리

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 서브에이전트는 성공했는데 영역이 빠짐 | 너무 좁은 분해 | 분해를 고치고, 빠진 부분을 확인하는 루프를 돈다 |
| 읽을 수 없는 출처 | 일시적이거나 복구할 수 없는 실패 | 국소 재시도 뒤 네 부분 실패 보고. 코디네이터가 정하고, 종합은 빠진 부분으로 표시 |
| 맡은 일에서 벗어나는 에이전트 | 역할 밖의 도구 | 그 도구를 빼고, 단순한 확인용 좁은 도구 하나를 추가 |

같은 원칙은 고객 지원 시나리오에도 적용됩니다. ShopAssist가 세 가지 요청 중 하나에만 답한다면 도구가 문제가 아닙니다. 메시지를 처음부터 항목별로 나누지 않은 것이 문제입니다.

시스템이 일을 빠뜨리거나 엉뚱한 일을 한다면, 먼저 일을 어떻게 나눴는지와 각 에이전트에게 무엇을 줬는지부터 고치세요.
