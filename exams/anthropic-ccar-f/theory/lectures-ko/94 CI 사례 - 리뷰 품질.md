# 94. CI 사례: 리뷰 품질

지난 점검에서 팀의 CI 작업은 세 가지를 익혔습니다. 스스로 끝나고, 지적 사항을 JSON으로 돌려주고, 자기가 이전에 한 말을 기억합니다.

이번 마지막 점검은 리뷰 자체의 품질을 다룹니다. 두 가지 결정을 살펴봅니다. 첫째, 개발자들이 봇의 코멘트를 기각할 때 무엇을 할까. 둘째, 큰 변경이 얕은 리뷰를 받을 때 무엇을 할까. 리뷰 봇은 개발자가 신뢰하고, 봇이 모든 파일을 꼼꼼히 읽을 때만 도움이 되기 때문에 중요합니다.

## 첫 번째 결정: 개발자들이 코멘트를 기각한다

첫 번째 증상입니다. 로그를 보니 2주 동안 개발자들이 봇의 코멘트 약 60개를 기각했다고 해 봅시다. 지적 사항마다 파일, 줄, 심각도, 범주, 메시지가 있습니다. 하지만 범주가 "error handling"처럼 넓습니다. 그래서 어떤 종류의 코멘트가 노이즈인지 아무도 알 수 없습니다. 팀이 아는 것은 신뢰가 다시 떨어지고 있다는 것뿐입니다.

```json
{
  "file": "refund.py",
  "line": 42,
  "severity": "medium",
  "category": "error handling",
  "message": "Default hides a missing value"
}
```

**무엇이 필요할까요?** 여기서는 아무도 보장을 요구하지 않습니다. 첫 단계가 필요하고, 그 단계는 원인을 찾는 것입니다.

**그럴듯한 오답**은 두 가지입니다.

1. **프롬프트에 "확신이 높은 지적 사항만 보고해"를 추가합니다.** 이 방법은 실패합니다. Claude는 아무도 원하지 않는 코멘트에 대해서도 매우 확신할 수 있습니다.
2. **개발자에게 코멘트를 기각할 때마다 이유를 쓰게 합니다.** 이것도 실패합니다. 자유 텍스트 이유는 세기 어렵고, 많은 사람이 건너뜁니다. 게다가 이미 봇에 지쳐 가는 바로 그 사람들에게 일을 더합니다.

**가장 좋은 선택**은 지적 사항마다 `detected_pattern`이라는 필드를 하나 더하는 것입니다. 이 필드는 지적 사항을 촉발한 코드 구조를 밝힙니다. 예를 들어 "기본값으로 읽는 선택적 필드(an optional field read with a default value)"나 "고객 메시지에서 가져온 금액(an amount taken from the customer's message)"입니다. 스키마가 이 필드를 필수로 만들기 때문에 모든 지적 사항이 이 필드를 가집니다.

```json
{
  "file": "refund.py",
  "line": 42,
  "severity": "medium",
  "category": "error handling",
  "detected_pattern": "amount taken from the customer's message",
  "message": "Default hides a missing value"
}
```

스크립트는 개발자들이 어떤 코멘트를 기각하는지 이미 알고 있습니다. 이제 그 기각을 패턴별로 셉니다. 기각 60개 중 40개가 "기본값으로 읽는 선택적 필드"라는 한 패턴을 공유한다고 해 봅시다. 팀은 그 패턴에 대해 명확한 건너뛰기 규칙을 쓰고, 대조 쌍(contrasting pair)을 하나 추가합니다. 새 규칙을 테스트할 때까지 봇은 그 패턴만 멈춥니다. 다른 error handling 지적 사항은 모두 계속 실행됩니다.

> **규칙**: 모든 지적 사항이 자기 패턴을 밝히게 하면, 기각이 셀 수 있는 데이터가 됩니다.

## 두 번째 결정: 큰 변경이 얕은 리뷰를 받는다

ShopAssist에 새 환불 옵션으로 store credit이 생깁니다. Claude Code가 변경을 작성하고, 이 변경은 파일 31개를 건드립니다. 그런 다음 같은 세션이 자기 작업을 리뷰합니다. 리뷰는 처음 몇 파일은 자세히 보고, 나머지 파일에는 한 줄씩만 씁니다.

리뷰가 두 파일 사이에 있는 버그를 놓친다고 해 봅시다. 환불 서비스는 이제 store credit에 새 상태를 줍니다. 그런데 케이스 정보(case facts) 코드는 여전히 옛 상태만 완료된 환불로 취급합니다. 그래서 고객의 store credit이 계속 대기 중으로 표시됩니다.

| 위치 | 무엇이 일어나나 |
| --- | --- |
| 환불 서비스 | 새 상태 `store_credit`을 씀 |
| 케이스 정보 코드 | 옛 상태만 완료로 셈 |
| 고객 화면 | 크레딧이 대기 중으로 표시됨 |

**무엇이 필요할까요?** 이번에도 첫 단계가 필요하고, 이번에는 리뷰를 어떻게 구성하느냐의 문제입니다.

**그럴듯한 오답**은 두 가지입니다.

1. **같은 세션에게 다른 사람이 쓴 것처럼 비판적으로 리뷰하라고 말합니다.** 이 방법은 실패합니다. 세션은 작성할 때의 추론을 그대로 갖고 있습니다. 그래서 코드를 자기 의도에 비춰 확인합니다.
2. **같은 세션에서 더 많이 생각하게 합니다.** 시험에서는 이것을 extended thinking이라고 부릅니다. 이것도 실패합니다. 더 많이 생각해도 같은 추론에서 출발하기 때문입니다.

> 제품 참고: 시험은 extended thinking이라고 부르지만, 지금은 effort 설정이 있는 adaptive thinking입니다. (강의 슬라이드 기준)

**가장 좋은 선택**은 세 부분으로 이루어집니다.

1. **독립된 인스턴스가 리뷰합니다.** 새 세션으로 시작하는 새 Claude Code 실행입니다. 작성자의 세션을 resume하거나 포크하지 않습니다.
2. **리뷰를 패스로 나눕니다.** 파일마다 패스 하나가 국소적인 이슈를 찾고, 모든 파일에서 같은 깊이로 봅니다. 이어서 통합 패스가 파일 사이로 데이터를 따라갑니다. 이 패스가 케이스 정보 코드가 모르는 새 상태를 찾아냅니다.
3. **검증 패스가 지적 사항마다 확인하고 신뢰도 점수를 붙입니다.** 팀은 과거 점수를 개발자가 확인하거나 기각한 지적 사항과 비교해 임계값을 정했습니다. 신뢰도가 높은 지적 사항은 코멘트로 게시합니다. 의심스러운 지적 사항은 먼저 사람에게 가고, 버리는 것은 하나도 없습니다.

> **규칙**: 큰 변경에는 새 리뷰어, 파일마다 한 패스, 파일 사이에 한 패스가 필요합니다. 신뢰도는 지적 사항이 어디로 갈지를 정할 뿐, 지적 사항을 지우지 않습니다.

이 두 가지 변화로 팀의 리뷰 봇도 달라집니다. 처음 몇 주 동안 개발자들은 봇을 무시했습니다. 이제 다시 읽습니다.

## 정리

| 요점 | 내용 |
| --- | --- |
| 기각 세기 | `detected_pattern` 필드를 추가하고 기각을 패턴별로 셈 |
| 패턴만 멈추기 | 봇 전체가 아니라 노이즈가 많은 패턴을 고치거나 멈춤 |
| 새 리뷰어 | 코드를 쓴 세션은 리뷰하지 않음. "비판적으로"라고 말해도 달라지지 않음 |
| 두 종류의 패스 | 큰 리뷰를 파일별 패스와 통합 패스로 나눔 |
| 신뢰도로 라우팅 | 검증 패스가 의심스러운 지적 사항을 사람에게 보내고, 버리는 것은 없음 |

같은 규칙은 추출 시나리오에도 적용됩니다. 거기서는 전체 정확도 수치 하나가 약한 문서 유형이나 필드를 가릴 수 있습니다. 그래서 팀은 부분마다 따로 측정하고, 캘리브레이션된 신뢰도로 사람이 리뷰할 곳을 정합니다.

Claude의 출력에 대한 신뢰가 떨어질 때마다, 그 출력을 측정할 수 있는 부분으로 나누고 실패하는 부분을 고치세요.
