# 83. 단계, 서브에이전트, 매니페스트

지난 노트에서는 스크래치패드 파일과 compact 커맨드로 긴 탐색 하나를 또렷하게 유지했습니다.

이번 노트에서는 컨텍스트 하나에 담기에 너무 크고, 실행 한 번에 끝내기에 너무 긴 작업을 살펴봅니다. 이런 작업은 서브에이전트와 단계에 나눠 맡깁니다. 그리고 조사 결과가 단계가 바뀌어도, 크래시가 나도 살아남게 합니다. 큰 변경은 며칠이 걸릴 수 있습니다. **하루치 조사 결과를 잃으면 그 하루의 비용을 두 번 치릅니다.**

## 세 단계로 환불 코드를 떼어 낸다

팀은 환불 처리를 ShopAssist 본 코드에서 꺼내 별도 서비스로 옮기려 합니다. 이 변경은 파일 수백 개를 건드립니다. 작업은 세 단계입니다.

| 단계 | 하는 일 |
| --- | --- |
| 탐색 | 환불 코드를 지도로 그립니다. |
| 설계 | 새 서비스가 어디서 시작하고 어디서 끝나는지 정합니다. |
| 이전 | 코드를 한 부분씩 옮깁니다. |

메인 에이전트 하나가 작업 전체를 운영하고, 이것을 **코디네이터**라고 부릅니다. 코디네이터는 메인 Claude Code 세션일 수도 있고, Agent SDK로 만든 개발자 도구의 메인 에이전트일 수도 있습니다. 코디네이터는 세부 작업을 위해 서브에이전트를 시작합니다.

가장 중요한 원칙은 **코디네이터는 큰 그림을 쥐고, 살아남아야 할 조사 결과는 모두 대화 밖에 적어 둔다**는 것입니다.

| 습관 | 내용 |
| --- | --- |
| 초점 있는 질문 | 서브에이전트마다 질문 하나 |
| 단계 요약 | 한 단계를 다음 단계로 넘겨줌 |
| 저장된 상태 | 크래시 복구용 매니페스트 |

## 1. 초점 있는 질문

큰 그림을 잃는 방법은 두 가지입니다.

- **코디네이터가 환불 파일을 모두 직접 읽는다.** 한 시간이 지나면 컨텍스트가 검색 출력으로 가득 차고, 큰 그림을 잃습니다.
- **서브에이전트 하나에 "환불 코드를 이해해 줘" 같은 모호한 작업을 보낸다.** 그 서브에이전트는 길고 일반론적인 보고서를 들고 옵니다.

대신 코디네이터는 서브에이전트마다 구체적인 질문 하나를 합니다.

| 서브에이전트 | 질문 |
| --- | --- |
| 테스트 서브에이전트 | 환불을 다루는 테스트 파일을 모두 찾아라. |
| 의존성 서브에이전트 | 환불 흐름의 의존성을 추적하라. 환불 코드가 호출하는 모듈과, 환불 코드를 호출하는 모듈이다. |

각 서브에이전트는 자기 컨텍스트에서 파일 수십 개를 읽습니다. 그리고 이름, 파일, 사실을 담은 짧고 구조화된 답을 돌려줍니다. 원본 출력은 코디네이터에게 닿지 않습니다. 코디네이터는 어떤 부분이 있고, 어떻게 연결되고, 다음에 무엇이 오는지라는 상위 수준의 그림만 유지합니다. 앞에서 본 Explore 서브에이전트도 같은 생각을 따릅니다.

## 2. 단계 요약

탐색이 끝나고 설계가 시작됩니다. 설계 서브에이전트는 새로 시작합니다. 기억하겠지만, **서브에이전트는 자기 프롬프트만 압니다.** 그래서 설계 서브에이전트를 시작하기 전에 코디네이터가 탐색의 핵심 조사 결과를 요약합니다.

```text
Context from discovery:
modules: refund_service, refund_rules, payouts
depends_on: orders, payments, notifications
tests: refund test files, listed by name
risks: the $500 limit is checked in two places,
       and only one of them has a test
open_questions: who sends the refund emails?
Task: decide where the new service begins and ends.
```

요약에는 환불 모듈과 그 의존성, 테스트 파일, 위험, 미해결 질문이 들어갑니다. 예를 들어 500달러 한도가 두 곳에서 확인되는데, 그중 한 곳에만 테스트가 있습니다.

모든 설계 서브에이전트는 이 요약을 초기 컨텍스트, 즉 프롬프트 첫머리에 받습니다. 그래서 0이 아니라 조사 결과에서 출발합니다. 대신 탐색 기록 전체를 넘기면 안 됩니다. 길고 노이즈가 많아서, 중요한 사실이 중간에 묻힙니다.

## 3. 크래시

이전 작업 둘째 날, 실행이 멈춥니다. 컴퓨터가 재시작됐을 수도 있고, 세션이 끝났을 수도 있습니다. 다섯 부분 중 세 부분은 이미 옮겼습니다.

| 부분 | 상태 |
| --- | --- |
| 1, 2, 3 | 옮김 |
| 4 | 중단됨 |
| 5 | 시작 안 함 |

저장된 상태가 없으면 작업이 처음부터 다시 시작합니다. 더 나쁘게는, 이미 파일을 바꾼 단계를 반복할 수도 있습니다.

### 에이전트마다 상태 파일

그래서 각 에이전트는 자기 상태를 **정해진 위치**로 내보냅니다. 프로젝트 안의 고정된 폴더이고, 에이전트마다 파일이 하나씩 있습니다. 파일에는 에이전트의 작업, 상태, 조사 결과, 바꾼 파일, 다음 단계가 들어갑니다. 에이전트는 끝날 때만이 아니라 **단계마다** 이 파일을 갱신합니다.

```yaml
# one state file per agent, in a fixed folder
task: move the payout code
status: in progress
findings: payouts call the refund rules
files_changed: payout.py, payout_rules.py, payout_api.py
next_step: update the payout imports
```

### 매니페스트

코디네이터는 **매니페스트**도 유지합니다. 매니페스트는 모든 에이전트와 그 상태 파일의 경로, 상태를 나열하는 짧은 파일 하나입니다. 상태는 done(완료), in progress(진행 중), not started(시작 안 함) 중 하나입니다.

```text
# the manifest: one short file for the whole job
# agent   state file          status
part-1    state/part-1.yaml   done
part-2    state/part-2.yaml   done
part-3    state/part-3.yaml   done
part-4    state/part-4.yaml   in progress
part-5    state/part-5.yaml   not started
# status: done, in progress or not started
```

### 크래시 뒤에 이어 가기

1. 작업이 다시 시작되면 코디네이터가 먼저 매니페스트를 불러옵니다.
2. 완료된 부분은 완료로 유지합니다.
3. 중단된 부분은 그 에이전트의 상태 파일을 읽습니다.
4. 그 내용을 새 서브에이전트의 프롬프트에 주입합니다. 무엇을 했는지, 어떤 파일이 바뀌었는지, 다음 단계가 무엇인지입니다.
5. 작업이 마지막으로 기록된 단계부터 이어집니다.

옛 대화에서 작업을 다시 구성하려 하면 안 됩니다. 크래시로 대화가 끊길 수 있고, 긴 기록은 코디네이터가 추측하게 만듭니다. 디스크의 상태 파일은 무엇이 끝났는지 정확히 말해 줍니다.

## 정리

- 코디네이터는 상위 수준의 그림을 쥐고, 서브에이전트에게 구체적인 질문을 보냅니다.
- 각 서브에이전트는 노이즈가 많은 읽기를 자기 컨텍스트에서 하고, 짧은 조사 결과를 돌려줍니다.
- 단계가 끝나면 코디네이터가 핵심 조사 결과를 요약합니다. 그 요약은 다음 단계 모든 서브에이전트의 첫 프롬프트에 들어갑니다.
- 각 에이전트는 단계마다 정해진 위치에 상태를 저장합니다.
- 다시 시작할 때 코디네이터는 매니페스트를 불러오고, 다시 시작하는 에이전트에 저장된 상태를 주입합니다.

여러 단계와 여러 날에 걸친 작업에서는 조사 결과를 대화에만 두지 말고 디스크에 두세요.

다음 노트에서는 넘어가기 전에, 시험이 팀의 Claude Code 설정을 어떻게 묻는지 봅니다.
