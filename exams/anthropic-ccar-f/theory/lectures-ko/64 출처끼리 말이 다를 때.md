# 64. 출처끼리 말이 다를 때

이제 스토어 리서치 보고서의 모든 주장은 출처를 유지합니다. 이번 노트에서는 좋은 출처 두 개가 서로 다른 숫자를 내놓을 때 무슨 일이 일어나는지 살펴봅니다. 보고서가 조용히 숫자 하나를 고르면 팀을 잘못된 방향으로 보낼 수 있습니다. 두 번째 숫자가 있었다는 사실조차 아무도 모르게 됩니다.

## 같은 모델, 같은 기간, 다른 숫자

리서치 어시스턴트는 여전히 **램프는 왜 그렇게 자주 반품될까?**에 답하고 있습니다. 스토어 내부 파일을 읽는 문서 분석 서브에이전트가 같은 램프 모델, 같은 기간(작년)에 대해 두 숫자를 찾습니다.

- 공급업체 품질 보고서: 램프 100개 중 2개에 결함이 있었다.
- 스토어 지원 티켓: 램프 100개 중 6개가 결함으로 반품됐다.

둘 다 믿을 만한 출처입니다. 하지만 둘 다 전체 진실일 수는 없습니다.

가장 중요한 원칙은 **값 하나를 임의로 고르지 않는다**는 것입니다. 두 값을 모두 각자의 출처와 함께 남기고, 둘이 어떻게 맞물리는지는 코디네이터가 정하게 합니다. 이번 노트에서는 문서 분석이 충돌을 보고하는 법, 날짜로 진짜 충돌과 추세를 구분하는 법, 최종 보고서가 확정된 것과 논란이 있는 것을 보여 주는 법을 차례로 봅니다.

## 1. 분석: 충돌을 그대로 보고하기

문서 분석이 숫자 하나를 그냥 고를 수도 있습니다. 더 최근 보고서, 더 큰 숫자, 더 공식적으로 들리는 숫자를 택하는 식입니다. 둘을 평균 내서 100개 중 4개라고 보고할 수도 있습니다. 둘 다 하면 안 됩니다. 하나를 고르면 다른 출처가 가려집니다. 평균은 어떤 출처도 보고한 적 없는 숫자입니다. 어느 쪽이든 누군가 살펴보기도 전에 충돌이 사라집니다.

그래서 문서 분석은 두 값을 모두 담아 작업을 마치고, 충돌을 명시적으로 표시합니다. 레코드에는 충돌 표시, 두 값, 그리고 값마다 출처, 기간, 방법이 들어갑니다.

```json
{
  "claim": "lamp defect rate, last year",
  "conflict": true,
  "values": [
    { "value": "2 in 100", "source": "supplier report",
      "period": "last year", "method": "factory test" },
    { "value": "6 in 100", "source": "support tickets",
      "period": "last year", "method": "customer returns" }
  ]
}
```

이 레코드는 종합으로 바로 가지 않고 **코디네이터**에게 갑니다. 종합이 보기 전에 두 값을 어떻게 맞출지 코디네이터가 정합니다.

여기서는 방법이 많은 것을 설명해 줍니다. 공급업체는 공장 테스트에서 불합격한 램프를 셉니다. 티켓은 고객이 고장 났다며 반품한 램프를 세는데, 배송 중에 헐거워진 배선도 여기에 들어갑니다. 즉 두 숫자는 서로 다른 것을 잽니다. 코디네이터는 “반품된 램프 중 실제로 검사한 것은 몇 개인가?” 같은 표적 질의를 하나 보낼 수 있습니다. 그다음 두 값이 어떻게 관련되는지 메모를 붙여 종합에 넘깁니다. 코디네이터가 차이를 설명할 수 있더라도, 두 값은 각자의 출처와 함께 보고서에 나란히 남습니다.

## 2. 날짜: 충돌인가, 추세인가

이번에는 다른 두 숫자입니다. 2년 전 공급업체 보고서는 램프 100개 중 8개에 결함이 있었다고 말합니다. 같은 공급업체의 작년 보고서는 100개 중 2개라고 말합니다. 날짜가 없으면 두 숫자는 서로 다른 말을 하는 것처럼 보이고, 종합은 이를 논란으로 표시할 수 있습니다. 그런데 공급업체는 지난봄 새 공장으로 옮겼습니다. 두 숫자는 다투는 것이 아니라 **추세**를 보여 줍니다. 불량률이 떨어진 것입니다.

종합이 이것을 알아보려면 모든 조사 결과에 날짜가 있어야 합니다. 앞에서 서브에이전트의 레코드에 날짜 필드를 넣은 이유가 바로 이것입니다. 그래서 서브에이전트의 프롬프트와 출력 스키마는 모든 조사 결과에 날짜를 요구합니다. 발행일뿐 아니라 **수집일**도 요청하세요. 올해 발행된 보고서가 작년에 수집한 데이터를 다룰 수 있기 때문입니다.

```text
{
  "properties": {
    "value": { "type": "string" },
    "source": { ... },
    "published": { ... },
    "collected": { ... }
  },
  "required": ["value", "source", "published", "collected"]
}
```

두 날짜가 없으면 서로 다른 해의 숫자가 두 출처의 의견 불일치처럼 보입니다.

## 3. 보고서: 확정된 결과와 논란이 있는 결과를 나누기

최종 보고서에는 두 섹션을 따로 둡니다.

| 섹션 | 내용 | 예 |
| --- | --- | --- |
| 충분히 확인된 결과 | 서로 독립적인 여러 출처가 일치하는 것 | 헐거운 배선이 반품의 주요 원인이다. 지원 티켓과 공급업체 보고서가 모두 이를 가리킨다. |
| 논란이 있는 결과 | 출처끼리 다른 것 | 작년 불량률. 두 값과 두 출처를 함께 둔다. |

논란이 있는 결과 섹션에서는 각 출처가 자기 표현과 자기 방법을 유지합니다. 공급업체가 자기 불량률을 “정상 범위 이내”라고 부른다고 해 보세요. 보고서는 그 표현을 그대로 인용합니다. “낮다”로 바꾸지도 않고, “하지만 티켓이 반대를 증명한다”를 덧붙이지도 않습니다. 각 숫자를 어떻게 만들었는지도 밝힙니다. 완제품 램프의 공장 테스트인지, 고객 반품 집계인지입니다. 이런 맥락이 있으면 팀이 숫자를 직접 판단할 수 있습니다. 보고서가 대신 판단하지 않습니다.

## 정리

- 믿을 만한 두 출처가 다를 때 값 하나를 고르지도, 평균을 내지도 않습니다.
- 문서 분석은 두 값을 모두 담고, 충돌을 표시하고, 값마다 출처, 기간, 방법을 붙입니다.
- 종합에 앞서 두 값을 어떻게 맞출지 코디네이터가 정합니다.
- 모든 조사 결과에 발행일이나 수집일이 있어야, 시간에 따른 변화를 의견 불일치가 아니라 추세로 읽을 수 있습니다.
- 보고서는 충분히 확인된 결과와 논란이 있는 결과를 별도 섹션에 두고, 각 출처는 자기 표현과 방법을 유지합니다.

출처끼리 말이 다르면 그 차이를 드러내고 맥락을 함께 남기세요. 다음 노트에서는 시험이 우리가 만든 것과 같은 리서치 시스템을 어떻게 묻는지 살펴보겠습니다.
