# 60. 에이전트 사이에 컨텍스트 전달하기

이제 스토어 리서치 어시스턴트의 서브에이전트는 각자 역할에 필요한 도구만 갖고 있습니다. 이번 노트에서는 서브에이전트가 시작할 때 무엇을 전달받는지 살펴봅니다. 서브에이전트는 자기 프롬프트 말고는 아무것도 모릅니다. 프롬프트에 빠진 사실은 쓸 수 없습니다.

## 숫자도 출처도 날짜도 없는 답

리서치 어시스턴트는 **램프는 왜 그렇게 자주 반품될까?**에 답하려고 합니다. 코디네이터는 이미 웹 검색과 문서 분석을 시작했고, 두 결과가 모두 돌아왔습니다. 이제 코디네이터가 Task 호출로 종합 서브에이전트를 시작합니다. 프롬프트는 이렇습니다.

> 램프 반품에 관한 조사 결과를 합쳐 몇 가지 분명한 결론으로 정리하라.

돌아온 답은 일반적인 말뿐입니다. 램프는 배송 중에 자주 파손된다. 일부 고객은 품질 문제를 보고한다. 숫자도, 출처도, 날짜도 없습니다. 램프에 관한 아무 기사나 똑같이 말할 수 있는 내용입니다.

가장 중요한 원칙은 **서브에이전트는 빈 상태로 시작한다**는 것입니다. 코디네이터가 프롬프트에 써 준 것만 압니다. 이번 노트에서는 서브에이전트가 빈 상태로 시작하는 이유, 코디네이터가 전달해야 하는 것, 그 컨텍스트의 형식과 크기를 차례로 봅니다.

## 1. 서브에이전트는 빈 상태로 시작한다

코디네이터 뒤에는 긴 대화가 있습니다. 그 대화에는 팀의 질문, 코디네이터의 계획, 앞선 두 서브에이전트의 결과가 담겨 있습니다. 종합 서브에이전트는 그중 아무것도 보지 못합니다. 서브에이전트는 **격리된 자기 컨텍스트**에서 실행되므로 코디네이터의 대화 기록을 물려받지 않습니다. 서브에이전트끼리 실행 사이에 메모리를 공유하지도 않습니다.

코디네이터가 빠진 부분을 찾아 종합을 두 번째로 실행한다고 해 보세요. 두 번째 실행은 첫 번째 실행을 기억하지 못합니다. 그래서 “조사 결과를 합쳐라”는 서브에이전트가 받은 적 없는 조사 결과를 가리킵니다. 합칠 것이 없으니 그럴듯한 내용을 씁니다.

서브에이전트가 코디네이터가 본 것을 볼 수 있다고 가정하면 안 됩니다. 그 가정이 바로 이런 답을 만듭니다. **서브에이전트에게는 프롬프트가 세계의 전부입니다.**

## 2. 무엇을 전달할까

웹 검색과 문서 분석의 조사 결과는 도구 결과로 코디네이터에게 돌아옵니다. 코디네이터는 그 결과를 종합 프롬프트에 **전부** 옮겨 넣어야 합니다. 두 서브에이전트의 모든 조사 결과를 넣어야 하고, “검색에서 배선 문제를 몇 가지 찾음” 같은 짧은 메모로는 부족합니다. 종합을 두 번째로 실행한다면 이전 결론과 새 조사 결과를 함께 넣습니다. 프롬프트에는 목표도 담습니다. 팀의 질문과, 좋은 답이 어떤 모습인지입니다.

슬라이드에 나온, 코디네이터가 종합 프롬프트를 만드는 한 가지 방법은 다음과 같습니다.

```python
prompt = f"""Web search findings (all of them):
{web_findings}

Document analysis findings (all of them):
{doc_findings}

Earlier conclusions (second run only):
{earlier_conclusions}

Goal: why are lamps returned so often?
A good answer: three conclusions, each with a source."""
```

## 3. 어떤 형식으로 전달할까

팀이 프롬프트를 바꿔서, 이제 코디네이터는 두 결과를 모두 프롬프트에 옮깁니다. 결론은 나아졌지만 새 문제가 생깁니다. 조사 결과가 문단 형태입니다. 한 문단에 주장, 인용, 보고서 이름, 연도가 섞여 있습니다. 종합 서브에이전트가 이 문단들을 결론으로 바꾸는 과정에서 이름과 연도가 빠집니다. 한 결론은 “특정 램프 모델이 다른 모델보다 두 배 자주 고장 난다”고 말합니다. 이 말이 어디서 나왔는지, 얼마나 오래된 정보인지 아무도 알 수 없습니다.

그래서 조사 결과 하나하나를 **구조화된 레코드**로 만듭니다. 내용과 메타데이터를 별도 필드에 둡니다.

```json
{
  "content": {"claim": "Model L-200 fails twice as often",
              "evidence": "8 returns per 100 sold, others 4"},
  "metadata": {
    "source": "returns-report.pdf, page 14",
    "date": "2026-03-01",
    "method": "count of 400 support tickets"
  }
}
```

| 구분 | 필드 | 내용 |
| --- | --- | --- |
| 내용 | 주장, 근거 | 주장과 짧은 근거입니다. |
| 메타데이터 | 출처 | 출처 URL이나 문서 이름, 그리고 쪽 번호입니다. |
| 메타데이터 | 날짜 | 보고서가 발행된 날짜나 데이터를 수집한 날짜입니다. |
| 메타데이터 | 방법 | 조사 결과를 어떻게 얻었는지입니다. 지원 티켓 400건을 집계한 결과는 포럼 글 하나보다 훨씬 무게가 있습니다. |

**왜 내용과 메타데이터를 나눌까요?** 종합 서브에이전트는 내용의 문구를 바꿉니다. 하지만 메타데이터는 자기 필드에 남아 각 주장에 붙어 있습니다. 종합 과정에서 잘려 나갈 수 있는 문장 안에 들어 있지 않습니다. 그래서 각 주장이 어디서 왔는지 항상 알 수 있습니다. 날짜가 있으면 두 보고서가 서로 다른 해에 나왔다는 것도 종합 서브에이전트가 알 수 있습니다. 출처끼리 서로 다른 말을 하는 경우는 뒤에서 따로 다룹니다.

이 형식은 상류, 즉 종합보다 먼저 실행되는 에이전트에서 시작해야 합니다. 코디네이터는 받은 메타데이터만 전달할 수 있습니다. 그래서 웹 검색과 문서 분석 서브에이전트를 바꿉니다. 프롬프트와 출력 스키마가 모든 조사 결과에 날짜, 출처 위치, 방법을 요구합니다. 이것이 빠진 조사 결과는 불완전한 것입니다.

```python
FINDING_SCHEMA = {
    "type": "object",
    "properties": {
        "claim": {"type": "string"},
        "evidence": {"type": "string"},
        "source": {"type": "string"},
        "date": {"type": "string"},
        "method": {"type": "string"},
    },
    "required": ["claim", "evidence", "source", "date", "method"],
}
```

## 컨텍스트는 크다고 완전해지지 않는다

같은 레코드가 크기 문제도 해결합니다. 첫 버전에서 웹 검색은 기사 전체를 돌려줬습니다. 자기 추론 과정도 함께 돌려줬습니다. “먼저 램프 불만을 검색했고, 그다음 포럼을 열었고…” 이렇게 해서 수천 단어가 됐습니다.

종합 서브에이전트는 모든 출처의 조사 결과를 한꺼번에 담아야 하므로 컨텍스트 예산이 제한되어 있다고 가정해 보세요. 긴 글과 단계별 추론은 그 예산을 노이즈로 채웁니다.

그래서 상류 에이전트가 구조화된 데이터를 돌려주도록 바꿉니다. 핵심 사실, 인용 출처, 그리고 조사 결과마다 **관련성 점수**를 돌려줍니다. 이제 종합 서브에이전트는 다른 에이전트가 어떻게 찾았는지가 아니라 사실에 예산을 씁니다. 안전하게 하려고 페이지 전체를 넘기면 안 됩니다. 글이 많다고 컨텍스트가 완전해지지 않습니다. 중요한 조사 결과가 들어갈 자리만 줄어듭니다.

## 정리

- 서브에이전트는 빈 컨텍스트로 시작합니다. 코디네이터의 기록을 물려받지 않고, 이전 실행도 기억하지 않습니다.
- 코디네이터는 앞선 에이전트의 조사 결과를 전부 서브에이전트의 프롬프트에 직접 넣습니다.
- 조사 결과는 구조화된 레코드로 만들고, 내용과 메타데이터(출처, 쪽, 날짜, 방법)를 분리합니다.
- 상류 에이전트는 긴 글과 추론이 아니라 핵심 사실, 인용 출처, 관련성 점수를 돌려줍니다.

서브에이전트 프롬프트는 읽는 쪽이 아무것도 모른다고 생각하고 쓰세요. 실제로 아무것도 모르기 때문입니다. 다음 노트에서는 코디네이터와 서브에이전트 둘을 코드로 만들고, 각자가 정확히 무엇을 받는지 확인하겠습니다.
