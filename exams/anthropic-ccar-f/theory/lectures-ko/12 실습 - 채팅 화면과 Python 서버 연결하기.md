# 12. 실습: 채팅 화면과 Python 서버 연결하기

지금까지 ShopAssist는 Python 스크립트 안에서 대화를 주고받았고, 대화 기록은 목록에 담았습니다. 스토어 고객은 이 스크립트를 실행하는 대신 웹사이트의 채팅창에 메시지를 입력합니다. 이번에는 그 메시지가 Claude에 도달하고, 답이 다시 채팅창에 나타나도록 연결해 보겠습니다.

등장하는 곳은 세 군데입니다. **브라우저**는 채팅 화면을 보여 줍니다. **우리 서버**는 브라우저의 요청을 기다리는 작은 Python 프로그램입니다. 이 서버가 시스템 지침과 대화 기록을 준비해 **Claude API**를 호출하고, 받은 답을 다시 브라우저로 보냅니다.

## 서버와 요청 형식 준비하기

새 파일 `app.py`를 엽니다. 앞에서 쓰던 `load_dotenv`와 `Anthropic`에 더해 세 가지를 가져옵니다. **FastAPI**는 Python으로 웹 서버를 만드는 라이브러리입니다. **StaticFiles**는 미리 만들어 둔 채팅 페이지 같은 파일을 브라우저에 보내 줍니다. Pydantic의 **BaseModel**은 요청에 어떤 데이터가 들어와야 하는지 정의할 때 씁니다.

전과 같이 `load_dotenv()`를 호출해 키를 읽고 클라이언트를 만듭니다. 이어서 `app = FastAPI()`로 웹 애플리케이션을 만듭니다. 모델 이름과 시스템 지침은 `conversation.py`에 쓴 것을 그대로 가져옵니다.

마지막으로 빈 목록 `history`를 만듭니다. 서버 안에 있으므로 브라우저에서 보낸 첫 번째 요청이 끝나도 다음 요청에서 같은 기록을 사용할 수 있습니다. **이 실습에서는 페이지를 연 모든 사용자가 목록 하나를 공유합니다.** 혼자 시험할 때 쓰는 구성입니다. 실제 스토어라면 한 고객의 대화가 다른 고객의 요청에 섞이지 않도록 고객별로 기록을 관리해야 합니다.

브라우저가 보낼 데이터의 모양도 정해 봅시다. `BaseModel`을 상속한 `ChatIn`에 문자열 필드 `text` 하나를 선언합니다. 고객이 입력한 메시지가 이 필드에 들어갑니다.

## POST /chat에서 답을 돌려주기

엔드포인트는 브라우저가 요청을 보낼 수 있는 주소입니다. `@app.post("/chat")` 아래에 `chat` 함수를 정의하면 `/chat`으로 POST 요청이 올 때 이 함수가 실행됩니다. 매개변수 `body`에는 브라우저가 JSON으로 보낸 데이터가 들어옵니다. FastAPI가 먼저 `ChatIn` 형식에 맞는지 확인하므로 함수 안에서는 `body.text`로 고객의 말을 꺼낼 수 있습니다.

이제 지난 노트에서 작성한 코드를 떠올려 보세요. 고객의 텍스트에 `user` 역할을 붙여 기록에 추가합니다. 모델, `max_tokens`, `effort`, 시스템 지침은 `conversation.py`에서 사용한 대로 두고, `messages`에는 이번 메시지까지 담긴 **전체 기록**을 넘깁니다. 응답이 오면 전과 같은 반복문으로 텍스트 블록에서 답을 꺼내고, 이 답도 `assistant` 역할로 기록에 추가합니다.

브라우저에 돌려줄 값은 두 가지입니다. **답변 텍스트**와 **Claude가 읽은 입력 토큰 수**를 Python 딕셔너리에 담아 반환합니다. FastAPI가 이를 브라우저에서 읽을 수 있는 JSON으로 변환합니다.

그다음 `static` 폴더의 파일을 제공하도록 설정합니다. 이 폴더에는 메시지 입력칸, 답변을 보여 줄 자리, 메시지의 이동 경로를 그린 작은 그림이 있는 HTML 페이지가 이미 준비되어 있습니다. `html=True`로 설정하면 기본 주소에서 `index.html`이 열립니다. 다른 주소를 정적 파일에 연결하는 이 설정은 **`/chat` 엔드포인트를 정의한 뒤 맨 마지막에** 둡니다. 그래야 `/chat` 요청이 앞에서 작성한 함수에 도달합니다.

## 채팅창과 터미널에서 같은 요청 확인하기

FastAPI 앱을 실행하는 프로그램은 Uvicorn입니다. `uvicorn app:app --port 8000`에서 콜론 앞의 `app`은 파일 `app.py`를, 뒤의 `app`은 그 안에 만든 웹 애플리케이션 변수를 가리킵니다. 실행하면 서버가 8000번 포트에서 브라우저 요청을 기다립니다.

편집기 안의 브라우저에서 채팅 페이지를 열어 보세요. 입력칸에 “20일 전에 재킷을 샀어요”라고 쓰면 브라우저가 우리 서버에 글을 보내고, 서버가 Claude를 호출합니다. 답은 같은 길을 거꾸로 돌아옵니다. 원문의 실행 예시에서 Claude는 반품 기한이 열흘 정도 남았다고 답했고, 채팅창에는 답 아래에 입력 토큰 수 **69**가 표시됐습니다. 터미널에는 **`POST /chat`** 요청 한 건과 성공 상태 코드 `200`이 찍힙니다.

이어서 “아직 반품할 수 있나요?”라고 물어보세요. 이 질문만 읽으면 무엇을 언제 샀는지 알 수 없습니다. 하지만 서버가 앞선 대화를 보관해 두었기에 재킷과 20일이라는 정보도 함께 전달됩니다. Claude는 반품할 수 있다고 답하고, 입력 토큰 수는 **약 150개**로 늘어납니다. 실행 장소가 웹으로 바뀌었을 뿐, 요청마다 전체 기록을 보낸다는 원리는 이전 실습과 같습니다.

왜 브라우저에서 곧바로 Claude를 호출하지 않을까요? 그렇게 하려면 누구나 읽을 수 있는 페이지에 API 키를 넣어야 합니다. 시스템 지침과 대화 기록까지 브라우저가 관리하면 고객 쪽에서 그 내용을 바꿀 수도 있습니다. 그래서 이 구조에서는 **브라우저가 우리 서버에 요청하고, Claude API 호출은 서버가 맡습니다.** 키와 규칙, 대화 기록을 우리가 관리하면서 고객에게는 필요한 답만 보여 줄 수 있습니다.
