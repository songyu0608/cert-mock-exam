# 96. 핵심 구분: Claude Code

지난 섹션들에서 ShopAssist 팀은 자기 작업을 위해 Claude Code를 설정했습니다. 그런 다음 Claude Code를 CI 파이프라인으로 옮겼습니다.

지난 노트에서는 제품을 시험의 눈으로 돌아봤습니다. 이번에는 팀의 도구를 같은 방식으로 봅니다. 시험이 오답 선택지로 바꾸는 Claude Code의 구분을 다룹니다. 이 오답 선택지는 실제 파일과 실제 플래그를 이름으로 대기 때문에 중요합니다. 문제는 그것을 엉뚱한 자리에 두거나 엉뚱한 작업에 쓴다는 점입니다.

> 가장 중요한 점: 두 가지를 물으세요. 설정이라면 누가 필요로 하고 언제 로드되는지 묻습니다. 작업이라면 그 작업이 자기 크기, 컨텍스트, 누가 지켜보는지에 대해 무엇을 말하는지 묻습니다.

두 그룹을 차례로 봅니다. 첫째, 구성. 둘째, 워크플로. 이 둘을 합치면 시험의 세 번째 도메인을 다룹니다.

## 첫 번째 그룹: 구성

### 첫 번째 쌍: 사용자 파일 대 프로젝트 파일

홈 폴더의 CLAUDE.md는 버전 관리로 공유되지 않기 때문에 나에게만 닿습니다. 리포지토리의 CLAUDE.md는 프로젝트를 클론하거나 pull하는 모든 사람에게 닿습니다. 그래서 새 팀원에게 팀 규칙이 빠져 있다면 먼저 사용자 수준을 봅니다.

`/memory` 커맨드로 세션이 어떤 파일을 로드했는지 확인합니다. 그런 다음 팀 규칙을 프로젝트 파일로 옮깁니다. 팀원에게 사본을 보내는 것은 오답입니다. 사본은 점점 서로 달라지기 때문입니다.

> 제품 참고: 현재 제품에서 `/memory`는 메모리 파일을 열고, `/context`는 무엇이 로드됐는지 보여 줍니다. (강의 슬라이드 기준)

### 두 번째 쌍: 경로 범위 규칙 대 디렉터리 파일

디렉터리 CLAUDE.md는 한 폴더에 속하므로, 그 폴더에만 있는 규칙에 맞습니다. rules 폴더에 있고 `paths` 필드가 붙은 규칙은 어느 폴더에 있든 일치하는 파일에 로드됩니다. 그래서 코드베이스 곳곳에 흩어진 테스트 파일의 규칙은 경로 범위 규칙에 둡니다. 예를 들어 `paths: **/*.test.ts`입니다.

여기서는 폴더마다 CLAUDE.md를 두는 것이 오답입니다. 루트 파일의 한 섹션이나 스킬도 오답입니다. 파일 하나가 너무 커지면 rules 폴더의 주제별 파일로 나눕니다. 그런 다음 패키지마다 필요한 표준만 가져오게(import) 합니다.

### 세 번째 쌍: 커맨드나 스킬 대 CLAUDE.md

CLAUDE.md는 항상 로드되므로 모든 작업에 필요한 표준을 담습니다. 커맨드나 스킬은 한 종류의 작업을 위해 필요할 때 실행됩니다. 팀 커맨드는 리포지토리의 commands 폴더에, 개인 커맨드는 홈 폴더에 둡니다. 커맨드 목록을 담는 설정 파일은 없습니다.

출력에 노이즈가 많은 스킬에는 `context: fork`를 주고, `argument-hint`는 필요한 입력을 요청합니다. 시험의 표현으로는 `allowed-tools`가 스킬을 제한합니다. 현재 제품은 이 키를 다르게 읽습니다. 개인용 변형은 다른 이름을 씁니다. 그리고 스킬에는 트리거 필드가 없습니다. Claude는 설명을 보고 스킬을 고릅니다.

```yaml
---
description: Summarise a noisy test run
context: fork
argument-hint: [suite name]
allowed-tools: Read, Bash(npm test *)
# no trigger key: Claude matches the description
---
Run the suite and report only failures.
Keep the output short.
```

> 제품 참고: 시험에서는 `allowed-tools`가 스킬을 제한한다고 봅니다. 현재 제품에서는 나열된 도구를 미리 승인합니다. (강의 슬라이드 기준)

## 두 번째 그룹: 워크플로

### 첫 번째 쌍: 플랜 모드 대 직접 실행

작업이 이미 말하는 것을 읽으세요. 파일이 많거나, 아키텍처 결정이 있거나, 유효한 접근법이 여러 개라면 먼저 플랜 모드입니다. 명확한 스택 트레이스가 있는 버그처럼 파일 하나의 분명한 변경이라면 직접 실행입니다.

작업이 이미 자기 크기를 말하는데 "일단 직접 시작하고 어려워지면 전환한다"는 오답입니다. 좋은 답은 두 모드를 함께 쓰는 경우가 많습니다. 먼저 계획하고, 승인된 계획을 직접 실행합니다. Explore 서브에이전트는 노이즈가 많은 탐색을 메인 컨텍스트 밖에 둡니다.

### 두 번째 쌍: resume, 포크, 새로 시작

| 선택 | 언제 |
| --- | --- |
| 이름 붙은 세션 resume | 이전 컨텍스트가 아직 대부분 유효할 때. 바뀐 파일을 알려 줌 |
| 포크 | 공유된 분석 하나에서 두 접근법을 비교할 때. 접근법마다 한 번씩 |
| 새로 시작 | 이전 도구 결과가 대부분 낡았을 때. 구조화된 요약을 가지고 시작 |

함정 하나를 조심하세요. 세션 포크는 기록을 유지하지만, 스킬의 `context: fork`는 기록 없이 시작합니다.

### 세 번째 쌍: CI 실행 대 사람이 키보드 앞에 있는 세션

CI에서는 아무도 지켜보지 않습니다. 그래서 Claude Code를 `-p`로 실행하고, `--output-format json`과 `--json-schema`로 스크립트가 게시할 수 있는 지적 사항을 받습니다. 셸 타임아웃, headless 환경 변수, batch 플래그, 빈 입력은 모두 오답입니다.

CI 실행에는 메모리도 없고, 파이프라인 머신에는 개발자의 홈 폴더도 없습니다. 그래서 프로젝트 CLAUDE.md가 표준을 담고, 프롬프트가 기존 테스트와 이전 지적 사항을 담습니다.

## 정리

- 팀 설정은 리포지토리에, 개인 설정은 홈 폴더에 둡니다.
- 여러 폴더에 흩어진 파일의 규칙은 경로 범위 규칙에 둡니다.
- CLAUDE.md는 항상 로드되고, 커맨드와 스킬은 필요할 때 실행됩니다.
- 작업이 밝힌 크기가 플랜 모드와 직접 실행 중 하나를 정합니다.
- resume, 포크, 새로 시작 중 무엇을 고를지는 이전 컨텍스트가 얼마나 아직 사실인지에 달려 있습니다.
- CI에서는 JSON 출력과 스키마를 붙여 `-p`로 실행합니다.

그러니 모든 Claude Code 선택지에 누가 필요로 하는지, 언제 로드되는지, 작업이 자기 자신에 대해 무엇을 말하는지 물으세요.

다음 노트에서는 프롬프트와 구조화된 출력을 같은 방식으로 돌아봅니다.
