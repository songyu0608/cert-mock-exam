# 85. Claude Code 사례: 계획하고 반복하기

지난 점검에서는 한 개발자에게만 동작하던 Claude Code 설정을 고쳤습니다.

이번 두 번째 점검은 결정 두 가지를 더 다룹니다.

| 결정 | 질문 |
| --- | --- |
| 작업 모드 고르기 | 먼저 계획할까, 바로 변경할까? |
| 반복되는 실수 고치기 | Claude Code가 계속 틀리는 변경을 어떻게 고칠까? |

시험의 코드 생성 시나리오는 두 질문을 모두 묻습니다. 어떤 오답은 빨라 보이고 어떤 오답은 신중해 보입니다. **둘 다 며칠을 잃게 할 수 있습니다.**

## 첫 번째 결정: 크기가 다른 두 작업

청구 모듈은 아무도 관리하지 않는 오래된 결제 라이브러리를 아직 부릅니다. 검색해 보니 그 라이브러리가 약 45개 파일에 있다고 가정합니다. 같은 날 아침, 버그 보고가 들어옵니다. 청구서에 할인 값이 없으면 청구 모듈이 크래시가 납니다. 스택 트레이스는 함수 하나의 한 줄을 가리킵니다.

**무엇이 필요할까요?** 여기서는 아무도 보장을 요구하지 않습니다. 작업마다 맞는 첫 단계가 필요합니다.

**그럴듯한 오답**은 두 가지입니다.

| 오답 | 실패하는 곳 |
| --- | --- |
| 안전하게 모두 계획하기 | 버그에서 실패합니다. 계획은 스택 트레이스가 이미 말하는 것을 되풀이할 뿐이고, 한 줄 수정이 괜히 기다립니다. |
| 둘 다 바로 시작하고, 이전이 어려워지면 그때 플랜 모드로 전환 | 이전에서 실패합니다. 파일 45개를 건드리므로 작업이 이미 어렵다고 말하고 있습니다. 숨은 연결이 늦게 드러나고, 반쯤 된 수정을 되돌려야 합니다. |

**가장 좋은 선택**은 작업마다 다른 모드를 쓰는 것입니다.

- **이전은 플랜 모드로** 보냅니다. 플랜 모드에서 Claude Code는 파일을 하나도 수정하지 않고 탐색하고 변경을 제안합니다. 파일 45개에 걸친 탐색은 노이즈가 많으므로, Explore 서브에이전트가 자기 컨텍스트에서 검색하고 요약만 돌려줍니다. 계획은 순서를 제안합니다. 공유 결제 코드, 그다음 청구 서비스, 그다음 테스트입니다. 우리가 승인하면, 계획된 단계는 직접 실행으로 전환해 진행합니다.
- **null 검사는 바로 직접 실행**합니다. 파일, 줄, 원인을 모두 알기 때문입니다.

**규칙**: 모드를 고르기 전에 작업을 읽습니다. 범위가 넓거나 타당한 방법이 여럿이면 먼저 계획합니다. 작고 명확하면 바로 변경합니다.

## 두 번째 결정: 대기 중인 환불이 지급된 것처럼 보인다

이전이 진행되면서 새 문제가 나타납니다. 오래된 라이브러리는 아직 정산되지 않은 환불에 null을 돌려줬습니다. 새 코드는 그 빈 날짜를 오늘 날짜로 채웁니다. 그래서 대기 중인 환불이 이제 지급된 것처럼 보입니다. 청구 레코드 약 50건 중 1건이 영향을 받는다고 가정합니다.

```python
def to_ledger(record):
    # the old library returned None while a refund is pending
    settled = record.settled_date or date.today()
    return {
        "status": record.status,
        "settled_date": settled,
    }
```

위 코드는 슬라이드의 예시용 버그입니다. 개발자는 "빠진 값을 올바르게 처리하라"고 두 번 설명했습니다. 매번 다른 경로가 틀린 채로 돌아옵니다.

**무엇이 필요할까요?** 이번에도 첫 단계가 필요하고, 이번에는 변경을 설명하는 방식에 있습니다.

**그럴듯한 오답**은 두 가지입니다.

| 오답 | 실패하는 이유 |
| --- | --- |
| 더 길고 자세한 설명 쓰기 | "올바르게"는 여전히 오늘 날짜, 기본 날짜, 레코드 건너뛰기 중 무엇이든 될 수 있습니다. 말이 늘어도 같은 빈틈이 남습니다. |
| "아직 틀렸어, 고쳐 줘"라고 답하기 | Claude Code는 어떤 사례가 실패했는지 볼 수 없어서, 이미 맞던 코드를 바꿀 수도 있습니다. |

**가장 좋은 선택**은 실패하는 구체적인 사례 하나로 시작합니다. 입력은 정산일이 null인 대기 중 환불 레코드입니다. 기대 출력은 같은 레코드로, 날짜는 여전히 null이고 상태도 여전히 pending입니다.

```python
# input: a pending refund record
case_input = {
    "status": "pending",
    "settled_date": None,
}
# expected output: the same record, unchanged
case_expected = {
    "status": "pending",
    "settled_date": None,
}
```

이런 예시는 두 가지로 읽힐 수 없습니다.

그다음 다음 시도 전에 테스트를 먼저 씁니다. 테스트는 기대 동작과 엣지 케이스를 다룹니다. null 날짜, 0원 금액, 알 수 없는 상태 코드 같은 것입니다.

1. Claude Code가 Bash로 테스트를 실행합니다.
2. 실패마다 입력, 기대 출력, 실제 출력을 공유합니다.
3. Claude Code가 고치고 다시 실행합니다.
4. 라운드마다 실패하는 테스트가 줄고, 작업이 언제 끝났는지는 테스트가 알려 줍니다.

**규칙**: 설명이 여러 방식으로 읽히면, 정확한 입력과 기대 출력을 보여 주고 모든 사례를 테스트로 확인합니다.

## 정리

- 작업이 자기 크기를 말해 주면, 모드를 바로 고릅니다.
- 파일 45개짜리 이전은 Explore로 탐색하는 플랜 모드로, 스택 트레이스가 분명한 한 줄 수정은 직접 실행으로 합니다.
- 변경이 계속 틀리게 돌아오면 설명을 멈춥니다. 실패하는 사례와 기대 출력을 주고, 테스트 실패를 보며 반복합니다.

같은 규칙이 시험의 **추출 시나리오**에서도 통합니다. 특이한 문서에서 추출이 필드 하나를 계속 비워 둡니다. 거기서도 더 강한 지침은 도움이 되지 않습니다. 정확한 사례가 빈틈을 보여 줍니다.

어느 시나리오에서든 작업이 말해 주는 크기로 작업 모드를 고르세요. 반복되는 실수는 더 긴 설명이 아니라 정확한 예시와 실패하는 테스트로 고치세요.
