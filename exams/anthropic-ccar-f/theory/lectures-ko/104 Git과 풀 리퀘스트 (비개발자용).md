# 104. Git과 풀 리퀘스트 (비개발자용)

한 개발자가 ShopAssist의 프롬프트를 개선했고, 테스트 세트에서 새 프롬프트가 더 높은 점수를 받았다고 해 봅시다.

이번 노트는 그 변경이 개발자의 컴퓨터에서 실제 고객에게 닿기까지의 과정을 다룹니다. 코드 리뷰와 자동 검사를 다루는 강의들이 이 용어를 계속 쓰기 때문에 중요합니다.

Git과 풀 리퀘스트를 써 본 적이 없는 분을 위한 선택 강의입니다.

> 핵심 아이디어: 아무도 ShopAssist를 직접 바꾸지 않습니다. 개발자가 변경을 제안하고, 다른 사람들이 읽습니다. 그다음에야 변경이 받아들여집니다.

변경 하나를 처음부터 끝까지 따라갑니다. 첫째, 코드가 어디에 사는지 봅니다. 둘째, 변경을 어떻게 만들고 저장하는지 봅니다. 셋째, 변경을 어떻게 제안하고 리뷰하는지 봅니다.

## 첫째: 코드가 사는 곳

ShopAssist는 파일 하나가 아닙니다. 채팅 창 뒤의 코드가 있고, 도구 정의와 테스트가 있습니다. 시스템 프롬프트가 담긴 지침 파일도 있습니다. 이 파일들은 모두 하나의 **리포지토리**에 함께 있습니다. 리포지토리는 프로젝트 폴더와 그 전체 기록입니다. 모든 변경을, 누가 언제 했는지와 함께 기억합니다.

이 기록을 관리하는 도구를 **Git**이라고 합니다. **GitHub**는 팀이 Git 리포지토리를 저장하고 공유하는 웹사이트입니다.

## 둘째: 변경을 만드는 방법

고객이 쓰는 버전을 직접 고쳐서는 안 됩니다. 그래서 **브랜치**라는 별도의 사본에서 작업합니다. main 브랜치에는 승인된 ShopAssist 버전이 있습니다. 새 브랜치는 main의 사본으로 시작하고, 우리 작업은 그 안에 머뭅니다.

이제 지침 파일에 새 줄을 추가합니다. 정책에 관한 단순한 질문에는 정책으로 답한다는 줄입니다. 그다음 무엇이 바뀌었는지 말하는 짧은 메시지와 함께 이 변경을 저장합니다. 이렇게 저장한 변경이 **커밋**입니다.

커밋은 프로젝트 기록의 한 단계입니다. 브랜치 하나에 커밋이 여러 개 있을 수 있습니다. 예를 들어 테스트 케이스도 하나 추가하면, 그것이 두 번째 커밋이 됩니다.

## 셋째: 변경을 제안하고 리뷰하는 방법

작업이 준비되면 **풀 리퀘스트**를 엽니다. 풀 리퀘스트는 제안입니다. 우리 브랜치의 변경을 main에 머지해 달라고 팀에 요청합니다. **머지**는 변경을 main 버전에 더한다는 뜻입니다.

풀 리퀘스트는 여러 부분으로 이루어진 페이지입니다. 가장 중요한 부분은 **diff**입니다. diff는 바뀐 것만 보여 줍니다. 지운 줄은 빨간색, 추가한 줄은 초록색입니다. 그래서 리뷰어는 프로젝트 전체를 읽지 않습니다. 지침 파일의 새 줄 하나만 읽습니다.

그다음 **코드 리뷰**가 이어집니다. 팀원이 diff를 읽고 리뷰 코멘트를 남깁니다. 리뷰 코멘트는 각각 특정한 줄에 붙습니다. 예를 들어 "이 규칙에서도 예외 요청은 여전히 사람에게 가나요?" 같은 코멘트입니다. 우리는 코멘트에 답하거나, 수정 사항을 담은 커밋을 하나 더 추가합니다.

리뷰어가 변경에 만족하면 **승인**합니다. 그러면 브랜치가 머지되고, 우리 변경은 main의 일부가 됩니다. 그 뒤에야 고객에게 닿을 수 있습니다.

| 용어 | 뜻 |
| --- | --- |
| 리포지토리 | 프로젝트 폴더와 그 전체 기록 |
| 브랜치 | main을 안전하게 두고 작업하는 별도의 사본 |
| 커밋 | 저장한 변경 하나 |
| 풀 리퀘스트 | 브랜치를 main에 머지하자는 제안 |
| diff | 바뀐 것만 보여 줌. 지운 줄은 빨간색, 추가한 줄은 초록색 |
| 리뷰 코멘트 | 특정 줄에 붙는 리뷰어의 의견 |
| 머지 | 변경을 main에 더함 |

## 정리

- 리포지토리는 ShopAssist의 파일과 그 기록을 담습니다.
- 작업은 브랜치에서 하므로 main은 안전합니다.
- 커밋은 저장한 변경 하나입니다.
- 풀 리퀘스트는 브랜치를 main에 머지하자고 제안합니다.
- 리뷰어는 머지 전에 diff를 읽고 코멘트를 남깁니다.

그러니 ShopAssist의 모든 변경은 고객이 보기 전에 이 경로를 거칩니다. 프롬프트 한 줄이라도 제안되고, 읽히고, 승인됩니다.

다음 노트에서는 모든 풀 리퀘스트에서 실행되는 자동 검사를 살펴봅니다.
