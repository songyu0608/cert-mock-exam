# 54. 실습: 훅과 핸드오프로 ShopAssist를 에이전트 시스템으로 만들기

지금까지 만든 도구는 누가 물어도 답합니다. 주문 번호만 주면 주문을 엽니다. 이번 노트에서는 ShopAssist를 에이전트 시스템으로 만듭니다. 루프 하나, 모든 도구 호출 전에 실행되는 코드의 검사, 그리고 상담원에게 넘기는 핸드오프를 갖춥니다. 아무 도구나 아무 때나 실행하는 루프는 언젠가 아무도 확인하지 않은 고객을 대신해 행동하게 되기 때문입니다.

## 전체 흐름

1. 고객 메시지가 루프에 들어옵니다.
2. 모든 도구 호출 전에 **훅**이 실행됩니다. 훅은 코드의 작은 함수이고, 지금까지 확인한 사실인 **케이스**를 봅니다. 고객 신원이 확인됐는지, 주문을 조회했는지 확인합니다.
3. 검사에 실패하면 도구는 실행되지 않고, Claude는 대신 구조화된 오류를 받습니다. 오류에는 무엇이 잘못됐는지와 고객에게 전할 메시지가 들어 있습니다.
4. 도구가 거절했는데 고객에게 여전히 도움이 필요하면 Claude가 `escalate`를 호출하고, 상담원이 이어서 처리합니다.

세 단계로 만들어 보겠습니다.

## 시작 파일: `agent.py`

`agent.py`는 지금까지 만든 것을 한데 모은 파일입니다.

- 맨 위에는 고객 한 명과 주문 하나가 있습니다. 배송된 지 45일 된 램프입니다.
- 그 아래에 도구 네 개가 있습니다. `get_customer`는 이메일로 고객을 확인합니다. `lookup_order`와 `start_return`은 전처럼 주문을 다룹니다. `escalate`는 짧은 사유와 함께 문의를 상담원에게 넘깁니다.
- 더 아래에는 도구 뒤에서 실행되는 함수들과, `run`이라는 함수 안에 익숙한 루프가 있습니다.

함수 세 개(`get_customer`, `lookup_order`, `escalate`)는 찾은 내용을 `case`라는 딕셔너리에 기록합니다. 케이스에는 고객 ID, 주문 ID, 상담원에게 넘겼는지 여부가 들어갑니다. 하지만 아직 케이스가 없으므로 스크립트는 이대로 실행되지 않습니다.

## 1단계: 케이스를 만들고 지금 상태를 시험하기

도구 정의 바로 뒤에 세 값이 모두 비어 있는 케이스를 둡니다. 이 짧은 스크립트에서는 케이스 하나가 실행 전체에 쓰입니다. 실제 시스템은 대화마다 케이스를 하나씩 둡니다. 맨 아래에는 첫 번째 테스트를 둡니다. 고객이 자신이 누구인지 밝히지 않고, 이 주문의 램프를 반품하고 싶다고 합니다.

실행해 보세요. 루프는 메시지를 Claude에 보내고, Claude가 요청한 도구를 무엇이든 실행합니다. Claude가 `lookup_order`를 요청했고 루프가 실행했습니다. 주문 정보가 돌아왔습니다. 램프는 물론 주인의 고객 ID까지 들어 있습니다. 그러자 Claude는 이 고객에게 램프와 배송일을 알려 줬습니다.

케이스를 보면 문제가 드러납니다. 주문 ID는 채워졌지만 고객 ID는 여전히 `None`입니다. 누가 묻고 있는지 아무도 확인하지 않았습니다. 코드가 낯선 사람에게 주문을 열어 준 것입니다.

## 2단계: 모든 도구 호출 앞에 게이트 두기

두 번째 단계는 게이트입니다. 앞의 흐름에서 본 훅, 즉 모든 도구 호출 전에 실행되고 호출을 멈출 수 있는 작은 함수입니다. 도구 이름과 함수를 연결하는 표 아래에 둡니다. 이름은 `before_tool`이고, Claude가 고른 도구 이름과 입력을 받습니다. 모든 도구 호출 전에 실행되며 호출을 막을 수 있다는 짧은 설명을 붙입니다.

규칙은 두 가지입니다.

1. **게이트**: 도구가 `get_customer`가 아닌데 케이스에 고객 ID가 아직 없으면 호출을 막습니다. 범주가 `permission`인 구조화된 오류를 돌려주고, 고객에게 전할 메시지는 “먼저 이메일을 알려 주세요”입니다.
2. **주문 일치**: `start_return`은 조회한 주문에만 쓸 수 있습니다. 다른 주문이면 `validation` 오류를 돌려주고, 메시지는 “먼저 주문을 조회하세요”입니다.

두 규칙을 모두 통과하면 훅은 `None`을 돌려줍니다. 이 호출에 반대할 이유가 없다는 뜻입니다.

아래는 흐름을 보여 주기 위한 예시입니다. 필드 이름은 [[41 실습 - 주문 조회와 반품 거절을 코드로 구분하기|41번 노트]]의 구조화된 오류를 따랐고, 원문 코드와 세부 표현은 다를 수 있습니다.

```python
def before_tool(name, tool_input):
    """모든 도구 호출 전에 실행되며, 호출을 막을 수 있다."""
    if name != "get_customer" and case["customer_id"] is None:
        return {
            "isError": True,
            "errorCategory": "permission",
            "customerMessage": "먼저 이메일을 알려 주세요.",
        }
    if name == "start_return" and tool_input.get("order_id") != case["order_id"]:
        return {
            "isError": True,
            "errorCategory": "validation",
            "customerMessage": "먼저 주문을 조회하세요.",
        }
    return None
```

이제 루프가 먼저 훅에 물어보게 합니다. 도구 함수를 실행하던 줄을 찾아, 그 자리에서 `before_tool`을 이름과 입력으로 호출합니다. 결과가 `None`이면 훅이 이 호출에 반대하지 않는다는 뜻이고, 그때만 실제 함수를 실행합니다. 원래 있던 호출을 `if` 안으로 옮긴 것입니다. 그래서 차단된 도구는 아예 실행되지 않습니다. Claude는 훅의 오류를 도구 결과로 받습니다. 도구 오류 실습에서처럼 결과에 `is_error`를 표시하므로 Claude는 호출이 실패했다는 것을 압니다.

같은 고객, 같은 메시지로 다시 실행해 보세요. Claude가 `lookup_order`를 요청했고, 훅이 “먼저 이메일을 알려 주세요”라는 `permission` 오류로 막았습니다. 그래서 Claude는 고객에게 이메일을 묻습니다. 케이스는 여전히 비어 있습니다. 아무것도 조회되지 않았습니다.

루프 안에서 일어난 일을 정리하면 이렇습니다.

1. Claude가 `lookup_order`를 요청했습니다.
2. 도구가 실행되기 전에 루프가 훅에 물었습니다.
3. 훅은 케이스에 고객 ID가 없다는 것을 확인하고 `permission` 오류를 돌려줬습니다.
4. 그 오류가 도구 결과로 Claude에 돌아갔고, 도구 자체는 실행되지 않았습니다.

## 3단계: 정책으로 도울 수 없는 확인된 고객을 상담원에게 넘기기

세 번째 단계는 정책으로 도울 수 없는 확인된 고객을 위한 핸드오프입니다. 먼저 시스템 프롬프트의 마지막 줄을 새 규칙으로 바꿉니다.

- 고객, 주문, 반품에는 도구를 사용합니다.
- 도구가 정책을 검사하고, 무엇이 부족한지 Claude에 알려 줍니다. 그러니 Claude가 규칙을 직접 적용하지 말고 도구가 판단하게 합니다.
- 도구가 거절했는데 고객에게 여전히 도움이 필요하면 `escalate`로 문의를 상담원에게 넘깁니다.
- 마지막에는 기존 규칙을 다시 둡니다. 두 문장으로 답합니다.

맨 아래에 두 번째 테스트를 둡니다. 같은 고객이 이메일을 알려 주고, 램프가 깨진 채로 왔다고 말합니다.

두 테스트를 함께 실행합니다. 두 테스트가 차례로 실행되고, 각 테스트는 Claude를 여러 번 호출하는 루프입니다. 출력이 많으니 터미널을 크게 키워 보세요.

- **첫 번째 테스트**는 이번에도 막히고, Claude는 이메일을 묻습니다.
- **두 번째 테스트**의 진행은 다음과 같습니다.
  1. `get_customer`가 이메일을 확인했고, 케이스에 고객 ID가 기록됐습니다.
  2. `lookup_order`가 45일 전에 배송된 램프를 찾았고, 케이스에 주문 ID가 기록됐습니다. 이 두 호출은 모두 먼저 훅을 통과했습니다.
  3. `start_return`이 30일 반품 기한이 지났다며 거절했습니다. 이번에는 훅이 아니라 도구가 거절한 것입니다.
  4. 고객에게 여전히 도움이 필요하므로 Claude가 문의를 요약한 사유와 함께 `escalate`를 호출했습니다. `escalate`는 상담원용 티켓을 열고, 넘겼다는 표시를 설정했습니다.
  5. Claude는 상담원이 이어서 처리할 것이라고 고객에게 안내하고 티켓 번호를 알려 줬습니다.

마지막 케이스에는 고객, 주문, 그리고 `escalated`가 `True`로 남아 있습니다.

## 검사를 도구 안에 넣으면 안 될까?

각 도구 안에 검사를 넣고 싶을 수 있습니다. 그러면 새 도구를 만들 때마다 같은 검사가 필요하고, 하나라도 빠뜨리면 그대로 구멍이 됩니다. 훅은 루프 안에 있으므로 나중에 추가하는 도구를 포함해 모든 도구 호출이 훅을 거칩니다.

## 정리

- 케이스의 사실 정보는 코드에 보관합니다.
- 모든 도구 호출은 실행 전에 훅이 검사하게 합니다.
- 정책으로 해결할 수 없는 문의를 위해 루프에 핸드오프 도구를 둡니다.
