# 24. 실습: 스키마에 맞는 응답 받기

고객이 “파란 재킷이 너무 작아서 반품하고 싶어요”라고 이메일을 보냈습니다. 고객 지원팀은 메일에서 **주문 ID, 상품, 반품 사유**를 꺼내 저장하려고 합니다. Claude가 매번 다른 문장으로 설명하면 우리 코드는 그 문장 속 어디에 주문 번호와 반품 사유가 있는지 다시 찾아야 합니다. 이번 노트에서는 원하는 응답의 모양을 먼저 정하고, 서로 다른 이메일 두 통을 그 모양으로 읽어 보겠습니다.

## 어떤 답을 받을지 스키마로 적기

빈 파일 `extract.py`에 `json`을 가져오고, 이전 실습처럼 `.env`에서 API 키를 읽어 클라이언트와 모델 이름을 준비합니다. 그런 다음 `SCHEMA`에 **JSON 스키마**를 정의합니다. 스키마는 어떤 필드가 있고, 각 필드에 어떤 종류의 값을 넣을 수 있는지 설명합니다.

이번 응답의 `type`은 `object`입니다. 객체 안에 허용할 세 필드를 `properties`에 적습니다. 주문 ID와 상품은 문자열입니다. 반품 사유도 문자열이지만 ‘너무 작음’, ‘너무 큼’, ‘파손’, ‘기타’ 가운데 하나만 받겠습니다. 이렇게 허용할 값을 미리 열거하는 것이 `enum`입니다. 고객이 어떤 표현을 쓰든 사유 필드에 다섯 번째 항목을 새로 만들 수는 없습니다.

세 필드를 모두 `required`에 넣어 어느 것도 빠지지 않게 합니다. `additionalProperties`는 `false`로 두어 목록에 없는 필드가 덧붙지 않게 합니다. 이 두 조건을 함께 걸면 완성된 응답 객체에는 우리가 정한 세 필드가 들어갑니다.

## 응답을 Python 딕셔너리로 읽기

`extract` 함수는 이메일 본문 하나를 받아 `client.messages.create(...)`를 호출합니다. 모델과 `max_tokens=300`을 지정합니다. 이번에 살펴볼 곳은 `output_config`입니다. 이전처럼 `effort`를 `low`로 두고, 같은 설정 안에서 `format`의 `type`을 `json_schema`로, `schema`를 조금 전에 만든 `SCHEMA`로 지정합니다. 이 설정이 API에 응답 형식을 알려 줍니다.

`messages`에는 `user` 메시지 하나를 넣습니다. “다음 고객 이메일에서 반품 요청 정보를 추출하세요”라고 쓴 뒤 줄을 두 번 바꾸고 실제 이메일을 붙입니다. 응답이 돌아오면 `response.content`를 순회하다가 `text` 블록을 만났을 때 `json.loads(block.text)`를 반환합니다. JSON 텍스트가 Python 딕셔너리로 바뀌므로 주문 번호가 들어갈 자리를 문장에서 다시 찾을 필요가 없습니다. 텍스트 블록이 하나도 없으면 이 함수는 값을 돌려주지 못합니다. 실제 서비스에서는 그 경우도 확인한 뒤 저장합니다.

## 주문 번호를 쓰지 않은 이메일 보내 보기

`EMAILS` 목록에 이메일 두 통을 넣고, 하나씩 `extract`에 넘겨 반환값을 출력합니다. 메일 한 통당 API 요청 한 번입니다. 두 응답을 차례로 살펴보세요.

첫 번째 고객은 **주문 ID를 알려 주고**, 그 주문으로 산 파란 재킷이 너무 작아 반품하고 싶다고 썼습니다. 원문의 실행 결과에는 고객이 적은 주문 ID, 파란 재킷, ‘너무 작음’에 해당하는 사유가 들어 있습니다. 코드가 필요한 세 값을 모두 읽을 수 있습니다.

두 번째 고객은 신발이 파손됐다고만 썼습니다. 상품은 신발이고 사유는 ‘파손’으로 분류할 수 있지만, 이메일 어디에도 주문 번호가 없습니다. 그런데 이번 실행에서는 주문 ID 필드까지 채워져 돌아옵니다. 그 안에 들어 있는 문자열은 `unknown`입니다.

왜 스키마를 통과했을까요? 주문 ID 필드에는 문자열이 반드시 있어야 하고, `unknown`도 문자열이기 때문입니다. 그렇다고 스토어에 그런 주문이 있다는 뜻은 아닙니다. 이 응답을 그대로 저장하면 어느 주문에도 연결할 수 없는 반품 요청이 생깁니다. **세 필드를 읽을 수 있는지**는 스키마로 정하고, **그 ID가 실제 주문을 가리키는지**는 애플리케이션 코드에서 확인해야 합니다.

시험에서는 같은 목적을 다른 방식으로 물을 수 있습니다. 추출할 필드를 **도구의 입력 스키마**로 정의한 뒤, `tool_choice`로 `any`나 특정 도구를 지정해 그 필드를 받는 방식입니다. [[23 tool_choice - 자동 선택, 호출 필수, 도구 지정|23번 노트]]에서 본 것처럼 원문에 나온 세 모델 버전은 두 강제 설정을 거부합니다. 이번 실습에서는 응답 자체의 출력 형식을 지정했습니다. 도구 입력으로 받는 구현이라면 `auto`와 `strict`를 함께 쓰고, 호출이 왔는지도 검사합니다. 어느 방식으로 데이터를 받든 주문 번호의 진위까지 스키마가 확인해 주지는 않습니다.
