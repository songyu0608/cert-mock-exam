# 88. 독립적인 리뷰

지금까지 ShopAssist 팀은 사람이 키보드 앞에 있는 상태로 Claude Code를 썼습니다. 이제 같은 도구가 아무도 지켜보지 않는 팀 파이프라인으로 들어갑니다.

이번 노트에서는 그보다 먼저 정해야 할 질문을 살펴봅니다. **Claude가 쓴 코드는 누가 리뷰해야 할까요?** 작성자의 생각을 공유하는 리뷰어는 작성자의 실수도 똑같이 놓치기 때문입니다.

## 자기 리뷰가 실제 버그를 놓쳤다

팀이 풀 리퀘스트에 추가한 리뷰 봇을 떠올려 보세요. 각 diff를 Claude에 보내고 지적 사항을 코멘트로 올리는 CI 작업입니다.

이제 이 봇이 리뷰하는 코드 중 점점 더 많은 부분을 Claude Code가 씁니다. 이번 주에는 Claude Code에 ShopAssist의 부분 환불 기능을 추가해 달라고 합니다. **부분 환불**은 주문 금액의 일부만 돌려주는 것입니다. Claude Code가 변경과 테스트를 씁니다. 그다음 같은 세션에서 자기 작업을 리뷰해 달라고 합니다. Claude Code는 변경이 맞아 보인다고 답합니다.

하지만 변경에는 버그가 있습니다.

```python
LIMIT = 500
def partial_refund(order, amount):
    if amount > LIMIT:
        raise ValueError("over limit")
    order.refund(amount)
partial_refund(order, 300)
partial_refund(order, 300)
```

새 코드는 500달러 한도를 주문 합계가 아니라 환불 한 건마다 확인합니다. 그래서 300달러짜리 부분 환불 두 건이 600달러를 돌려주고, 어떤 사람도 이 사례를 보지 못합니다.

가장 중요한 원칙은 **리뷰어는 작성자의 추론을 공유해서는 안 된다**는 것입니다. 이번 노트에서는 자기 리뷰가 이 버그를 놓치는 이유, 도움이 안 되는 두 해결책, 독립적인 리뷰 인스턴스를 차례로 봅니다.

## 1. 자기 리뷰

코드를 쓴 세션은 작성하면서 생각한 모든 것을 그대로 갖고 있습니다. 작성하는 동안 이 세션은 환불 훅이 이미 한도를 처리한다고 결정했습니다. 그래서 리뷰할 때 그 결정을 거쳐 코드를 읽습니다. 코드가 의도대로 동작하는지는 확인하지만, 의도 자체를 의심할 가능성은 훨씬 낮습니다.

1. 코드 작성: "훅이 한도를 처리한다"고 결정
2. 같은 세션의 리뷰: 그 결정을 거쳐 코드를 읽음
3. 맞아 보임: 의도는 한 번도 의심받지 않음

시험은 이것을 **자기 리뷰의 한계**(self-review limitation)라고 부릅니다. 모델이 생성할 때의 추론 컨텍스트를 그대로 갖고 있으므로, 같은 세션에서는 자기 선택을 좀처럼 의심하지 않습니다.

## 2. 옳아 보이는 해결책

| 해결책 | 실패하는 이유 |
| --- | --- |
| 더 강한 지침: "다른 사람이 쓴 것처럼 비판적으로 리뷰해 줘." | 지침은 앞선 추론을 지우지 못합니다. 세션은 모든 줄이 왜 거기 있는지 여전히 기억합니다. |
| 더 오래 생각하기 | 같은 인스턴스가 더 생각해도 같은 추론에서 출발하고, 그 추론을 더 따라갈 뿐입니다. |

시험에서는 더 오래 생각하는 것을 **extended thinking**이라고 부릅니다.

> 제품 참고: 현재 모델에서는 더 높은 effort 설정으로 더 많이 생각하게 합니다(강의 슬라이드 기준).

## 3. 독립적인 인스턴스

새 컨텍스트로 두 번째 Claude 인스턴스를 시작합니다. 이 인스턴스는 diff와 프로젝트 표준을 받지만, 코드를 만든 대화는 받지 않습니다.

| 두 번째 인스턴스가 받는 것 | 받지 않는 것 |
| --- | --- |
| diff: 무엇이 바뀌었나 | 작성자의 대화 기록 |
| 프로젝트 표준: 규칙 | |

이 인스턴스는 작성자가 무엇을 의도했는지 모릅니다. 코드가 무엇을 하는지만 봅니다. 그래서 평범한 질문을 던집니다. 주문 하나에 부분 환불이 두 번 들어오면 어떻게 되지? 그 질문이 버그를 찾습니다. 이런 독립적인 인스턴스는 자기 리뷰 지침과 extended thinking이 놓치는 미묘한 문제를 잡아냅니다.

### Claude Code에서

Claude Code에서는 이것이 **세션 컨텍스트 격리**입니다. 리뷰는 새 세션으로 하는 별도의 Claude Code 실행입니다. 코드를 쓴 세션을 resume하지 않고, 포크하지도 않습니다. 포크는 작성자의 기록 전체를 복사하기 때문입니다.

```bash
# Run 1: writes the code (session A)
claude -p "Add partial refunds"
# Run 2: reviews it in a new session (session B)
git diff main | claude -p "Review this diff"
# Never resume session A to review:
#   claude --resume <session-A> ...
# Never fork it - a fork copies the history:
#   claude --resume <session-A> --fork-session
```

리뷰어는 같은 모델이어도 됩니다. **독립성은 다른 모델이 아니라 컨텍스트에서 나옵니다.** 그래서 코드를 먼저 쓰고, 독립적인 인스턴스로 리뷰하는 것은 타당한 패턴입니다. 한 인스턴스가 쓰고, 두 번째 인스턴스가 확인합니다.

## 정리

- 코드를 쓴 세션은 자기 추론을 유지하므로, 자기 결정을 좀처럼 의심하지 않습니다.
- 비판적으로 보라고 지시해도 바뀌지 않습니다. 같은 인스턴스가 더 오래 생각해도 바뀌지 않습니다.
- 새 컨텍스트의 독립적인 인스턴스가 미묘한 버그를 잡습니다.
- Claude Code에서는 리뷰를 자기 세션에서 실행하고, 코드를 쓴 세션에서는 절대 하지 않습니다.

한 Claude가 코드를 쓰고, 다른 Claude가 깨끗한 컨텍스트로 리뷰하게 하세요. 다음 노트에서는 리뷰 한 번에 담기에 너무 큰 변경을 다룹니다.
