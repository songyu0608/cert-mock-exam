# 58. Task로 서브에이전트 시작하기

지난 노트에서는 코디네이터가 주제 전체를 덮도록 램프 질문을 나눴습니다. 이번 노트에서는 코디네이터가 서브에이전트를 실제로 어떻게 시작하고, 여러 서브에이전트를 어떻게 동시에 실행하는지 살펴봅니다. 좋은 계획도 작업이 시작되기 전에는 아무 일도 하지 않습니다. 그리고 서브에이전트를 시작하는 방식에 따라 팀이 보고서를 얼마나 기다릴지가 정해집니다.

스토어 팀은 Agent SDK로 리서치 어시스턴트를 만들었습니다. 이 어시스턴트는 **램프는 왜 그렇게 자주 반품될까?**라는 큰 질문 하나에 답합니다. 가운데에 코디네이터가 있고, 주위에 웹 검색, 문서 분석, 종합, 보고서 서브에이전트가 있습니다. 코디네이터의 계획은 준비됐고, 주제의 모든 영역에 담당자가 있습니다. 이제 코디네이터가 서브에이전트들을 시작해야 합니다.

가장 중요한 원칙은 **코디네이터는 도구를 호출해서 서브에이전트를 시작한다**는 것입니다. 이번 노트에서는 Task 도구, 에이전트 정의, 서브에이전트 병렬 실행을 차례로 봅니다.

## 1. Task 도구

코디네이터에게 서브에이전트는 도구처럼 보입니다. 코디네이터는 도움이 필요하면 **Task** 도구를 요청합니다. ShopAssist가 `lookup_order`를 요청하는 방식과 똑같습니다.

1. 코디네이터가 Task를 요청합니다. 입력에는 시작할 서브에이전트의 이름과, 그 서브에이전트가 할 일을 담은 프롬프트가 들어갑니다.
2. SDK가 서브에이전트를 시작합니다.
3. 서브에이전트는 자기 도구를 가지고 자기 루프에서 일합니다.
4. 일이 끝나면 서브에이전트의 최종 답이 도구 결과로 코디네이터에게 돌아옵니다.

Task는 시험에서 쓰는 이름입니다. 현재 SDK 릴리스에서는 이 도구를 **Agent**라고 부릅니다. **시험에서는 Task로 답하세요.**

앞에서 본 허용 도구 옵션은 에이전트가 쓸 수 있는 도구를 나열합니다. 코디네이터의 이 목록에는 반드시 Task가 들어 있어야 합니다. Task를 빼면 코디네이터는 계획을 세울 수 있고, 서브에이전트에게 일을 넘긴다고 글로 쓸 수도 있습니다. 하지만 서브에이전트는 하나도 시작할 수 없습니다.

슬라이드의 코디네이터 설정은 다음과 같습니다.

```python
# Exam: "Task". Current SDK releases: "Agent".
MODEL = "claude-sonnet-5-5"
coordinator = ClaudeAgentOptions(
    model=MODEL,
    system_prompt="You coordinate research on lamp returns.",
    allowed_tools=["Task"],
)
```

## 2. 에이전트 정의

서브에이전트의 종류마다 **에이전트 정의**(agent definition)가 하나씩 있습니다. 시험에서 이 설정을 부르는 이름입니다. 주요 부분은 세 가지입니다.

| 부분 | 역할 |
| --- | --- |
| 설명(description) | 이 서브에이전트가 무엇을 하고 언제 쓰는지 밝힙니다. Claude가 도구 설명을 읽고 도구를 고르듯, 코디네이터는 이 설명을 읽고 알맞은 서브에이전트를 고릅니다. |
| 시스템 프롬프트(prompt) | 서브에이전트의 역할과 규칙을 줍니다. 문서 분석이라면 “스토어의 지원 티켓과 공급업체 보고서를 읽고, 모든 조사 결과에 출처와 날짜를 붙여라”입니다. |
| 도구(tools) | 이 서브에이전트가 쓸 수 있는 도구를 제한합니다. 이 목록에 무엇을 넣을지는 다음 노트에서 정합니다. |

슬라이드의 문서 분석 정의는 다음과 같습니다.

```python
agents = {
    "document-analysis": AgentDefinition(
        description="Reads the store's tickets and supplier reports. "
                    "Use it for facts from the store's own files.",
        prompt="Read the support tickets and supplier reports. "
               "Give every finding its source and its date.",
        tools=["Read", "Grep"],
    ),
}
```

설명과 프롬프트는 필수이고, 도구와 모델은 선택입니다. 코디네이터는 서브에이전트마다 정의를 하나씩 갖고, 모두 하나의 도구로 시작합니다.

## 3. 서브에이전트 병렬 실행

웹 검색과 문서 분석은 서로에게 의존하지 않습니다. 하나는 웹을 읽고, 다른 하나는 스토어 내부 파일을 읽습니다. 그래서 코디네이터는 **한 응답에 Task 호출 두 개**를 넣습니다. SDK는 두 서브에이전트를 동시에 실행하고, 두 결과는 코디네이터에게 가는 다음 메시지에 함께 돌아옵니다. ShopAssist가 한 응답에서 `lookup_order`를 두 번 호출했던 것과 같은 방식을 한 단계 위에서 쓰는 것입니다.

턴을 나눠 호출하는 경우와 비교해 보세요. 코디네이터가 웹 검색을 요청하고 결과를 기다립니다. 그다음에야 문서 분석을 요청합니다. 서브에이전트마다 몇 분씩 걸린다고 가정하면 대기 시간이 더해지고 보고서는 훨씬 늦게 나옵니다. 서로 독립적인 서브에이전트를 한 턴에 하나씩 시작하면 안 됩니다. Task 호출을 한 응답에 함께 넣으세요.

종합은 다릅니다. 종합에는 두 검색의 조사 결과가 모두 필요합니다. 그래서 코디네이터는 두 결과가 모두 돌아온 뒤, 다음 턴에 종합을 시작합니다. 보고서 서브에이전트도 같은 이유로 종합 뒤에 시작합니다. 독립적인 작업만 병렬로 실행합니다. 앞선 결과가 필요한 작업은 그 결과를 기다립니다.

| 작업 | 시작 시점 |
| --- | --- |
| 웹 검색, 문서 분석 | 같은 응답에서 함께 |
| 종합 | 두 결과가 돌아온 뒤 |
| 보고서 | 종합이 끝난 뒤 |

Task 호출마다 자기 프롬프트도 함께 보냅니다. 그 프롬프트에 무엇을 담을지는 별도 주제이고, 곧 다시 다룹니다.

## 정리

- 코디네이터는 Task 도구를 호출해 서브에이전트를 시작합니다. 현재 릴리스에서는 이 도구를 Agent라고 부릅니다.
- 코디네이터의 허용 도구에 Task가 없으면 서브에이전트를 하나도 시작할 수 없습니다.
- 서브에이전트의 종류마다 설명, 시스템 프롬프트, 도구 제한을 담은 에이전트 정의가 있습니다.
- 한 응답 안의 Task 호출 여러 개는 병렬로 실행됩니다. 턴을 나눈 Task 호출은 차례로 실행됩니다.

서브에이전트마다 정의를 한 번 만들고, 코디네이터에게 Task를 주고, 서로 독립적인 서브에이전트는 한 응답에서 함께 시작하세요. 다음 노트에서는 각 서브에이전트가 어떤 도구를 받을지 정하겠습니다.
