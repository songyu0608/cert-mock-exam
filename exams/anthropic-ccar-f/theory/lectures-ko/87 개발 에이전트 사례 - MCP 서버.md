# 87. 개발 에이전트 사례: MCP 서버

지난 점검에서는 팀의 개발 에이전트가 오래된 결제 모듈을 단계별로 파악하고, 요청 코드를 안전하게 바꿨습니다. 개발자 생산성 시나리오의 이번 마지막 점검은 MCP 서버에 관한 것입니다.

| 결정 | 위험 |
| --- | --- |
| 서버가 제공하는 더 나은 도구를 에이전트가 왜 무시하나 | 설치돼 있어도 쓰이지 않는 서버는 도움이 되지 않습니다. |
| 모두가 공유하는 통합을 팀이 어떻게 추가하나 | 잘못 공유한 서버는 비밀 정보를 새게 할 수 있습니다. |

## 첫 번째 결정: 에이전트가 더 나은 도구를 건너뛴다

팀은 자체 코드 검색 MCP 서버를 에이전트에 연결했습니다. 이 서버의 도구는 함수를 호출하는 모든 곳을 찾습니다. 코드 구조를 이해하므로, 다른 이름으로 된 호출도 찾고 주석은 건너뜁니다. 그런데 이 도구의 설명은 "Searches code."(코드를 검색함)뿐입니다.

로그를 보면 열 번 중 아홉 번은 에이전트가 대신 Grep을 쓴다고 가정합니다. Grep은 텍스트를 일치시키므로, 다른 이름으로 된 호출을 놓칩니다. 그래서 에이전트는 그 함수를 호출하는 곳의 목록을 불완전하게 보고합니다.

**무엇이 필요할까요?** 여기서는 아무도 보장을 요구하지 않습니다. 에이전트가 선택을 내리는 레이어에서의 첫 단계가 필요합니다.

**그럴듯한 오답**은 에이전트의 도구에서 Grep을 빼서, 다른 선택지를 없애는 것입니다. 이 방법은 실패합니다.

- 로그의 오류 메시지 같은 평범한 텍스트에는 Grep이 여전히 맞는 도구입니다.
- Grep을 빼면 그 작업이 깨집니다.
- 진짜 원인을 가립니다.

**가장 좋은 선택**은 MCP 도구의 설명을 개선하는 것입니다. 에이전트는 주로 설명을 보고 도구를 고르는데, "Searches code."는 거의 아무것도 알려 주지 않습니다. 새 설명은 도구가 무엇을 할 수 있고 무엇을 돌려주는지 말합니다.

```python
{
  "name": "find_callers",
  "description": (
    "Finds every place that calls a function or class, "
    "including calls under another name. "
    "Skips comments. "
    "Returns each file, line and calling function. "
    "Use it to find who calls a name; "
    "use Grep for plain text."
  ),
}
```

함수나 클래스를 호출하는 모든 곳을, 다른 이름으로 된 호출까지 찾습니다. 주석은 건너뜁니다. 파일, 줄, 호출하는 함수를 돌려줍니다. 누가 어떤 이름을 호출하는지 찾을 때 쓰고, 평범한 텍스트에는 Grep을 씁니다. 이제 에이전트에게는 이 도구를 고를 분명한 이유가 있습니다.

### 두 번째 수: 카탈로그

이 결정에는 두 번째 수가 있습니다. 에이전트가 과제마다 시작할 때, 어느 모듈이 무엇을 하는지 알아내는 데만 호출을 약 12번 쓴다고 가정합니다. 폴더를 나열하고, 폴더마다 설명 파일을 열고, 이름을 검색합니다.

그래서 서버가 모듈 카탈로그도 **리소스**로 제공합니다. 도구는 동작을 수행하고, 리소스는 읽을 내용을 줍니다. 카탈로그는 모듈마다 무엇을 맡는지, 진입점이 어디인지 나열합니다. 에이전트는 카탈로그를 한 번 읽고 곧장 결제 모듈로 갑니다.

**규칙**:

| 증상 | 해결책 |
| --- | --- |
| 에이전트가 더 나은 MCP 도구를 무시한다 | 그 도구의 설명을 개선하고, 내장 도구는 그대로 둡니다. |
| 에이전트가 무엇이 있는지 알아내려고만 탐색한다 | 카탈로그를 리소스로 제공합니다. |

## 두 번째 결정: 모두에게 Jira가 필요하다, 비밀 정보 없이

팀은 흔히 쓰는 이슈 트래커인 Jira로 버그를 관리합니다. 이제 에이전트가 과제마다 그 뒤의 티켓을 읽어야 하고, 모든 개발자의 Claude Code도 그래야 합니다. 한 개발자는 커스텀 Jira 서버를 만들기 시작했습니다. 다른 개발자는 자기 노트북에 동작하는 설정이 있는데, 설정에 자기 토큰을 붙여 넣었습니다.

**무엇이 필요할까요?** 모든 개발자가 받는 공유 설정이고, 리포지토리에는 비밀 정보가 없어야 합니다.

**그럴듯한 오답**은 두 가지입니다.

| 오답 | 실패하는 이유 |
| --- | --- |
| 팀이 통제하도록 커스텀 서버를 완성하기 | Jira용 커뮤니티 서버가 이미 있고, 다른 사람들이 최신으로 유지합니다. 커스텀 서버는 스토어 규칙이 담긴 ShopAssist 백엔드처럼 팀 고유의 워크플로에 맞습니다. |
| 동작하는 설정을 그대로 커밋하기 | 토큰이 리포지토리 기록에 들어가고, 리포지토리를 읽을 수 있는 누구나 토큰을 읽습니다. |

**가장 좋은 선택**은 커뮤니티 Jira 서버를 프로젝트 파일 `.mcp.json`에 설정하고 커밋하는 것입니다. 설정에 토큰이 필요한 자리에는 대신 환경 변수 이름을 적습니다. 달러 기호와 이름을 감싼 중괄호로 씁니다. 개발자는 각자 자기 컴퓨터에서 이 변수를 한 번 설정합니다.

```json
{
  "mcpServers": {
    "jira": {
      "command": "npx",
      "args": ["-y", "community-jira-server"],
      "env": {
        "JIRA_TOKEN": "${JIRA_API_TOKEN}"
      }
    }
  }
}
```

패키지 이름 `community-jira-server`는 강의의 예시입니다.

Claude Code는 모든 개발자의 환경에서 이 파일을 읽습니다. 에이전트도 프로젝트 설정을 로드하도록 설정돼 있으면 이 파일을 읽습니다. 설정에 있는 모든 서버의 도구는 연결할 때 발견되므로, Jira 도구가 코드 검색 도구 옆에 놓입니다.

실험용 서버를 써 보고 싶은 개발자는 홈 폴더의 `.claude.json`에 둡니다. 거기서는 그 개발자에게만 닿습니다.

| 범위 | 위치 | 받는 사람 |
| --- | --- | --- |
| 프로젝트 | `.mcp.json`, 커밋 | 모두 |
| 개인 | `~/.claude.json` | 나만 |
| 로컬 | `claude mcp add`의 세 번째 선택지 | 나, 한 프로젝트에서만 |

> 제품 참고: 로컬 범위는 현재 서버 추가 명령이 제공하는 세 번째 범위입니다(강의 슬라이드 기준).

**규칙**: 표준 시스템에는 커뮤니티 서버를 씁니다. 프로젝트 파일로 공유하고, 비밀 정보는 모두 환경 변수에 둡니다.

## 정리

- 더 나은 MCP 도구보다 Grep을 고르는 에이전트에게는 도구를 줄이는 것이 아니라, 그 도구의 더 나은 설명이 필요합니다.
- 리소스로 제공하는 카탈로그는 둘러보기만 하는 호출을 많이 줄여 줍니다.
- 표준 시스템에는 커뮤니티 서버를, 팀 고유의 워크플로에는 커스텀 서버를 씁니다.
- 팀 서버는 `.mcp.json`에 두고, 비밀 정보는 환경 변수 이름으로 적습니다.
- 개인 실험은 `.claude.json`에 둡니다.

같은 규칙이 **고객 지원 시나리오**에서도 통합니다. 주문에 관한 질문에 ShopAssist가 `get_customer`를 부르면, 첫 해결책은 도구 설명입니다(예: `lookup_order_by_id`에 더 명확한 설명). 라우팅 레이어나 도구 합치기는 필요하다면 그다음입니다.

에이전트가 엉뚱한 도구를 고르면, 골랐어야 할 도구의 설명을 개선하세요. 다른 도구를 빼앗지 마세요.
