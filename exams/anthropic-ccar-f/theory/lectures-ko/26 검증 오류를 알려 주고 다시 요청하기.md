# 26. 검증 오류를 알려 주고 다시 요청하기

지난 노트에서는 ShopAssist가 주문 번호를 검사하고, 잘못된 값을 받으면 오류를 알려 주고 다시 요청하도록 했습니다. 이번에는 고객이 이메일에 첨부한 반품 신청서를 읽어 보겠습니다. ShopAssist는 주문 번호, 상품, 주문일, 배송일, 반품 사유를 추출하고 코드는 저장 전에 각 값을 검사합니다. 어떤 신청서는 한 번 다시 읽으면 바로잡히는데, 어떤 신청서는 몇 번을 읽어도 같은 필드에서 막힙니다. 둘의 차이는 어디에 있을까요?

## 형식이 틀렸을 때와 뜻이 틀렸을 때

필수 필드가 빠졌거나, 숫자를 받을 자리에 문자열이 왔거나, 미리 정한 목록에 없는 값이 오면 **스키마 오류**입니다. 시험에서는 추출용 도구에 JSON 스키마를 지정해 이런 오류를 막는 상황이 나옵니다. API에서 도구 입력이 스키마를 따르도록 보장하려면 엄격한 도구 사용(`strict: true`)을 설정합니다. 응답 본문을 JSON으로 받을 때는 [[24 실습 - 스키마에 맞는 응답 받기|24번 노트]]에서처럼 구조화된 출력 형식을 지정할 수 있습니다. 일반 도구에 스키마를 적는 것만으로 모든 호출의 입력 형식이 보장되지는 않습니다.

**의미 오류**는 각 필드의 형식이 맞아도 생깁니다. 알렉스가 재킷의 반품 신청서에 주문일과 배송일을 모두 적었다고 해 보세요. Claude가 두 날짜를 서로 바꿔 넣어도 각각은 올바른 날짜입니다. 그런데 코드에서 “배송일은 주문일보다 빠를 수 없다”는 규칙을 검사하면 오류가 드러납니다. 금액 필드가 모두 숫자여도 합계가 맞지 않을 수 있는 것과 같습니다.

날짜 하나가 `Sept 3rd`로 들어오는 경우도 있습니다. 우리 코드가 연·월·일을 숫자로 받는다면, 이 값은 기대한 표기와 다릅니다. 원문에 연도까지 적혀 있다면 표기를 고칠 수 있습니다. 연도가 어디에도 없다면 이야기가 달라집니다.

## Claude가 다시 볼 자료 세 가지

후속 API 요청을 보낼 때는 이전 요청의 내용을 다시 담아야 합니다. “다시 해 보세요” 한 줄만으로는 Claude가 신청서를 다시 읽거나 잘못된 필드를 찾을 수 없습니다.

| 다음 요청에 담을 내용 | 알렉스의 반품 신청서에서 하는 역할 |
| --- | --- |
| 원본 문서 | 신청서에서 ‘주문일’과 ‘배송일’ 옆에 적힌 날짜를 다시 읽습니다. |
| 실패한 추출 결과 | 앞선 응답에서 어느 날짜를 어느 필드에 넣었는지 확인합니다. |
| 구체적인 검증 오류 | “배송일이 주문일보다 빠릅니다. 두 항목의 이름을 확인하고, 날짜는 연·월·일 순서로 적어 주세요”처럼 필드와 수정 기준을 짚습니다. |

이렇게 보내면 Claude가 날짜를 임의로 앞뒤만 바꾸는 대신 신청서의 항목 이름을 확인할 수 있습니다. 데이터가 없었던 것이 아니라 Claude가 갖고 있던 데이터를 잘못 적었을 뿐이므로, 피드백으로 고칠 수 있습니다. 재시도는 한두 번으로 제한합니다. [[25 실습 - 주문 번호를 검증하고 오류와 함께 다시 요청하기|25번 노트]]에서 최초 요청까지 합쳐 최대 세 번 시도한 이유입니다.

## 확인 메일이 첨부되지 않았다면

이번에는 주문 번호 칸이 비어 있고 고객이 “주문 번호는 주문 확인 메일에 있어요”라고만 적었습니다. ShopAssist가 받은 것은 반품 신청서 한 장입니다. 같은 신청서를 열 번 다시 읽어도 확인 메일의 주문 번호를 알아낼 수는 없습니다. 재시도는 매번 요청이 하나 더 늘어나므로, 성공할 수 없는 재시도는 비용만 낭비합니다. 오히려 값을 꼭 채우라고 요구하면 형식 검사까지 통과하는 가짜 번호가 생길 수 있습니다.

이때는 재시도를 멈추고 주문 번호를 `null`로 남깁니다. 해당 필드를 누락으로 표시한 뒤 ShopAssist가 알렉스에게 번호를 요청합니다. 저장 전에 검사가 실패하면 먼저 이렇게 물어보세요. **원문 어디에서 올바른 값을 확인할 수 있을까요?** 확인할 곳이 있다면 그곳을 다시 읽도록 오류를 돌려주고, 없다면 값을 아는 사람이나 자료에서 받아야 합니다.

다음 노트에서는 개별 필드를 검사해도 드러나지 않는 오류를 찾아보겠습니다.
