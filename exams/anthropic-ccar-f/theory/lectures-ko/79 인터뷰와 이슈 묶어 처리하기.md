# 79. 인터뷰와 이슈 묶어 처리하기

지난 노트에서는 예시와 테스트로 Claude Code가 데이터 마이그레이션을 제대로 하게 만들었습니다.

이번 노트에서는 다듬기 습관 두 가지를 더 봅니다.

| 습관 | 질문 |
| --- | --- |
| 인터뷰 | 작업을 시작하기 전에 누가 질문하나? |
| 이슈 묶기 | 메시지 하나에 문제를 몇 개 넣나? |

두 습관 모두 변경에 몇 라운드가 걸릴지를 정합니다. 그리고 고객이 쓰기 시작한 뒤 놀랄 일이 얼마나 생길지도 정합니다.

## 캐시가 조회를 빠르게 한다

ShopAssist는 대화마다 `lookup_order`를 여러 번 부릅니다. 바쁜 날에는 주문 서비스가 느리다고 가정합니다. 그래서 팀의 한 개발자가 캐시를 추가하려 합니다. **캐시**는 데이터를 필요로 하는 코드 가까이에 두는 단기 사본입니다. 다음 조회는 그 사본을 읽으므로 훨씬 빠릅니다. 그런데 이 개발자는 캐시를 만들어 본 적이 없습니다.

가장 중요한 원칙은 다음과 같습니다.

- **익숙하지 않은 분야에서는 코드를 쓰기 전에 Claude Code가 나에게 질문하게 합니다.**
- 나중에는 서로 영향을 주는 문제는 메시지 하나로 보내고, 독립적인 문제는 하나씩 고칩니다.

## 1. 인터뷰

개발자는 그냥 "lookup_order에 캐시를 추가해"라고 쓸 수 있습니다. Claude Code는 캐시를 만들 것입니다. 하지만 캐시의 어려운 부분은 그 요청에 들어 있지 않습니다.

그래서 개발자는 다르게 씁니다.

> 무엇이든 구현하기 전에, 이 변경에 대해 나를 인터뷰해 줘. 내가 생각하지 못했을 수도 있는 질문을 해 줘.

이것을 **인터뷰 패턴**이라고 합니다. Claude Code의 질문 중 세 가지는 이렇습니다.

| 주제 | 질문 |
| --- | --- |
| 신선도 | 주문은 언제 바뀌고, 사본은 얼마나 최신이어야 하나? |
| 무효화 | 환불이 처리되면 캐시된 주문을 바로 지워야 하나? |
| 장애 모드 | 캐시 자체가 다운되면 어떻게 해야 하나? |

두 번째 질문은 **캐시 무효화**에 관한 것입니다. 사본이 더는 사실이 아니어서 버려야 하는 시점을 정하는 일입니다. 개발자는 이것을 생각하지 못했습니다. 이것이 없으면, 고객이 환불을 받고 1분 뒤 다시 물었을 때 ShopAssist는 사본에서 옛 상태를 읽습니다.

세 번째 질문은 **장애 모드**, 즉 한 부분이 망가지는 방식에 관한 것입니다. 개발자의 답은 이렇습니다. 캐시가 다운되면 주문 서비스에서 직접 읽고, 대화는 절대 멈추지 않는다.

```text
ShopAssist → 캐시:        lookup_order ORD-1042
캐시 → ShopAssist:        delivered (옛 상태) ← 무효화가 없을 때
캐시 다운 → 주문 서비스에서 직접 읽기 → status: refunded
```

모르는 분야에서 질문을 건너뛰면 안 됩니다. 그러면 Claude Code가 빈틈마다 추측으로 채우고, 우리는 그 추측을 나중에, 고객보다 늦게 발견합니다. **답이 코드보다 먼저입니다.**

## 2. 메시지 하나에 문제 몇 개

캐시가 만들어졌고, 팀원의 리뷰에서 문제 다섯 개가 나왔습니다.

### 서로 영향을 주는 문제

그중 두 개는 서로 영향을 줍니다.

```python
def lookup_order(order_id, customer_id):
    key = order_id
    if key in cache:
        return cache[key]
    order = order_service.get(order_id)
    check_owner(order, customer_id)
    cache[key] = order
    return order
def on_refund(order_id):
    cache.pop(order_id, None)
```

- 캐시 키가 주문 ID만 씁니다. `lookup_order`는 고객 ID도 확인하므로, 한 고객이 다른 고객의 캐시된 주문을 받을 수 있습니다.
- 환불 코드도 같은 키로 캐시된 주문을 지웁니다. 그래서 키가 바뀌면 지우는 코드도 함께 바뀌어야 합니다.

이것이 **서로 영향을 주는 문제**입니다. 하나를 고치면 다른 하나가 바뀝니다.

그래서 두 문제를 자세한 메시지 하나에 넣습니다. 두 문제를 모두 적고, 어떻게 연결되는지 말합니다. 원하는 결과도 적습니다. 키에는 주문과 고객이 모두 들어가고, 환불은 정확히 그 키를 지운다.

두 문제를 하나씩 보내면 안 됩니다. 첫 라운드에서 Claude Code는 키를 고치고, 환불 코드는 옛 키를 지우는 채로 둘 것입니다.

```python
# Round 1: only the key is fixed
def lookup_order(order_id, customer_id):
    key = (order_id, customer_id)
    cache[key] = order
def on_refund(order_id):
    # still the old key
    cache.pop(order_id, None)
```

그러면 두 번째 라운드는 첫 라운드가 망가뜨린 것을 고쳐야 합니다.

### 독립적인 문제

나머지 세 문제는 독립적입니다.

- 로그 메시지에 오타가 있습니다.
- 테스트 파일에 import가 빠져 있습니다.
- 함수 하나의 서식이 틀렸습니다.

어느 수정도 다른 수정을 건드리지 않습니다. 그래서 작은 라운드로 하나씩 고칩니다. 변경마다 짧고, 다음 것을 보내기 전에 확인합니다. 무언가 실패하면 어느 수정 때문인지 압니다.

## 정리

- 익숙하지 않은 분야에서는 무엇이든 구현하기 전에 Claude Code에 나를 인터뷰해 달라고 합니다.
- 그 질문이 캐시 무효화나 장애 모드처럼 예상하지 못한 것을 드러냅니다.
- 수정이 서로 영향을 주면, 그 문제를 모두 자세한 메시지 하나에 적고 어떻게 연결되는지 말합니다.
- 문제가 독립적이면 하나씩 고치고 변경마다 확인합니다.

작업이 시작되기 전에는 Claude Code가 질문하게 하세요. 리뷰 후에는 서로 영향을 주는지에 따라 문제를 묶으세요. 다음 노트에서는 작업이 며칠에 걸칠 때, 세션을 이어 갈지 새로 시작할지 정하겠습니다.
