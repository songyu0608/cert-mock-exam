# 59. 에이전트별 도구 범위 정하기

지난 노트에서는 코디네이터가 Task 도구로 서브에이전트를 시작했습니다. 서브에이전트마다 에이전트 정의가 있었고, 그 안의 필드 하나는 비워 뒀습니다. 바로 도구(tools) 필드입니다.

```python
web_search = AgentDefinition(
    description="Finds sources on the web",
    prompt="You search the web and report sources.",
    tools=...,  # left open until now
)
synthesis = AgentDefinition(
    description="Combines the findings it receives",
    prompt="You combine findings into one answer.",
    tools=...,  # left open until now
)
```

이번 노트에서는 이 필드에 무엇을 넣을지 정합니다. 도구가 잘못된 에이전트는 잘못 고르고, 다른 에이전트의 몫인 일까지 하기 시작합니다.

## 모든 에이전트에게 모든 도구를 줬더니

스토어의 리서치 어시스턴트는 **램프는 왜 그렇게 자주 반품될까?**라는 질문 하나에 답합니다. 코디네이터와 서브에이전트 넷(웹 검색, 문서 분석, 종합, 보고서)이 있습니다. 첫 버전에서 팀은 빠르고 쉬운 방법을 택했습니다. 모든 서브에이전트에게 시스템의 모든 도구, 총 18개를 줬습니다.

그런데 로그를 읽어 보니, 받은 조사 결과를 합치기만 해야 하는 종합 서브에이전트가 직접 웹 검색을 하고 있습니다. 새로 찾은 결과는 코디네이터의 계획에 없는 것이고, 일부는 웹 검색 서브에이전트가 이미 찾은 내용을 반복합니다.

가장 중요한 원칙은 **각 에이전트에게는 역할에 필요한 도구만 준다**는 것입니다. 이번 노트에서는 도구의 수와 종류, 범용 도구 대신 좁은 도구, 역할을 넘나드는 작은 도구 하나를 차례로 봅니다.

## 1. 몇 개를, 어떤 도구를 줄까

에이전트는 행동할 때마다 자기 도구 설명을 모두 읽고 하나를 고릅니다. 도구가 네다섯 개면 고르기 쉽습니다. 18개면 비슷해 보이는 도구가 많아서 매번 고르기가 더 어렵습니다. 그래서 잘못된 도구를 더 자주 고릅니다. 이것이 첫 번째 문제입니다. **도구가 너무 많으면 도구 선택의 신뢰성이 떨어집니다.**

두 번째 문제는 로그에 나타난 그대로입니다. 에이전트는 자기 전문 분야 밖의 도구가 있으면 그것을 쓰는 경향이 있습니다. 종합 서브에이전트는 검색 도구가 보이니까 검색합니다. 하지만 검색은 다른 에이전트의 일입니다.

그래서 서브에이전트마다 역할에 맞게 도구를 제한합니다.

| 에이전트 | 도구 |
| --- | --- |
| 코디네이터 | 서브에이전트를 시작하는 Task |
| 웹 검색 | `search_web`, `load_document` |
| 문서 분석 | `read_tickets`, `read_reports` |
| 종합 | 검색 도구 없음 |
| 보고서 | `write_report` |

각 목록은 많아야 네다섯 개입니다. 이 숫자는 시험에 나오는 예시이지 엄격한 한도는 아닙니다. 규칙은 간단합니다. **역할에 필요한 도구만, 그 이상은 주지 않습니다.**

“혹시 모르니까” 18개 도구를 모든 에이전트에게 남겨 두면 안 됩니다. 도구가 하나 늘 때마다 모든 선택이 어려워지고, 역할 밖의 일을 부추깁니다.

## 2. 범용 도구 대신 좁은 도구

웹 검색 서브에이전트에는 `fetch_url`이라는 도구가 있었습니다. 어떤 웹 주소든 그 주소의 내용을 내려받습니다. 매우 범용적입니다. 서브에이전트는 아무 페이지나, 쇼핑 페이지나, 램프와 관련 없는 페이지를 열 수 있습니다.

그래서 이 도구를 `load_document`라는 **제약이 있는 도구**로 바꿉니다. 제약이 있는 도구는 한 가지 일만 하고, 받아들이는 입력을 제한합니다. `load_document`는 공급업체 보고서나 공개된 리뷰처럼 실제 문서를 가리키는 주소만 받습니다. 먼저 주소를 확인하고, 그 밖의 주소는 거절합니다.

```python
ALLOWED_HOSTS = {"reports.supplier.example", "reviews.example"}

def load_document(url: str) -> str:
    host = urlparse(url).hostname
    if host not in ALLOWED_HOSTS:
        # the check lives inside the tool
        raise ValueError("Not a real document address")
    return download(url)
```

확인 로직이 도구 안에 있으므로 호출할 때마다 실행됩니다. **무엇이든 할 수 있는 도구보다, 올바른 일만 할 수 있는 도구를 고르세요.**

## 3. 역할을 넘나드는 도구 하나

이제 종합 서브에이전트에는 검색 도구가 없습니다. 그런데 조사 결과를 합치다 보면 작은 사실을 확인해야 할 때가 많습니다. 공급업체 보고서의 날짜나 불량률 같은 것입니다. 그러면 종합 서브에이전트는 제어권을 코디네이터에게 돌려줍니다. 코디네이터가 웹 검색을 시작하고, 기다렸다가, 종합을 다시 시작합니다. 이 과정 때문에 보고서마다 왕복이 두세 번 늘고, 팀이 40% 더 오래 기다린다고 가정해 보겠습니다. 또 확인 100건 중 85건 정도는 날짜, 이름, 숫자 같은 단순한 확인이고, 나머지는 실제 조사가 필요하다고 가정합니다.

빨라 보이는 해결책이 하나 있습니다. 종합 서브에이전트에게 웹 검색 도구를 다시 모두 주는 것입니다. 그러면 두 문제가 모두 돌아옵니다. 종합 서브에이전트는 도구가 너무 많아지고, 혼자 리서치를 시작합니다.

**가장 좋은 선택**은 범위를 좁힌 도구 하나, `verify_fact`입니다. 주장 하나를 받아 출처와 대조합니다. 출처가 그 주장을 뒷받침하는지와, 어떤 출처를 썼는지를 돌려줍니다.

- 자주 나오는 단순한 확인은 종합 서브에이전트가 `verify_fact`로 처리합니다.
- 복잡한 확인은 여전히 코디네이터를 거쳐 웹 검색으로 보냅니다.

허브 앤 스포크 구조는 그대로입니다. 종합 서브에이전트는 자기의 좁은 도구를 호출할 뿐, 다른 에이전트와 직접 대화하지 않습니다.

한 가지 더 기억하세요. 도구 목록은 에이전트가 어떤 도구에 접근할 수 있는지를 정할 뿐, 단계의 순서를 정하지는 않습니다. 그리고 SDK는 이 목록을 코드로 강제합니다. 에이전트는 받지 않은 도구를 호출할 수 없습니다.

## 정리

- 각 에이전트에게 시스템의 모든 도구가 아니라 역할에 맞는 도구 네다섯 개를 줍니다.
- 도구가 너무 많으면 선택의 신뢰성이 떨어집니다.
- 역할 밖의 도구는 잘못 쓰입니다. 종합 서브에이전트가 웹 검색을 하는 것이 그 예입니다.
- 범용 도구는 제약이 있는 도구로 바꿉니다. `fetch_url` 대신 `load_document`를 씁니다.
- 자주 나오는 단순한 필요에는 다른 역할의 좁은 도구 하나를 더합니다. `verify_fact`가 그 예입니다. 복잡한 경우는 코디네이터를 거칩니다.

에이전트가 자기 일이 아닌 일을 하고 있다면, 먼저 그 에이전트의 도구 목록을 보세요. 다음 노트에서는 각 보조 에이전트가 시작할 때 무엇을 전달받는지 살펴보겠습니다.
