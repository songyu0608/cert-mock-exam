# 36. 실습: 주문 조회부터 반품 접수까지

“이 주문으로 산 재킷을 반품하고 싶어요.” 고객이 주문 번호와 함께 이렇게 적었습니다. 주문 조회 한 번으로 배송일은 알 수 있지만, 고객이 받으려는 것은 반품용 라벨입니다. 이번 노트에서는 ShopAssist가 주문을 조회한 뒤 반품을 접수하고 라벨 번호까지 안내하는 과정을 따라가 보겠습니다.

## 도구 이름으로 Python 함수 찾기

`agent_loop.py`를 만들고 이전 도구 호출 실습에서 쓴 클라이언트 설정과 모델 이름을 가져옵니다. 시스템 프롬프트에는 ShopAssist의 역할과 배송 후 30일 반품 규칙을 적습니다. 이번에는 주문 조회와 반품 접수에 도구를 쓰고 고객에게 짧게 답하라는 지침을 더합니다. 예시 주문 데이터는 20일 전에 배송된 재킷 한 건입니다.

`TOOLS` 목록에는 도구를 두 개 넣습니다. `lookup_order`는 주문 ID로 주문 내역을 조회합니다. 새 도구 `start_return`의 설명에는 배송이 완료됐고 30일 기한 안인 주문을 반품 접수할 때 쓰며, 반품 라벨 번호를 돌려준다고 적습니다. 두 도구 모두 주문 ID 하나를 필수 입력으로 받습니다.

이제 같은 이름의 Python 함수를 준비합니다. 실습의 `start_return`은 주문 ID와 예시 라벨 번호를 돌려줍니다. 실제 스토어라면 여기서 정책 조건을 검사하고 반품을 데이터베이스에 기록해야 합니다. `TOOL_FUNCTIONS`라는 딕셔너리에서 각 도구 이름을 해당 함수에 연결합니다. Claude를 호출하기 전에 이 딕셔너리에서 이름으로 함수를 찾아 같은 주문 ID로 한 번씩 실행해 보세요. 첫 함수에서는 배송된 재킷 주문이, 두 번째 함수에서는 라벨 번호가 나오면 연결된 것입니다. 확인용 호출 두 줄은 루프를 실행하기 전에 지웁니다.

## 첫 번째 응답에서 확인할 것

고객의 반품 요청과 주문 ID를 첫 `user` 메시지로 넣습니다. 라운드 수를 0에서 시작하고 `while True` 안에서 하나씩 늘립니다. 매번 모델, 시스템 프롬프트, 도구 목록, 지금까지의 대화 전체, 기존의 `effort` 설정을 API에 보냅니다. 이번 실습의 `max_tokens`는 500입니다. 응답이 오면 라운드 번호와 `stop_reason`을 출력합니다.

먼저 도구를 실행하는 부분을 비워 두고 한 라운드만 따라가 보세요. 종료 사유는 `tool_use`이고, 응답의 블록을 순회하면 고객의 주문 ID를 입력으로 받은 `lookup_order`가 나옵니다. 이때 터미널에 도구 이름을 출력하기만 했다면 Claude는 아직 재킷이 언제 배송됐는지 모릅니다. 다음 호출에 실제 주문 내역을 실어 보내야 합니다.

## 실행 결과를 대화에 넣어 다음 라운드 열기

다음은 루프에서 `tool_use`를 받았을 때 실행하는 부분입니다. `response`는 이번 API 응답이고 `messages`는 다음 호출에도 보낼 대화 목록입니다. 도구 함수는 이 예제에서 JSON으로 표현할 수 있는 딕셔너리를 반환합니다.

```python
messages.append({"role": "assistant", "content": response.content})
results = []
for block in response.content:
    if block.type == "tool_use":
        output = TOOL_FUNCTIONS[block.name](**block.input)
        results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": json.dumps(output, ensure_ascii=False),
        })
messages.append({"role": "user", "content": results})
```

`**block.input`은 Claude가 보낸 입력을 함수의 이름 있는 인자로 풀어 줍니다. 각 결과에는 원래 호출의 ID를 넣습니다. 한 응답에서 도구를 여러 개 요청할 수 있으므로, `user` 메시지는 블록을 모두 순회한 뒤 한 번만 추가합니다. 이제 루프가 다음 라운드를 시작하면 Claude도 앞선 결과를 읽을 수 있습니다.

원문의 짧은 실습 코드는 종료 사유가 `tool_use`가 아니면 반복을 빠져나옵니다. 이 예제에서 기대하는 값은 `end_turn`입니다. 실제 서비스에서는 [[35 에이전트 루프는 언제 멈출까|35번 노트]]처럼 다른 종료 사유도 구분하고, 정상 완료일 때 마지막 응답의 텍스트를 고객에게 보여 줍니다.

## 재킷 반품이 끝나는 세 라운드

1. **주문 조회.** Claude가 `lookup_order`를 요청합니다. 종료 사유는 `tool_use`입니다. 코드가 재킷이 20일 전에 배송됐다는 주문 내역을 돌려줍니다.
2. **반품 접수.** 주문이 30일 기한 안인 것을 확인한 Claude가 `start_return`을 요청합니다. 이번에도 `tool_use`입니다. 코드가 함수를 실행해 라벨 번호를 돌려줍니다.
3. **고객 안내.** Claude가 반품이 접수됐다고 알리고 라벨 번호를 안내합니다. 이번 종료 사유는 `end_turn`이므로 고객에게 답변을 보여 주고 반복을 마칩니다.

첫 번째 결과에 배송일이 있어야 Claude가 반품 접수를 선택할 수 있고, 두 번째 결과에 라벨 번호가 있어야 고객에게 그 번호를 안내할 수 있습니다. 각 라운드에서 어떤 정보를 받았고 다음 요청에 무엇을 돌려주는지 따라가면 루프가 필요한 이유가 보입니다. 두 도구를 실행한 것은 Claude가 아닙니다. Claude는 어떤 도구를 어떤 순서로 호출할지 정했고, 도구를 실행하고 `stop_reason`을 읽어 언제 멈출지 정한 것은 우리 루프입니다. 루프가 결과를 돌려보내지 않으면 Claude는 그 결과를 결코 볼 수 없습니다.
