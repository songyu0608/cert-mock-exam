# 41. 실습: 주문 조회와 반품 거절을 코드로 구분하기

이번 노트에서는 ShopAssist에 두 가지 요청을 보내 보겠습니다. 첫 번째 고객은 스토어에 없는 주문 번호를 줍니다. 두 번째 고객은 실제로 구입한 램프를 반품하고 싶어 합니다. 다만 배송받은 지 45일이 지났습니다. 두 고객 모두 반품 라벨을 받을 수 없지만, 한 사람에게는 주문 번호를 물어야 하고 다른 사람에게는 정책을 설명해야 합니다.

## 기존 루프로 두 요청을 보내 보기

[[36 실습 - 주문 조회부터 반품 접수까지|36번 노트]]의 루프를 `tool_errors.py`로 옮깁니다. 이번에는 시스템 프롬프트에 “반품 정책은 `start_return`이 검사합니다. 도구 결과를 바탕으로 한두 문장으로 답하세요”라고 적습니다. 주문 데이터에는 배송된 지 20일 된 재킷과 45일 된 램프를 둡니다.

한 가지 요청만 처리하던 루프는 `handle(customer_text)` 함수 안으로 옮깁니다. 함수가 시작할 때마다 전달받은 고객 문장으로 새 대화를 만듭니다. 매 라운드의 종료 사유를 확인하고, 도구를 실행하면 도구 이름과 반환값을 출력합니다. 실행 결과는 호출 ID에 맞춰 대화에 추가하고, 턴이 끝나면 `ShopAssist`라는 이름과 함께 최종 답변을 출력합니다. 파일을 직접 실행할 때만 `if __name__ == "__main__":` 아래에서 두 요청을 차례로 보냅니다.

도구 함수를 고치기 전의 결과부터 보세요. 없는 주문 번호를 주면 기존 `lookup_order`는 “주문을 찾지 못함”을 `error`에 담아 반환합니다. Claude는 번호를 다시 물으므로 겉으로는 잘 작동해 보입니다. 램프 쪽은 문제가 분명합니다. 기존 `start_return`에는 배송일을 확인하는 코드가 없어 45일 된 주문에도 라벨 번호가 나옵니다. 프롬프트에서 도구가 정책을 검사한다고 안내했으니, 이제 그 검사를 도구 안에 구현해야 합니다.

## 주문을 찾았는지, 반품을 허용하는지 차례로 확인하기

아래는 원문의 두 함수를 짧게 옮긴 예시입니다. `orders`는 주문 ID를 키로 쓰는 실습용 딕셔너리이고, 각 주문에는 배송 후 경과 일수인 `days_since_delivery`가 있습니다. 라벨 번호도 실습용 값입니다.

```python
def lookup_order(order_id):
    order = orders.get(order_id)
    if order is None:
        return {"found": False, "message": "이 번호와 일치하는 주문이 없습니다."}
    return {"found": True, "order": order}


def start_return(order_id):
    lookup = lookup_order(order_id)
    if not lookup["found"]:
        return lookup

    days = lookup["order"]["days_since_delivery"]
    if days > 30:
        return {
            "isError": True,
            "errorCategory": "business",
            "isRetryable": False,
            "customerMessage": "배송 후 30일이 지나 반품 기한을 넘겼습니다.",
            "developerMessage": f"반품 기한 30일, 배송 후 경과 일수 {days}일",
        }
    return {"order_id": order_id, "return_label": f"RET-{order_id}"}
```

먼저 `lookup_order`만 바꿔 보면, 고객에게 번호를 다시 묻는 답변은 같아도 그 근거가 달라집니다. `found: false`는 검색을 마쳤고 일치하는 주문이 없었다는 정상 결과입니다. 이어서 `start_return`도 바꾸면 라벨을 내기 **전에** 배송 후 경과 일수를 검사합니다. 30일째는 기한 안이고 31일째부터는 거절합니다. 원문의 짧은 실습은 반품을 요청한 주문이 존재한다고 가정합니다. 위 예시는 없는 번호가 반품 도구에 직접 들어와도 같은 조회 결과를 돌려줍니다.

## 실패 여부를 API의 도구 결과에도 표시하기

도구가 돌려준 딕셔너리는 우리 코드의 데이터입니다. Messages API로 결과를 보낼 때는 `tool_result` 블록에도 실패 여부를 표시합니다. 여기서 API 필드의 표기는 `is_error`입니다. 앞서 MCP 결과에서 본 `isError`와 철자가 다릅니다. 빈 조회 결과에는 실패 표시가 없으므로 `False`로 전달하고, 기한을 넘긴 램프에는 `True`로 전달합니다. [Anthropic 도구 결과 문서](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

원문 실습은 딕셔너리 전체를 보내므로 Claude가 개발자용 메시지까지 읽을 수 있습니다. [[40 고객에게 전할 말과 빈 조회 결과|40번 노트]]처럼 내부 설명을 스토어에만 남기려면, 다음과 같이 로그에 쓴 뒤 나머지 필드만 보냅니다. 이 코드는 `json`과 Python 로거 `logger`를 준비한 루프 안에서 실행합니다.

```python
public_result = output.copy()
detail = public_result.pop("developerMessage", None)
if detail is not None:
    logger.info("%s: %s", block.name, detail)

results.append({
    "type": "tool_result",
    "tool_use_id": block.id,
    "is_error": output.get("isError", False),
    "content": json.dumps(public_result, ensure_ascii=False),
})
```

두 요청을 다시 실행해 보세요. 없는 주문은 `found: false`로 돌아오고 ShopAssist는 고객에게 번호를 확인해 달라고 합니다. 램프 주문은 찾았지만 반품 도구가 `business`와 `isRetryable: false`를 돌려줍니다. 이번에는 라벨을 발급하지 않고 고객에게 30일 기한을 설명합니다. 두 경우 모두 루프는 고객에게 답할 수 있습니다. 어느 단계까지 성공했고 무엇 때문에 더 진행할 수 없는지가 도구 결과에 남아 있기 때문입니다.
