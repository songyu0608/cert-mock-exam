# 86. 개발 에이전트 사례: 코드 탐색

앞의 점검에서는 Claude Code 세션마다 개발자가 키보드 앞에 있었습니다.

이번 세 번째 점검은 시험의 **개발자 생산성 시나리오**를 씁니다. 이 시나리오에서는 Agent SDK로 만든 에이전트가 내장 도구로 코드를 탐색하고 바꿉니다.

| 결정 | 질문 |
| --- | --- |
| 큰 모듈 파악하기 | 컨텍스트가 바닥나지 않게 큰 레거시 모듈을 어떻게 파악할까? |
| 많은 파일 바꾸기 | 아무것도 깨뜨리지 않고 많은 파일을 어떻게 바꿀까? |

두 실패 모두 결과가 틀리게 돌아오기 전까지는 진전처럼 보입니다.

ShopAssist 팀은 자기 작업을 위해 이런 에이전트를 만들었습니다. Agent SDK 위의 프로그램입니다. 개발자의 과제를 받아, Read, Write, Edit, Bash, Grep, Glob으로 리포지토리를 읽고, 검색하고, 수정합니다. 첫 큰 작업은 오래된 결제(billing) 모듈입니다.

## 첫 번째 결정: 전부 읽으면 컨텍스트가 찬다

개발자가 에이전트에 청구서 합계가 어떻게 계산되는지 묻습니다. 결제 모듈에 파일이 약 300개 있다고 가정합니다. 에이전트는 파일을 하나씩 읽기 시작합니다. 약 80개를 읽자 컨텍스트가 거의 찹니다. 그러자 답이 일반론이 됩니다. 합계는 보통 서비스 레이어에서 계산된다고 말하고, 우리 코드의 클래스는 하나도 언급하지 않습니다. 첫 한 시간에는 실제 클래스를 찾았는데, 이제 답이 그 조사 결과와 맞지 않습니다.

**무엇이 필요할까요?** 여기서는 아무도 보장을 요구하지 않습니다. 컨텍스트가 차지 않게 하고, 조사 결과를 잃지 않게 하는 첫 단계가 필요합니다.

**그럴듯한 오답**은 두 가지입니다.

| 오답 | 실패하는 이유 |
| --- | --- |
| 300개 파일이 다 들어가도록 더 큰 컨텍스트 창 쓰기 | 텍스트가 늘면 중간만 길어지고, 놓치는 것은 바로 중간의 사실입니다. |
| 다시 묻고 "우리 코드에 대해 구체적으로"를 덧붙이기 | 초기 조사 결과는 같은 탐색 출력 아래 묻힌 채로 남습니다. |

**가장 좋은 선택**은 세 부분으로 이루어집니다.

1. **단계별로 탐색합니다.** Grep이 진입점을 찾고, Read가 한 번에 파일 하나씩 import를 따라갑니다. 결제 모듈 하나는 호출을 외부 라이브러리로 넘기기만 하므로 특별히 다룹니다. 에이전트는 그 모듈이 내보내는 이름을 모두 나열하고, 이름마다 검색합니다.
2. **조사 결과를 적어 둡니다.** 에이전트는 클래스 이름, 파일, 사실을 담은 스크래치패드 파일을 유지하고, 나중 질문에 답하기 전에 그 파일을 읽습니다. 단계가 끝날 때마다 다음 단계가 출발할 짧은 요약을 씁니다.
3. **탐색을 메인 컨텍스트 밖에 둡니다.** Explore 서브에이전트가 노이즈 많은 검색을 자기 컨텍스트에서 하고 짧은 요약을 돌려줍니다. 그래도 컨텍스트가 차면, 에이전트는 먼저 스크래치패드를 갱신하고 그다음 compact 커맨드를 실행합니다. 요약을 주입한 새 세션을 시작하는 방법도 있습니다.

> 제품 참고: Agent SDK는 Claude Code와 같은 엔진으로 동작하므로, Explore와 compact도 거기서 동작합니다.

**규칙**: 읽기 전에 검색하고, 조사 결과는 디스크에 두고, 노이즈는 서브에이전트가 떠안게 합니다.

## 두 번째 결정: 모든 핸들러가 요청 ID를 로그로 남긴다

분석이 끝났습니다. 이제 팀은 결제 모듈의 모든 이벤트 핸들러에 같은 보일러플레이트를 넣으려 합니다. **보일러플레이트**는 거의 바뀌지 않고 반복되는 코드입니다. **이벤트 핸들러**는 결제 제공자의 메시지를 받는 함수입니다. 각 핸들러는 첫 단계로 요청 ID를 로그로 남겨야 합니다.

```python
def handle_payment_failed(event):
    logger.info("request_id=%s", event.request_id)
    order = load_order(event.order_id)
    if order is None:
        return
    order.mark_payment_failed()
    notify_customer(order)
    save(order)
```

핸들러는 약 40개라고 가정합니다. 파일 이름은 모두 "handler"로 끝나고, 여러 폴더에 흩어져 있습니다.

**무엇이 필요할까요?** 아무것도 깨뜨리지 않는 빠짐없는 변경, 그리고 효과가 있었다는 증거입니다.

**그럴듯한 오답**은 두 가지입니다.

| 오답 | 실패하는 이유 |
| --- | --- |
| 에이전트가 핸들러 파일마다 Write로 다시 쓰기 | Write는 파일 전체를 바꾸므로, 제대로 옮겨 적지 않은 부분은 사라집니다. |
| Edit가 거부한 파일은 건너뛰고 나머지를 완료로 보고 | 변경이 빠짐없지 않고, 어떤 핸들러가 빠졌는지 아무도 모릅니다. |

**가장 좋은 선택**은 도구마다 자기 일을 맡기는 것입니다.

1. **Glob**이 모든 폴더에서 이름 패턴으로 파일을 찾습니다. 약 40개입니다.
2. 에이전트가 파일마다 **Edit**를 씁니다. 기준점은 핸들러의 첫 줄입니다. 기준점이 고유했던 약 37개 파일이 바뀝니다.
3. 파일 3개에는 첫 줄이 똑같은 핸들러가 두 개씩 있다고 가정합니다. 이 파일에서는 기준점이 고유하지 않으므로 Edit가 거부합니다. 이 경우 **시험의 답은 Read 후 Write**입니다. 파일 전체를 읽고, 두 곳을 모두 바꾸고, 다시 씁니다.
4. 마지막으로 **Bash**가 테스트를 실행합니다. 실패마다 입력, 기대 출력, 실제 출력을 에이전트에 돌려주고, 에이전트가 고친 뒤 다시 실행합니다.

> 제품 참고: 현재 제품은 더 긴 기준점이나 replace-all 옵션도 제공합니다(강의 슬라이드 기준).

**규칙**: Glob으로 이름으로 파일을 찾고, Edit로 바꿉니다. Read와 Write는 기준점이 고유하지 않을 때만 씁니다. 끝났는지는 테스트가 정합니다.

### 하나 더: 접근법마다 포크

팀에는 접근법이 두 가지 보일 수 있습니다. 핸들러마다 로그 한 줄을 넣는 것과, 모든 핸들러가 호출하는 공유 함수 하나를 두는 것입니다. 이 경우 접근법마다 한 번씩 세션을 포크해서, 둘 다 같은 분석에서 출발하게 합니다.

## 정리

- 에이전트가 흔한 패턴으로 흐를 때, 해결책은 더 큰 컨텍스트 창이 아닙니다.
- Grep이 진입점을 찾고, Read가 import를 따라가고, 결제 모듈이 내보내는 이름마다 따로 검색합니다.
- 스크래치패드 파일과 단계 요약이 조사 결과를 디스크에 둡니다.
- Explore, compact, 또는 요약을 넣은 새 세션이 노이즈를 메인 컨텍스트 밖에 둡니다.
- 일괄 변경에서는 Glob이 파일을 찾고 Edit가 하나씩 바꿉니다. Edit가 거부하면 Read와 Write가 대안입니다. Bash가 테스트를 실행합니다.

같은 규칙이 시험의 **리서치 시나리오**에서도 통합니다. 거기서 종합 에이전트는 컨텍스트 예산이 제한돼 있습니다. 검색 에이전트에게서 전체 페이지가 아니라 구조화된 핵심 사실을 받습니다.

코드에도 출처에도 규칙은 같습니다. 노이즈는 에이전트의 컨텍스트 밖에 두고, 조사 결과는 적어 두고, 끝났다고 하기 전에 모든 변경을 확인하세요.
