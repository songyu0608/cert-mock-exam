# 90. CI의 Claude Code: -p와 JSON

지난 노트에서는 큰 리뷰를 파일마다 한 패스, 그리고 통합 패스 하나로 나눴습니다. 이제 그 리뷰를 키보드 앞에 아무도 없는 CI에서 실행해야 합니다.

이번 노트에서는 Claude Code가 파이프라인 안에서 동작하게 만드는 명령줄 플래그를 살펴봅니다. CI 작업은 스스로 끝나야 하고, 그 출력은 스크립트가 읽을 수 있어야 하기 때문입니다.

| CI의 조건 | 의미 |
| --- | --- |
| 스스로 끝난다 | 입력하거나 클릭할 사람이 없습니다. |
| 스크립트가 읽을 수 있는 출력 | 사람을 위해 쓴 텍스트가 아닙니다. |

## 첫 CI 실행이 끝나지 않는다

팀의 리뷰 봇은 ShopAssist의 모든 풀 리퀘스트에서 실행되는 CI 작업입니다. 이제 팀은 Claude Code가 직접 리뷰하게 하려 합니다. Claude Code는 리포지토리 전체를 읽을 수 있기 때문입니다. 그래서 작업 스크립트가 프롬프트와 함께 Claude Code를 시작합니다. 이 풀 리퀘스트를 환불 로직, 에스컬레이션, 빠진 테스트 위주로 리뷰하라는 프롬프트입니다.

첫 실행은 끝나지 않습니다. Claude Code가 평소의 대화형 세션을 열고 누군가 입력하기를 기다립니다. 아무도 입력하지 않습니다. 한 시간 뒤 파이프라인이 작업을 멈춥니다.

가장 중요한 원칙은 **CI에서 Claude Code는 사람 없이 실행되고, 프로그램이 파싱할 수 있는 출력을 돌려줘야 한다**는 것입니다. 이를 가능하게 하는 것은 두 가지입니다. print 플래그, 그리고 스키마를 따르는 JSON 출력입니다.

## 1. print 플래그

짧은 형태는 `-p`, 긴 형태는 `--print`입니다. 이 플래그가 있으면 Claude Code는 프롬프트를 받아 작업하고, 결과를 표준 출력에 쓰고, 종료합니다. **표준 출력**은 파이프라인이 프로그램에서 받아 가는 텍스트 흐름입니다. 세션이 열린 채로 남지 않으므로, 아무것도 입력을 기다리지 않습니다.

```bash
claude -p "Review this pull request for refund logic, escalation and missing tests"
```

위 명령은 스크립트 설명에 맞춘 예시입니다.

기다림을 멈추는 다른 방법을 찾으면 안 됩니다. 그럴듯해 보이는 세 가지는 모두 틀렸습니다.

| 그럴듯한 오답 | 사실 |
| --- | --- |
| 대화형 세션을 끄는 특별한 환경 변수 | 존재하지 않습니다. |
| batch 플래그 | 존재하지 않습니다. |
| 명령에 빈 입력을 파이프로 넣기 | Unix 요령일 뿐, Claude Code를 실행하는 문서화된 방법이 아닙니다. |

**시험에서 정답은 `-p`입니다.**

## 2. 출력

이제 작업은 끝나지만, 리뷰를 자유 텍스트로 출력합니다. 어떤 실행은 목록을, 어떤 실행은 문단을 냅니다. 줄 번호가 매번 다른 곳에 있습니다. 하지만 스크립트는 지적 사항마다 풀 리퀘스트의 맞는 줄에 코멘트를 달아야 합니다. 자유 텍스트에서 그것을 읽어 내는 것은 불안정합니다.

그래서 플래그 두 개를 더합니다. 둘 다 `-p`와 함께 동작합니다.

| 플래그 | 효과 |
| --- | --- |
| `--output-format json` | Claude Code가 답을 실행에 관한 세부 정보와 함께 JSON으로 돌려줍니다. |
| `--json-schema` | 스키마를 넘기면, Claude Code가 그 스키마에 맞는 구조화된 출력을 돌려줍니다. |

우리 스키마는 지적 사항 목록을 정의합니다. 각 지적 사항에는 파일 경로, 줄 번호, 심각도, 분류, 메시지, 수정안이 있습니다.

```json
{ "type": "object",
  "required": ["findings"],
  "properties": { "findings": { "type": "array", "items": {
    "type": "object",
    "properties": {
      "file": {"type": "string"},  "line": {"type": "integer"},
      "severity": {"type": "string"},  "category": {"type": "string"},
      "message": {"type": "string"},  "fix": {"type": "string"}
    } } } } }
```

전체 명령은 이런 모양입니다. 아래는 예시이며, 스키마를 넘기는 정확한 방식은 원본 화면과 다를 수 있습니다.

```bash
claude -p "Review this pull request" \
  --output-format json \
  --json-schema "$(cat review-schema.json)"
```

이제 스크립트의 일은 단순합니다.

1. JSON을 읽고 지적 사항을 하나씩 훑습니다.
2. 지적 사항마다 코드 호스팅 사이트의 API를 호출합니다.
3. 메시지를 그 파일, 그 줄에 인라인 코멘트로 게시합니다.

아무도 손으로 옮겨 적을 필요가 없습니다.

### 스키마가 주는 것과 주지 않는 것

| | 내용 |
| --- | --- |
| 보장하는 것 | 형태. 모든 지적 사항이 파싱됩니다. |
| 보장하지 못하는 것 | 지적 사항이 맞는지. 줄 번호가 diff에 없는 줄을 가리킬 수도 있습니다. |

그래서 스크립트는 코멘트를 게시하기 전에 각 줄을 diff와 대조합니다.

## 정리

- 대화형 Claude Code는 사람을 기다리므로, `-p` 없는 CI 작업은 멈춥니다.
- `-p`(print)는 프롬프트를 실행하고, 결과를 쓰고, 종료합니다.
- `--output-format json`은 스크립트가 읽을 수 있는 JSON으로 답을 돌려줍니다.
- `--json-schema`는 그 JSON이 내 스키마를 따르게 합니다. 예를 들어 파일, 줄, 심각도, 수정안이 있는 지적 사항 목록입니다.
- 스크립트는 줄을 diff와 대조한 뒤, 지적 사항마다 인라인 코멘트로 게시합니다.

파이프라인에서는 항상 Claude Code를 `-p`로 실행하고, 스키마를 따르는 JSON을 요청하세요. 다음 노트에서는 각 CI 실행이 스스로는 볼 수 없는 프로젝트 컨텍스트를 줍니다.
