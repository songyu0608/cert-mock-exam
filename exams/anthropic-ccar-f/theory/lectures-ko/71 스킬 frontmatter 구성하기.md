# 71. 스킬 frontmatter 구성하기

지난 노트에서는 팀의 커맨드와 스킬을 어디에 둘지 정했습니다.

이번 노트에서는 스킬의 **frontmatter**를 살펴봅니다. SKILL.md 파일 맨 위에 있는 몇 가지 설정으로, 스킬이 실행되는 방식을 정합니다. 이 설정이 없는 스킬은 대화를 넘치게 만들거나, 해야 할 일보다 많은 일을 하거나, 필요한 입력 없이 시작할 수 있습니다.

## map-flow 스킬의 첫 주

ShopAssist 팀에는 `map-flow`라는 스킬이 있습니다. 리포지토리 skills 폴더에 있으므로 모든 개발자가 이 스킬을 가집니다. 환불 흐름처럼 ShopAssist의 한 부분을 지정하면, 스킬은 지원 케이스가 그 코드를 어떻게 지나가는지 추적합니다. 환불 금액을 확인하는 곳, 에스컬레이션이 일어나는 곳, 고객 메시지를 작성하는 곳을 찾아 보고합니다.

```markdown
---
name: map-flow
description: Maps how a support case moves through one part of ShopAssist
---
Trace the flow you are given.
Report where each step happens.
```

첫 주에 팀은 세 가지 문제를 발견합니다.

| 문제 | 내용 |
| --- | --- |
| 대화가 넘침 | 읽은 파일을 모두 채팅에 출력해서, 개발자의 대화가 검색 결과로 가득 찹니다. |
| 파일을 수정함 | 읽기만 해야 할 파일을 한 번 바꿨습니다. |
| 입력을 추측함 | 이름만 입력하고 뒤에 아무것도 없으면, 무엇을 그릴지 추측해서 리포지토리 전체를 훑습니다. |

가장 중요한 원칙은 **frontmatter가 스킬이 어디서 실행되는지, 무엇을 쓸 수 있는지, 시작하려면 무엇이 필요한지 정한다**는 것입니다.

## 전체 헤더

frontmatter는 SKILL.md 맨 위, 대시 세 개로 된 두 줄 사이의 짧은 헤더입니다. 경로별 규칙에서 본 것과 같은 종류의 헤더입니다. 모든 스킬은 여기에 이름(`name`)과 설명(`description`)을 둡니다. 여기에 키 세 개를 더하면 세 문제가 해결됩니다.

```markdown
---
name: map-flow
description: Maps how a support case moves through one part of ShopAssist
context: fork
allowed-tools: Read, Grep, Glob
argument-hint: "[flow to map: refund, escalation or a PR number]"
---
```

## 1. context: fork

`context: fork`가 없으면 스킬은 개발자의 대화 안에서 실행됩니다. 스킬이 읽은 파일과 검색 결과가 모두 그 대화에 남습니다. map-flow를 한 번 실행하면 메인 세션에 수십 개 파일의 탐색 결과가 쌓이고, 개발자의 실제 작업에 쓸 공간이 줄어듭니다.

`context`를 `fork`로 설정하면 Claude Code는 스킬을 **격리된 서브에이전트 컨텍스트**에서 실행합니다. 도우미 에이전트를 위한 별도 대화입니다. 도우미는 자기 공간에서 읽고, 검색하고, 탐색합니다. 끝나면 결과만 메인 세션으로 돌아옵니다. 여기서는 환불 흐름이 어디에 있고 어떤 테스트가 그것을 다루는지 정리한 짧은 지도입니다.

| | 메인 세션에 남는 것 |
| --- | --- |
| fork 없음 | 스킬이 읽은 모든 파일 |
| `context: fork` | 결과만 |

fork는 이럴 때 씁니다.

- 코드베이스 분석처럼 출력이 장황한 스킬
- 환불 코드를 재구성하는 방법 세 가지를 브레인스토밍하는 것 같은 탐색적인 작업. 메인 세션에는 과정의 모든 아이디어가 아니라 짧은 비교만 있으면 됩니다.

넘치는 출력을 스킬 지침에 "출력을 짧게 하라"를 넣어서 고치면 안 됩니다. 검색은 여전히 메인 대화에서 일어납니다. fork는 그 검색을 다른 곳으로 옮깁니다.

## 2. allowed-tools

map-flow는 읽고 검색하기만 해야 합니다. 시험에서는 `allowed-tools` 키가 **스킬이 실행되는 동안 쓸 수 있는 도구를 제한한다**고 봅니다. 그래서 도구 세 개를 나열합니다.

| 도구 | 하는 일 |
| --- | --- |
| Read | 파일을 엶 |
| Grep | 파일 안을 검색 |
| Glob | 이름으로 파일을 찾음 |

시험 기준으로, 이제 map-flow는 파일을 고치거나 명령을 실행할 수 없습니다. 시험에 나오는 예는 파일을 만드는 스킬입니다. 이 스킬은 파일 쓰기로만 제한되므로 폴더 삭제 같은 파괴적인 명령을 실행할 수 없습니다. 두 경우 모두 스킬은 자기 일에 필요한 도구만 받습니다.

| 경우 | 동작 |
| --- | --- |
| map-flow | Read, Grep, Glob만. 수정도 명령도 없음. |
| 파일 쓰기 전용 스킬 | 파일 쓰기만 하므로 폴더를 지울 수 없음. |
| 현재 제품 | 나열한 도구를 미리 승인함. 다른 도구를 막지는 않음. |

> 제품 참고: 현재 제품은 이 키를 다르게 해석합니다(위 표의 마지막 줄, 강의 슬라이드 기준). 시험에서는 allowed-tools가 스킬을 제한한다고 답합니다.

## 3. argument-hint

map-flow에는 ShopAssist의 어느 부분을 그릴지라는 입력 하나가 필요합니다. 포크된 스킬은 메인 대화의 기록 없이 시작합니다. 그래서 개발자가 무엇을 뜻했는지 채팅을 돌아보며 알아낼 수 없습니다.

`argument-hint`는 개발자에게 무엇을 넣어야 하는지 알려 주는 짧은 텍스트입니다. 여기서는 "그릴 흐름: 환불이나 에스컬레이션 같은 것, 또는 PR 번호"입니다. 개발자가 스킬 이름을 입력하면 Claude Code가 그 옆에 힌트를 보여 줍니다.

```text
/map-flow <the flow to map, such as refund or escalation, or a PR number>
```

그래서 인수 없이 스킬을 부르는 사람도 무엇이 빠졌는지 볼 수 있습니다. **힌트는 입력을 검사하지 않습니다.** 필요한 입력을 분명히 보여 줄 뿐입니다.

## trigger 필드는 없다

일부 튜토리얼은 Claude에게 스킬을 언제 시작할지 알려 주는 trigger 필드를 설명합니다. 그런 필드는 존재하지 않습니다. Claude는 **설명(description)을 보고** 스킬을 고릅니다. 그래서 스킬이 엉뚱한 때 시작하거나 전혀 시작하지 않으면, 설명을 다시 씁니다.

## 정리

- 스킬의 frontmatter는 SKILL.md 맨 위에 이름, 설명과 함께 있습니다.
- `context: fork`는 스킬을 격리된 서브에이전트에서 실행하므로, 장황한 출력과 탐색이 메인 세션에 들어오지 않습니다.
- `allowed-tools`는 시험 기준으로 스킬이 쓸 수 있는 도구를 제한합니다.
- `argument-hint`는 개발자에게 어떤 입력을 넣을지 알려 줍니다.
- trigger 필드는 없습니다. Claude는 설명을 보고 스킬을 고릅니다.

스킬이 대화를 넘치게 하거나, 일을 너무 많이 하거나, 입력 없이 시작한다면 frontmatter부터 고치세요. 다음 노트에서는 이 모든 것을 직접 설정해 보겠습니다.
