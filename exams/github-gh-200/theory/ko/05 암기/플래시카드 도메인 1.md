# 플래시카드 도메인 1　워크플로 작성과 관리

#flashcards/gh-200/d1

형식: `질문::답` (Spaced Repetition 플러그인). 플러그인이 없어도 한 줄씩 읽으면 된다.

## 개념 확인
pull_request 이벤트의 기본 활동 유형 3가지는?::opened, synchronize, reopened
외부 시스템이 REST API로 워크플로를 시작하게 하는 이벤트는?::repository_dispatch(event_type, client_payload)
GITHUB_TOKEN으로 만든 이벤트 중 새 실행을 만드는 예외 2가지는?::workflow_dispatch, repository_dispatch
schedule 이벤트는 어느 커밋에서 실행되나?::기본 브랜치의 최신 커밋
공개 리포지토리 예약 워크플로가 자동 비활성화되는 조건은?::60일간 리포지토리 활동 없음
workflow_dispatch 입력 유형 5가지는?::boolean, choice, number, environment, string
workflow_dispatch 최상위 입력 최대 개수는?::25개
재사용 워크플로를 만드는 트리거는?::on: workflow_call
재사용 워크플로 최대 중첩 단계는?::10단계
workflow_call 입력 유형 3가지는?::boolean, number, string
작업의 기본 timeout-minutes는?::360분
Linux 러너의 기본 run 셸은?::bash -e {0}
단계의 기본 상태 조건은?::success()
앞 작업 결과와 관계없이 항상 실행하려면?::if: always()
needs 대상이 실패해도 작업을 실행하려면?::if: always() (또는 failure() 등)
needs 컨텍스트로 읽을 수 있는 것은?::대상 작업의 outputs와 result
같은 그룹에서 진행 중인 실행까지 취소하려면?::cancel-in-progress: true
로그에서 값을 가리는 명령은?:::add-mask:값
pre·main·post 단계 사이에 상태를 넘기는 환경 파일은?::GITHUB_STATE
다음 단계에서 쓸 환경 변수를 설정하는 파일은?::GITHUB_ENV
env가 워크플로·작업·단계에 모두 있으면 무엇이 이기나?::단계(가장 구체적인 범위)
GitHub 호스팅 러너의 미리 설치된 도구 디렉터리 변수는?::RUNNER_TOOL_CACHE
컨테이너 작업에서 서비스 컨테이너 호스트 이름은?::서비스 라벨 이름
러너에서 직접 실행하는 작업은 서비스에 어떻게 접속하나?::localhost와 매핑한 포트
매트릭스 최대 작업 수는?::워크플로 실행당 256개
한 조합 실패 시 나머지를 계속하려면?::fail-fast: false
동시 실행 매트릭스 작업 수를 제한하는 키는?::max-parallel
windows-latest가 이전된 OS는?::Windows Server 2025(2025년 9월)
Ubuntu 20.04 대신 쓸 라벨은?::ubuntu-22.04 또는 ubuntu-24.04
YAML에서 내용을 표시하는 기호와 반복하는 기호는?::앵커 &, 별칭 *
github.ref와 github.ref_name의 차이는?::refs/heads/main 전체 vs main 짧은 이름
트리거 이벤트의 웹후크 페이로드를 담은 컨텍스트는?::github.event
식 안 문자열 리터럴은 어떤 따옴표?::작은따옴표
JSON 문자열을 객체로 바꾸는 함수는?::fromJSON
VS Code 확장이 참조 액션의 무엇을 읽어 자동 완성하나?::입력·출력(메타데이터)
미접근 캐시가 제거되는 기간은?::7일
리포지토리 기본 캐시 한도는?::10 GB
key가 없을 때 대신 찾는 키 목록은?::restore-keys
로그·아티팩트 기본 보존 기간은?::90일
아티팩트별 보존 기간을 정하는 upload-artifact 입력은?::retention-days
조직 캐시 보존 기본값과 최대값은?::7일, 365일
아티팩트·로그 기본 보존은?::90일
단계 출력을 설정하는 환경 파일은?::GITHUB_OUTPUT
다른 작업의 출력을 읽는 식은?::needs.<job_id>.outputs.<name>
작업 출력 한도는?::작업당 1 MB, 실행당 50 MB
작업 요약 Markdown을 쓰는 환경 파일은?::GITHUB_STEP_SUMMARY
단계당 요약 크기 한도는?::1 MiB
배지가 기본으로 보여 주는 브랜치는?::기본 브랜치
특정 브랜치 배지를 만드는 쿼리는?::?branch=브랜치이름
필수 검토자로 지정할 수 있는 최대 수는?::사용자·팀 합쳐 6개
대기 타이머 범위는?::1~43,200분(30일)
환경 비밀에 접근할 수 있는 시점은?::환경을 참조한 작업이 보호 규칙(승인)을 통과한 뒤

## 상황 → 판단
상황: PR이 열릴 때만 실행 → 정답은?::on: pull_request + types: [opened]
상황: docs 폴더만 바뀌면 건너뛰기 → 정답은?::paths-ignore 필터
상황: 외부 시스템이 API로 워크플로 시작 → 정답은?::repository_dispatch
상황: 매일 정해진 시각 실행 → 정답은?::schedule + cron(UTC)
상황: 버튼으로 실행하며 환경을 선택 → 정답은?::workflow_dispatch + environment/choice 입력
상황: 여러 리포가 같은 파이프라인을 호출 → 정답은?::재사용 워크플로(workflow_call)
상황: 호출한 워크플로에 비밀 전부 넘기기(같은 조직) → 정답은?::secrets: inherit
상황: 앞 작업 실패해도 정리 작업 실행 → 정답은?::needs + if: always()
상황: main 브랜치일 때만 배포 단계 → 정답은?::if: github.ref == 'refs/heads/main'
상황: 같은 브랜치 새 푸시 시 이전 실행 취소 → 정답은?::concurrency + cancel-in-progress: true
상황: 로그에 파일·줄 위치 경고 표시 → 정답은?:::warning file=…,line=…:
상황: 다음 단계에서 쓸 환경 변수 설정 → 정답은?::GITHUB_ENV 파일
상황: 테스트에 PostgreSQL 필요 → 정답은?::services: 서비스 컨테이너
상황: 3개 OS × 3개 Node 버전 테스트 → 정답은?::strategy.matrix
상황: 한 조합 실패해도 나머지 계속 → 정답은?::fail-fast: false
상황: 한 파일 안 반복 env 블록 줄이기 → 정답은?::YAML 앵커(&)·별칭(*)
상황: 브랜치 짧은 이름이 필요 → 정답은?::github.ref_name
상황: 워크플로 YAML을 편집기에서 검증·자동 완성 → 정답은?::GitHub Actions VS Code 확장
상황: 매번 패키지 설치가 느림 → 정답은?::actions/cache 또는 setup-* 캐시
상황: 빌드 결과를 배포 작업에서 사용 → 정답은?::upload-artifact → download-artifact
상황: 값 하나를 다른 작업으로 → 정답은?::GITHUB_OUTPUT → 작업 outputs → needs
상황: 테스트 결과 표를 실행 요약에 → 정답은?::GITHUB_STEP_SUMMARY
상황: README에 CI 상태 → 정답은?::상태 배지 badge.svg
상황: 프로덕션 배포 전 사람 승인 → 정답은?::환경 + 필수 검토자

## 목표 번호
목표 1.1의 내용은?::예약·수동·웹후크·리포지토리 이벤트로 워크플로가 실행되도록 구성한다
목표 1.2의 내용은?::워크플로 자동화에 맞는 범위, 권한, 이벤트를 고른다
목표 1.3의 내용은?::workflow_dispatch 입력(유형, 필수, 기본값)을 정의·검증하고, workflow_call의 입력·비밀 매핑으로 재사용 워크플로에 입력을 전달한다
목표 1.4의 내용은?::작업(job), 단계(step), 조건 논리를 사용한다
목표 1.5의 내용은?::작업 간 종속성을 구현한다
목표 1.6의 내용은?::워크플로 명령과 환경 변수를 사용한다
목표 1.7의 내용은?::종속 서비스(데이터베이스, 큐)에 서비스 컨테이너(services:)를 쓰고 포트, 상태 검사, 컨테이너 옵션을 구성한다
목표 1.8의 내용은?::strategy와 matrix로 작업 변형(OS, 언어·런타임 버전)을 만든다. include/exclude를 적용하고 fail-fast와 max-parallel을 제어하며, 비용·성능을 위해 매트릭스 크기를 최적화하고 러너 이미지 변경(Ubuntu 20.04 지원 중단, windows-latest의 Windows Server 2025 이전)을 고려한다
목표 1.9의 내용은?::YAML 앵커와 별칭(&, *, 병합 <<)으로 한 워크플로 파일 안의 반복되는 매핑·단계를 재사용한다
목표 1.10의 내용은?::미리 정의된 컨텍스트(github, runner, env, vars, secrets, inputs, matrix, needs, strategy, job, steps, github.event, github.ref)로 워크플로·리포지토리·런타임 메타데이터에 접근한다. 불변 액션(immutable actions)의 동작과 버전 고정 요구 사항을 이해한다
목표 1.11의 내용은?::컨텍스트를 참조하는 ${{ }} 식을 평가한다. 정적(워크플로 구문 분석 시) 평가와 런타임 평가를 구분하고, 로그와 식에서 비밀 유출을 막는다
목표 1.12의 내용은?::편집기 도구(GitHub Actions VS Code 확장, YAML 스키마 자동 완성, 메타데이터 IntelliSense, 유효성 검사)로 워크플로를 효율적으로 작성·유지한다
목표 1.13의 내용은?::캐싱과 아티팩트 관리를 구성하고, 조직·리포지토리 수준에서 REST API로 보존 정책(로그, 아티팩트, 워크플로 실행)을 적용한다
목표 1.14의 내용은?::작업과 단계 사이에 데이터를 전달한다(아티팩트, 출력, GITHUB_ENV·GITHUB_OUTPUT 환경 파일, 재사용 워크플로 출력)
목표 1.15의 내용은?::GITHUB_STEP_SUMMARY로 풍부한 Markdown 보고서(테스트 결과, 커버리지, 링크)를 담은 작업 요약을 만든다
목표 1.16의 내용은?::워크플로 상태 배지와 환경 보호를 추가한다
