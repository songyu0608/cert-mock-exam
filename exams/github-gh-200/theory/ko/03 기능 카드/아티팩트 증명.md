# 아티팩트 증명

> [!summary] 한 줄 정의
> 아티팩트 증명은 빌드 결과물이 어떤 리포·워크플로·커밋·이벤트에서 만들어졌는지 서명해 기록한 출처 증명이다. 배포 전 `gh attestation verify`로 검증한다.

**English** Artifact attestations and provenance

## 시험 트리거
- "배포하는 바이너리가 우리 CI에서 빌드된 것인지 확인"
- "SLSA 빌드 레벨 3"
- "컨테이너 이미지에 SBOM 증명"

## 핵심
- 생성: `actions/attest`(2026-11 문서 기준 @v4). 바이너리는 subject-path, 이미지는 subject-name + subject-digest + push-to-registry. SBOM은 sbom-path.
- 권한: id-token: write, contents: read, attestations: write(이미지 레지스트리 푸시는 packages: write 추가).
- 검증: `gh attestation verify 파일 -R 조직/리포`, 이미지는 `oci://...`. 검증해야 의미가 있다.
- 단독으로 SLSA v1.0 Build Level 2, 공유 재사용 워크플로에서 빌드하면 Level 3까지.
- Sigstore 사용: 공개 리포는 공개 투명성 로그, 비공개 리포는 GitHub의 Sigstore 인스턴스(투명성 로그 없음).
- 요금제: 공개 리포는 모든 요금제, 비공개·내부 리포는 GitHub Enterprise Cloud.
- 릴리스·배포 바이너리에 서명하고 잦은 테스트 빌드나 소스 파일 하나하나는 서명하지 않는다. 증명은 "안전하다"는 보장이 아니다.
- (참고) 학습 자료에 흔한 actions/attest-build-provenance 이름은 2026-11 how-to 문서에 나오지 않는다.

## 오답 함정
> [!warning] 오답이 되기 쉬운 선택지
> - 아티팩트 증명이 있으면 아티팩트가 안전하다는 선택지 → 출처·무결성만 증명
> - 비공개 리포에서 모든 요금제가 증명을 쓸 수 있다는 선택지 → Enterprise Cloud
