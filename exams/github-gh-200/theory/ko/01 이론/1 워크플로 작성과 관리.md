## 목표 1.1

**예약·수동·웹후크·리포지토리 이벤트로 워크플로가 실행되도록 구성한다**

> [!quote]- 공식 원문 (English / 한국어 공식 안내서)

>
> 예약, 수동, 웹후크 및 리포지토리 이벤트에 대해 실행되도록 워크플로 구성

push·pull_request 같은 리포지토리 이벤트, schedule(cron, UTC, 기본 브랜치 최신 커밋, 최소 5분), workflow_dispatch(수동), repository_dispatch(외부 웹후크)로 실행한다. types와 branches·paths 필터로 좁힌다.

## 목표 1.8

**strategy와 matrix로 작업 변형(OS, 언어·런타임 버전)을 만든다. include/exclude를 적용하고 fail-fast와 max-parallel을 제어하며, 비용·성능을 위해 매트릭스 크기를 최적화하고 러너 이미지 변경(Ubuntu 20.04 지원 중단, windows-latest의 Windows Server 2025 이전)을 고려한다**

> [!quote]- 공식 원문 (English / 한국어 공식 안내서)
> Use strategy and matrix to generate job variations (OS, language/runtime versions); apply include/exclude; control fail-fast and max-parallel; optimize matrix size for cost and performance; account for runner image changes (Ubuntu 20.04 deprecation, Windows Server 2025 migration for windows-latest)
>
> 전략 및 매트릭스를 사용하여 작업 변형(OS, 언어/런타임 버전)을 생성합니다. include/exclude를 적용합니다. 장애를 신속하게 처리하고 병렬 최대화를 제어합니다. 비용과 성능을 최적화하기 위해 매트릭스 크기를 조정합니다. 실행기 이미지 변경(Ubuntu 20.04 지원 중단, Windows-Latest에 대한 Windows Server 2025로의 마이그레이션)을 고려합니다.

matrix 조합마다 작업 하나(최대 256). include/exclude, fail-fast(기본 true), max-parallel. -latest 이미지 변경(Ubuntu 20.04 퇴역, windows-latest → Windows Server 2025)을 고려해 라벨을 고정한다.

## 요약
- GITHUB_TOKEN 이벤트는 새 실행 없음(dispatch 2종 예외).
- workflow_dispatch 입력 5종 vs workflow_call 입력 3종.
- 작업 if에 secrets 불가 · ! 시작 식은 ${{ }} 필수.
- 매트릭스 256 · fail-fast 기본 true.
- 캐시 7일·10 GB · 아티팩트·로그 90일.
- 작업 출력 1 MB/작업 · 50 MB/실행.

## 이 도메인의 카드
- [[워크플로 트리거와 이벤트]] — `on:`에 적은 이벤트(푸시, PR, 일정, 수동, 외부 웹후크 등)가 일어나면 워크플로가 실행된다. `types`와 브랜치·경로 필터로 범위를 좁힌다.
- [[예약 실행(schedule)]] — `on: schedule`에 POSIX cron 식을 적어 정해진 시각에 워크플로를 실행한다.
- [[수동 실행(workflow_dispatch)]] — `workflow_dispatch`를 넣으면 Actions 탭, GitHub CLI, REST API로 워크플로를 수동 실행하고 입력값을 넘길 수 있다.
- [[재사용 워크플로]] — `on: workflow_call`로 선언한 워크플로를 다른 워크플로의 작업(job) 수준에서 `uses:`로 호출해 파이프라인 전체를 재사용한다.
- [[작업과 단계 구조]] — 워크플로는 하나 이상의 작업(job)으로, 작업은 같은 러너에서 차례로 실행되는 단계(step)로 이루어진다. 단계는 `run`(셸 명령) 또는 `uses`(액션)다.
- [[조건 실행(if)]] — 작업이나 단계의 `if:`에 식을 적어 조건이 참일 때만 실행한다. 기본 조건은 `success()`다.
- [[작업 종속성(needs)]] — `needs:`에 다른 작업 ID를 적으면 그 작업이 성공한 뒤에 실행된다. 작업 실행 순서와 데이터 흐름을 만든다.
- [[동시성 제어(concurrency)]] — `concurrency.group`이 같은 실행·작업을 한 번에 하나만 돌게 하고, `cancel-in-progress`로 진행 중인 것을 취소할 수 있다.
- [[워크플로 명령]] — 단계나 액션이 표준 출력에 `::명령::` 형식의 줄을 쓰거나 환경 파일에 써서 러너에게 변수 설정, 주석, 마스킹 등을 지시한다.
- [[환경 변수와 환경 파일]] — `env:`(워크플로·작업·단계)로 변수를 정의하고, 실행 중 값은 `$GITHUB_ENV` 파일에 써서 다음 단계부터 쓴다. GitHub가 기본 변수(GITHUB_SHA 등)를 제공한다.
- [[서비스 컨테이너]] — `services:`로 작업에 데이터베이스·캐시 같은 Docker 컨테이너를 붙여 테스트한다. 작업마다 만들어지고 작업이 끝나면 제거된다.
- [[매트릭스 전략]] — `strategy.matrix`에 변수와 값 목록을 주면 모든 조합마다 작업이 하나씩 만들어진다(OS × 언어 버전 등).
- [[러너 이미지 변경]] — GitHub 호스팅 러너의 `-latest` 라벨이 가리키는 OS 이미지는 바뀐다. 오래된 이미지는 퇴역한다. 버전을 고정하거나 미리 대응해야 한다.
- [[YAML 앵커와 별칭]] — 한 워크플로 파일 안에서 `&이름`으로 표시한 내용을 `*이름`으로 다시 써서 반복되는 매핑·단계를 줄인다.
- [[컨텍스트]] — 컨텍스트는 실행·작업·단계·러너 정보를 담은 객체로, `${{ github.ref }}`처럼 식에서 읽는다.
- [[식과 평가 시점]] — `${{ }}` 안의 식은 리터럴, 컨텍스트, 연산자, 함수로 값을 계산한다. 러너에 보내기 전 GitHub가 평가해 그 결과를 문자열로 넣는다.
- [[GitHub Actions VS Code 확장]] — GitHub 공식 VS Code 확장으로 편집기 안에서 워크플로 작성(자동 완성·검증)과 실행 관리를 한다.
- [[의존성 캐싱]] — `actions/cache`(또는 setup-* 액션의 내장 캐시)로 패키지 등 의존성을 실행 간에 재사용해 시간을 줄인다.
- [[워크플로 아티팩트]] — 아티팩트는 실행이 만든 파일(빌드 결과, 테스트 보고서 등)이다. `actions/upload-artifact`로 올리고 `download-artifact`로 다른 작업에서 받는다.
- [[보존 정책]] — 로그·아티팩트·캐시를 얼마나 보관할지 정하는 설정이다. UI와 REST API로 리포지토리·조직·엔터프라이즈 수준에서 관리한다.
- [[작업 간 데이터 전달]] — 단계 간에는 GITHUB_OUTPUT·GITHUB_ENV, 작업 간에는 작업 출력(outputs)과 아티팩트, 재사용 워크플로와는 workflow_call 출력으로 데이터를 넘긴다.
- [[작업 요약(GITHUB_STEP_SUMMARY)]] — 단계가 `$GITHUB_STEP_SUMMARY` 파일에 Markdown을 쓰면 실행 요약 페이지에 표시된다. 테스트 결과·커버리지·링크 보고에 쓴다.
- [[상태 배지]] — 워크플로 상태 배지는 README 등에 워크플로 실행 성공·실패 상태를 이미지로 보여 준다.
- [[환경과 배포 보호 규칙]] — 환경(environment)은 배포 대상(production 등)을 나타내며, 보호 규칙(필수 검토자, 대기 타이머, 배포 브랜치 제한)과 전용 비밀·변수를 가진다.
