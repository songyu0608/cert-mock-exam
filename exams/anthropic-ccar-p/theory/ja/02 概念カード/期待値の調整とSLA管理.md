# 期待値の調整とSLA管理

> [!summary] 一行定義
> LLMの確率的な性質をステークホルダーと事前に共有し、測定可能な指標でSLAを合意し、フィードバックを定期的に反映する。

**English** Stakeholder feedback loops and expectation alignment (including SLAs)

## 試験のトリガー
- 「100%正確であるべきという要求」
- 「バッチ処理を24時間のSLAとして約束しようとしている」
- 「ユーザーの不満が改善に反映されない」

## 要点
- ハルシネーションは軽減手法を使っても完全にはなくせない（公式ドキュメント） → 無誤りを約束する代わりに、許容誤り率と人間のレビュー範囲を合意する。
- Message Batches APIの24時間は、処理が終わらなければ期限切れになる期限である。ほとんどは1時間以内に終わるが、需要によって遅くなることがある → 保証SLAとして使ってはいけない。
- 〔解釈〕SLAの候補：レイテンシ（p95）、可用性、スループット、評価指標に基づく品質。各指標の測定方法も併せて記す。
- 〔解釈〕フィードバックループ：ユーザーのフィードバック・モニタリング結果 → 評価セットに追加 → 改善 → ステークホルダーへの報告を定期的に回す。

## 誤答の落とし穴
> [!warning] 誤答になりやすい選択肢
> - バッチAPIの24時間を処理完了の保証として顧客に約束する選択肢 → 期限切れの期限であってSLAではない
> - 「ハルシネーション0%」を約束する選択肢 → 公式ドキュメント上、完全な除去は不可能
