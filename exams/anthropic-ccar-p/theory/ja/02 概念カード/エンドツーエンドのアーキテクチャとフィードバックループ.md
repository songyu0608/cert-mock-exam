# エンドツーエンドのアーキテクチャとフィードバックループ

> [!summary] 一行定義
> 入力 → 処理 → 出力にフィードバックループ（評価・モニタリング・ユーザーフィードバック）をつなぎ、運用結果が設計の改善に戻るようにする全体構造。

**English** End-to-end architecture (input → processing → output → feedback loops)

## 試験のトリガー
- 「リリース後に品質が落ちても気づけなかった」
- 「ユーザーフィードバックをどこに反映するか」
- 「入力から出力までの全体の流れを設計」

## 要点
- 入力：ユーザーのリクエスト、文書、ツールの結果。信頼できないコンテンツはこの段階で区別する → [[プロンプトインジェクション]]。
- 処理：プロンプト・検索・ツール呼び出し・ワークフロー/エージェント → [[ワークフローとエージェント型]]。
- 出力：形式の検証、ガードレール、必要に応じて人間のレビュー → [[ガードレールの多層化]] · [[ヒューマン・イン・ザ・ループ]]。
- フィードバックループ：エージェントは各ステップで環境から実際の結果（ツール呼び出しの結果、コードの実行結果）を得て進捗を判断すべきだと公式記事は説明する。
- 運用のフィードバック：トレーシング・評価・ユーザーフィードバックを集めてプロンプト・検索・モデルを再調整する → [[オブザーバビリティとモニタリング]]。
- 〔解釈〕ガイドはこの4段階を目標の文言として示すだけである。各段階の具体的な構成はAnthropicの公式記事に基づく解釈。

## 紛らわしい概念
| 概念 | 違い |
|---|---|
| [[ライフサイクルの各フェーズ]] | アーキテクチャのフィードバックループはシステム内部の流れ、ライフサイクルはプロジェクトの段階（ディスカバリー〜反復） |

## 誤答の落とし穴
> [!warning] フィードバックループを「ユーザー満足度アンケート」だけとみなす選択肢 → 自動評価・モニタリング・トレーシングが抜けていれば不完全
