# コンテキストウィンドウとトークン管理

> [!summary] 一行定義
> コンテキストウィンドウは、モデルが応答を生成するときに参照する作業記憶。大きいほど良いのではなく、何を入れるかを管理する必要がある。

**English** Context windows and token usage

## 試験のトリガー
- 「会話が長くなるにつれて精度が落ちる」
- 「リクエスト1件でどれだけトークンを使うか事前に知りたい」
- 「長い会話を続ける必要がある」

## 要点
- コンテキストに含まれるもの：システムプロンプト、すべてのメッセージ（ツールの結果・画像・文書）、ツール定義、そして生成される出力（思考を含む）。
- トークンが増えると精度と再現率が落ちる（context rot）。どれだけ入れるかと同じくらい、何を入れるかが重要。
- 応答のusageフィールドで使用量を確認し、送信前はトークンカウントAPIで見積もる。キャッシングを使うとinput_tokens・cache_read_input_tokens・cache_creation_input_tokensに分かれる。
- 長時間の会話やエージェントでは、サーバー側のコンパクションが基本戦略 → [[コンテキストの圧縮とメモリ]]。
- 2026-11のドキュメントでは主要な最新モデルは1Mトークンのウィンドウ、リクエストあたり最大128k出力トークン（変動情報）。

## 誤答の落とし穴
> [!warning] 「コンテキストウィンドウが大きいので関連文書をすべて入れる」→ context rotとコスト増。高シグナルな情報だけを選ぶ
