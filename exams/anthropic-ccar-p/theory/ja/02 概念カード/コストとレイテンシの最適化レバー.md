# コストとレイテンシの最適化レバー

> [!summary] 一行定義
> 品質を守りながらトークン・レイテンシ・コストを下げるレバー：キャッシング、バッチ、モデル・effortの調整、ルーティング、出力・コンテキストの縮小、ストリーミング。

**English** Optimizing token usage, latency and cost-performance

## 試験のトリガー
- 「月のAPIコストが予算を超えた」
- 「夜間の大量文書処理」
- 「応答が始まるのが遅い」

## 要点
- プロンプトキャッシング：繰り返しプレフィックスの再利用でコストとTTFTを同時に下げる → [[プロンプトキャッシング]]。
- Message Batches API：即時応答が不要な大量の作業を50%割引。キャッシングの割引と重ねられる → [[Message Batches API]]。
- モデル・effort：effortの調整がモデル切り替えより良いことが多い。ルーティングで簡単なリクエストを小さいモデルへ → [[ルーティング]]。
- トークンの削減：簡潔なプロンプト・出力、max_tokens、ツール応答のページネーション、ツール検索、プログラムによるツール呼び出し（−37%）。
- レイテンシ：ストリーミングは体感のレイテンシ（最初の出力まで）を下げる。まずベースラインの測定から。

## 誤答の落とし穴
> [!warning] 誤答になりやすい選択肢
> - リアルタイムのチャット応答にMessage Batches APIを使う選択肢 → バッチは非同期（大半は1時間以内、最大24時間）
> - 品質を確認せずに最小のモデルに切り替える選択肢 → サンプル2の誤答（B）
