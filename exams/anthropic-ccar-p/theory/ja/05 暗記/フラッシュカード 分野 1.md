# フラッシュカード 分野 1　ソリューション設計とアーキテクチャ

#flashcards/ccar-p/d1

形式：`質問::答え`（Spaced Repetitionプラグイン）。プラグインがなくても1行ずつ読めばよい。

## 概念の確認
良い成功基準の4つの性質（公式ドキュメント）は？::具体的、測定可能、達成可能、関連性
「応答品質が良いこと」を成功基準に直すと？::測定可能な数値と対象を決める。例：テストセットN件で正解率・F1いくつ以上
エンドツーエンドのアーキテクチャの4要素（ガイドの表記）は？::入力 → 処理 → 出力 → フィードバックループ
エージェントが進捗を判断する根拠として公式記事が強調するものは？::各ステップで環境から得る実際の結果（ツール呼び出しの結果・コードの実行結果など）
拡張LLMを作る3つの拡張は？::検索（retrieval）、ツール（tools）、メモリ（memory）
ワークフローとエージェントを分ける基準（公式の定義）は？::ワークフローは事前定義のコードパス、エージェントはLLMが自ら手順とツールの使い方を決める
エージェント型システムが性能を得る代償は？::レイテンシとコストの増加（エラー累積のリスクを含む）
プロンプトチェーンが向くタスクの条件は？::固定のサブタスクにきれいに分けられるタスク
チェーンのトレードオフは？::レイテンシを増やして精度を得る
ルーティングでコストを下げる公式の例は？::簡単でよくある質問を、より小さくコスト効率の良いモデルに送る
並列化の2つの変形は？::セクショニング（独立したサブタスクの並列実行）、投票（同じタスクの複数回実行）
並列化でガードレールを実装する際の公式記事の推奨は？::応答生成のインスタンスとは別のチェック用インスタンスを置く
オーケストレーター・ワーカーと並列化の核心的な違いは？::サブタスクが事前に決まっておらず、オーケストレーターが入力に応じて動的に決める
評価者・最適化者が効果的な2つの条件は？::明確な評価基準があり、反復的な改善が測定可能な価値をもたらすとき
マルチエージェントシステムのトークン使用量はチャットの約何倍（リサーチシステムの記事）？::約15倍（単一エージェントは約4倍）
マルチエージェントに向かないタスクの特徴は？::すべてのエージェントが同じコンテキストを共有する必要がある、またはエージェント間の依存が多いタスク
固定の分解と動的な分解の代表的なパターンは？::固定：プロンプトチェーン・セクショニング／動的：オーケストレーター・ワーカー・エージェント
ガイドが挙げるビジネス価値の柱5つは？::効率性、変革、生産性、コスト、パフォーマンスSLA

## 状況 → 判断
状況：成功基準なしに「AI導入」だけを求められる → 正解の方向は？::測定可能な成功基準から定める
状況：ステップが固定で予測可能である必要がある → 正解の方向は？::ワークフロー
状況：必要なステップ数を事前に予測できない → 正解の方向は？::エージェント
状況：単一の呼び出し＋検索＋例示で十分 → 正解の方向は？::エージェントを作らない（最も単純な解決策）
状況：固定のサブタスク＋途中のチェック → 正解の方向は？::プロンプトチェーン（ゲート）
状況：簡単な質問は小さいモデルで → 正解の方向は？::ルーティング
状況：応答の生成と不適切なコンテンツのチェック → 正解の方向は？::並列化（セクショニング）：別のインスタンス
状況：サブタスクを入力に応じて動的に → 正解の方向は？::オーケストレーター・ワーカー
状況：明確な基準＋反復改善の価値 → 正解の方向は？::評価者・最適化者
状況：広い並列探索、価値の高いタスク → 正解の方向は？::マルチエージェント（トークン約15倍を許容）
状況：依存関係の大きいコーディングをサブエージェントに分割 → 正解の方向は？::マルチエージェントは不適
