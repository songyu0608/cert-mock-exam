# フラッシュカード 分野 2　Claudeモデル、プロンプト作成、コンテキストエンジニアリング

#flashcards/ccar-p/d2

形式：`質問::答え`（Spaced Repetitionプラグイン）。プラグインがなくても1行ずつ読めばよい。

## 概念の確認
公式ドキュメントのモデル選択基準4つは？::能力、速度、コスト、effort
モデル選択で最も重要なステップ（公式ドキュメント）は？::自分のユースケースに合ったベンチマーク（評価セット）を作ること
一つのモデルの中で知能とレイテンシ・コストをトレードするパラメーターは？::effort
プロンプトの指示・文脈・例・入力を区別する公式の推奨方法は？::それぞれの内容をXMLタグで囲む
公式ドキュメントがClaudeをたとえた表現は？::規範や仕事の進め方を知らない優秀な新入社員
公式ドキュメントが推奨する例の数は？::3〜5個
良い例の3条件は？::関連性、多様性、構造化（<example>タグ）
思考（thinking）トークンはどう課金されるか？::出力トークンとして課金され、max_tokensとコンテキストウィンドウに含まれる
適応的思考で推論量を決める2つの要因は？::effortパラメーターとクエリの複雑さ
トークンが増えるほど精度・再現率が落ちる現象は？::context rot（コンテキストの劣化）
リクエスト送信前にトークン数を見積もる方法は？::トークンカウントAPI
コンテキストエンジニアリングの目標を一文で？::望む結果の可能性を最大化する、最小の高シグナルなトークンの集合を見つけること
ツールセットについて公式記事が挙げるよくある失敗は？::機能が重なるツールが多く、どのツールを使うかあいまいな肥大化したツールセット
長い文書と質問の推奨配置は？::長い文書を上部、質問を末尾
質問を末尾に置いたときの品質向上（公式テスト）は？::最大30%
長時間タスク向けのコンテキスト手法3つ（公式記事）は？::コンパクション、構造化されたメモ、サブエージェント
最も軽いコンパクションの形は？::古いツール結果の消去
プロンプトキャッシングが効果を出す配置の原則は？::静的な内容を前に、動的な内容を後ろに（プレフィックスの一致）
cache_controlのブレークポイントの最大数とデフォルトTTLは？::リクエストあたり4つ、デフォルト5分（オプションで1時間）
キャッシュのヒットを確認するusageのフィールドは？::cache_read_input_tokens
ガイドの目標2.5が挙げるプロンプト再利用戦略3つは？::キャッシング、モジュール型プロンプト、スキル
スキルの3段階の読み込みは？::メタデータ（常時、約100トークン） → SKILL.md（トリガー時、5k未満） → リソース（必要時）
descriptionに必ず含めるべき2つは？::何をするのか、いつ使うべきか

## 状況 → 判断
状況：どのモデルが合うか根拠が必要 → 正解の方向は？::ユースケース専用の評価セットで比較
状況：同じモデルでレイテンシ・コストを下げたい → 正解の方向は？::effortを下げる
状況：出力形式が毎回異なる → 正解の方向は？::few-shotの例3〜5個（<example>）
状況：複数ステップの推論の誤り → 正解の方向は？::思考の連鎖・thinking・effortを上げる
状況：長文ドキュメント＋質問 → 正解の方向は？::ドキュメントを上、質問を末尾（最大30%向上）
状況：同じ長いシステムプロンプトを毎回送信 → 正解の方向は？::静的な内容を先頭に＋プロンプトキャッシング
状況：キャッシュがヒットしない → 正解の方向は？::先頭の動的な値（タイムスタンプなど）を除去、最小長を確認
状況：長時間のエージェントがコンテキストの上限に → 正解の方向は？::コンパクション・ツール結果のクリア・ノート
状況：共通の手順を必要なときだけ読み込む → 正解の方向は？::Agent Skills
