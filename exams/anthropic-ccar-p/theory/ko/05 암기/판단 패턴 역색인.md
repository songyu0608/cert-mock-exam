# 판단 패턴 역색인

문제 속 상황에서 정답 방향을 거꾸로 찾는 표. 가운데 열을 가리고 말해 본다.

## 도메인 1　솔루션 설계와 아키텍처

| 문제 속 상황 | 정답 방향 | 노트 |
|---|---|---|
| 성공 기준 없이 "AI 도입"만 요구 | 측정 가능한 성공 기준부터 정한다 | [[비즈니스 문제 정의와 성공 기준]] |
| 단계가 고정되고 예측 가능해야 함 | 워크플로 | [[워크플로 vs 에이전트]] |
| 필요한 단계 수를 미리 알 수 없음 | 에이전트 | [[워크플로 vs 에이전트]] |
| 단일 호출 + 검색 + 예시로 충분 | 에이전트를 만들지 않는다(가장 단순한 해법) | [[워크플로 vs 에이전트]] |
| 고정 하위 작업 + 중간 검사 | 프롬프트 체이닝(게이트) | [[프롬프트 체이닝]] |
| 쉬운 질문은 작은 모델로 | 라우팅 | [[라우팅]] |
| 응답 생성과 부적절 콘텐츠 검사 | 병렬화(섹셔닝): 별도 인스턴스 | [[병렬화(섹셔닝·투표)]] |
| 하위 작업을 입력에 따라 동적으로 | 오케스트레이터-워커 | [[오케스트레이터-워커]] |
| 명확한 기준 + 반복 개선 가치 | 평가자-최적화자 | [[평가자-최적화자]] |
| 넓은 병렬 탐색, 가치 높은 작업 | 멀티 에이전트(토큰 약 15배 감수) | [[멀티 에이전트 도입 판단]] |
| 의존성 큰 코딩을 서브에이전트로 쪼갬 | 멀티 에이전트 부적합 | [[멀티 에이전트 도입 판단]] |

## 도메인 2　Claude 모델, 프롬프팅, 컨텍스트 엔지니어링

| 문제 속 상황 | 정답 방향 | 노트 |
|---|---|---|
| 어떤 모델이 맞는지 근거가 필요 | 사용 사례 전용 평가셋으로 비교 | [[모델 선택 트레이드오프]] |
| 같은 모델에서 지연·비용을 낮추고 싶다 | effort를 낮춘다 | [[모델 선택 트레이드오프]] |
| 출력 형식이 매번 달라짐 | 퓨샷 예시 3~5개(<example>) | [[퓨샷 프롬프팅]] |
| 여러 단계 추론 오류 | 사고의 연쇄·thinking·effort 상향 | [[사고의 연쇄와 확장 사고]] |
| 긴 문서 + 질문 | 문서 위, 질문 끝(최대 30% 향상) | [[긴 문서 배치 순서]] |
| 같은 긴 시스템 프롬프트를 매번 전송 | 정적 내용 앞 + 프롬프트 캐싱 | [[프롬프트 캐싱]] |
| 캐시가 적중하지 않음 | 앞쪽 동적 값(타임스탬프 등) 제거, 최소 길이 확인 | [[프롬프트 캐싱]] |
| 장시간 에이전트가 컨텍스트 한도 | 컴팩션·도구 결과 지우기·노트 | [[컨텍스트 압축과 메모리]] |
| 공통 절차를 필요할 때만 로드 | Agent Skills | [[Agent Skills]] |

## 도메인 3　통합

|---|---|---|

| API 엔드포인트별 도구가 많음 | 워크플로 단위 도구로 통합 | [[도구 설계 원칙]] |
| 에이전트가 서비스 계정 권한으로 전체 데이터 접근 | 인가를 도구·데이터 계층에서 강제 | [[인증과 인가의 공백]] |
| 정확도를 올리려 단계·추론 추가 | 지연 증가를 측정해 SLA와 비교 | [[정확도-지연 트레이드오프]] |
| 에이전트 실패 원인을 알 수 없음 | 전체 프로덕션 트레이싱 | [[관측 가능성과 모니터링]] |
| 실행 중 에이전트를 깨지 않고 배포 | 레인보 배포 | [[관측 가능성과 모니터링]] |
| 지식 베이스 200,000토큰 미만 | RAG 없이 전체 투입 + 캐싱 | [[RAG 파이프라인 설계]] |
| 청크가 원래 맥락을 잃음 | 컨텍스트 기반 검색(50~100토큰 설명) | [[컨텍스트 기반 검색]] |
| 정확한 오류 코드·ID 검색 | BM25 결합(하이브리드) | [[검색 전략과 하이브리드 검색]] |
| 여러 앱이 같은 사내 시스템 사용 | MCP | [[통합 메커니즘 선택(MCP·API·CLI·A2A)]] |
| 로컬 STDIO 서버를 API에 연결 | MCP 커넥터 불가(원격 HTTP만) | [[MCP 커넥터]] |
| 도구 정의가 수만 토큰 | 점진적 탐색(도구 검색·코드 실행) | [[점진적 탐색 vs 일괄 컨텍스트]] |
