# 플래시카드 도메인 2　Claude 모델, 프롬프팅, 컨텍스트 엔지니어링

#flashcards/ccar-p/d2

형식: `질문::답` (Spaced Repetition 플러그인). 플러그인이 없어도 한 줄씩 읽으면 된다.

## 개념 확인
공식 문서의 모델 선택 기준 4가지는?::능력, 속도, 비용, effort
모델 선택에서 가장 중요한 단계(공식 문서)는?::자기 사용 사례에 맞는 벤치마크(평가셋)를 만드는 것
한 모델 안에서 지능과 지연·비용을 맞바꾸는 파라미터는?::effort
프롬프트에서 지시·맥락·예시·입력을 구분하는 공식 권장 방법은?::각 내용을 XML 태그로 감싼다
공식 문서가 Claude를 비유한 표현은?::규범과 작업 방식을 모르는 유능한 신입 직원
공식 문서가 권장하는 예시 개수는?::3~5개
좋은 예시의 3조건은?::관련성, 다양성, 구조화(<example> 태그)
사고(thinking) 토큰은 어떻게 과금되나?::출력 토큰으로 과금되고, max_tokens와 컨텍스트 창에 포함된다
적응형 사고에서 추론량을 정하는 두 요인은?::effort 파라미터와 질의 복잡도
토큰이 늘수록 정확도·회상률이 떨어지는 현상은?::context rot(컨텍스트 열화)
요청을 보내기 전에 토큰 수를 추정하는 방법은?::토큰 카운팅 API
컨텍스트 엔지니어링의 목표를 한 문장으로?::원하는 결과 가능성을 최대화하는 가장 작은 고신호 토큰 집합을 찾는 것
도구 세트에서 공식 글이 꼽는 흔한 실패는?::기능이 겹치는 도구가 많아 어떤 도구를 쓸지 모호한 비대한 도구 세트
긴 문서와 질문의 권장 배치는?::긴 문서를 위쪽, 질문을 끝에
질문을 끝에 둘 때의 품질 향상(공식 테스트)은?::최대 30%
장시간 작업용 컨텍스트 기법 3가지(공식 글)는?::컴팩션, 구조화된 노트, 서브에이전트
가장 가벼운 컴팩션 형태는?::오래된 도구 결과 지우기
프롬프트 캐싱이 효과를 내는 배치 원칙은?::정적 내용을 앞에, 동적 내용을 뒤에(접두사 일치)
cache_control 중단점의 최대 개수와 기본 TTL은?::요청당 4개, 기본 5분(선택 1시간)
캐시 적중을 확인하는 usage 필드는?::cache_read_input_tokens
안내서 2.5가 든 프롬프트 재사용 전략 3가지는?::캐싱, 모듈형 프롬프트, 스킬
스킬의 3단계 로딩은?::메타데이터(항상, 약 100토큰) → SKILL.md(트리거 시, 5k 미만) → 리소스(필요 시)
description에 꼭 들어가야 하는 두 가지는?::무엇을 하는지, 언제 써야 하는지

## 상황 → 판단
상황: 어떤 모델이 맞는지 근거가 필요 → 정답 방향은?::사용 사례 전용 평가셋으로 비교
상황: 같은 모델에서 지연·비용을 낮추고 싶다 → 정답 방향은?::effort를 낮춘다
상황: 출력 형식이 매번 달라짐 → 정답 방향은?::퓨샷 예시 3~5개(<example>)
상황: 여러 단계 추론 오류 → 정답 방향은?::사고의 연쇄·thinking·effort 상향
상황: 긴 문서 + 질문 → 정답 방향은?::문서 위, 질문 끝(최대 30% 향상)
상황: 같은 긴 시스템 프롬프트를 매번 전송 → 정답 방향은?::정적 내용 앞 + 프롬프트 캐싱
상황: 캐시가 적중하지 않음 → 정답 방향은?::앞쪽 동적 값(타임스탬프 등) 제거, 최소 길이 확인
상황: 장시간 에이전트가 컨텍스트 한도 → 정답 방향은?::컴팩션·도구 결과 지우기·노트
상황: 공통 절차를 필요할 때만 로드 → 정답 방향은?::Agent Skills
