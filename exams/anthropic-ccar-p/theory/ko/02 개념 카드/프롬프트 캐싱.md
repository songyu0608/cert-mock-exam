# 프롬프트 캐싱

> [!summary] 한 줄 정의
> 요청마다 반복되는 접두사(prefix)를 캐시해 재사용하는 기능. 정적 내용을 앞에, 동적 내용을 뒤에 두어야 효과가 난다.

**日本語** プロンプトキャッシング　·　**English** Prompt caching

## 시험 트리거
- "매 요청마다 같은 긴 시스템 프롬프트·정책 문서를 보낸다"
- "지연과 비용을 함께 줄이고 싶다"
- "캐시 적중이 안 된다"

## 핵심
- 공식 샘플 2 정답: 정적 시스템 프롬프트·정책을 동적 내용 앞에 두고 프롬프트 캐싱을 켠다 → 첫 토큰까지 시간(TTFT)과 요청당 비용을 함께 줄인다.
- 캐시는 접두사 일치: 렌더링 순서는 tools → system → messages. 앞부분 1바이트만 달라도 그 뒤 캐시가 모두 무효가 된다.
- cache_control 중단점은 요청당 최대 4개. TTL은 기본 5분, 선택 1시간.
- 비용(대부분 모델 기준): 캐시 읽기 약 0.1배, 쓰기 1.25배(5분) 또는 2배(1시간). 모델에 따라 읽기 배율이 다르다(변동 정보).
- 최소 캐시 길이가 모델마다 있어 짧은 접두사는 오류 없이 캐시되지 않는다. usage의 cache_read_input_tokens로 적중을 확인한다.
- 타임스탬프·요청 ID 같은 동적 값이 앞쪽에 있거나, 세션 중 도구·모델을 바꾸면 캐시가 깨진다.

## 오답 함정
> [!warning] 오답이 되기 쉬운 선택지
> - 정책 문서를 앞 1,000토큰만 남기고 자른다 → 공식 샘플 2에서 오답(A). 필요한 정책이 사라진다
> - 시스템 프롬프트 맨 앞에 현재 시각을 넣는다 → 매 요청 접두사가 달라져 캐시가 적중하지 않는다
