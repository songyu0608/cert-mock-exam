# RAG 파이프라인 설계

> [!summary] 한 줄 정의
> 문서를 청크로 나눠 인덱싱하고, 질의 시 관련 청크를 검색해 프롬프트에 넣어 답하게 하는 구조. 검색 단계 품질이 답의 품질을 좌우한다.

**日本語** RAGパイプライン　·　**English** RAG pipeline design

## 시험 트리거
- "사내 문서 수천 건으로 답하는 챗봇"
- "문서 갱신 뒤 확신에 찬 오답이 나온다"
- "지식 베이스가 작다"

## 핵심
- 기본 흐름: 문서 수집 → 청킹(보통 수백 토큰 이하) → 임베딩·BM25 인덱스 → 검색 → (재랭킹) → 프롬프트에 넣어 생성.
- 지식 베이스가 200,000토큰(약 500쪽)보다 작으면 RAG 없이 전체를 프롬프트에 넣고 캐싱하는 편이 단순하다(Contextual Retrieval 글).
- 공식 샘플 3: 문서 갱신 뒤 모델·지연은 그대로인데 확신에 찬 오답 → 검색/인덱싱 단계가 무관하거나 오래된 청크를 반환하는지 먼저 본다(재인덱싱 실패, 임베딩 불일치).
- 〔해석〕 인덱싱 전략: 문서 갱신 시 재인덱싱 절차, 청크 메타데이터(출처·날짜), 같은 임베딩 모델 사용을 함께 관리한다.

> [!warning] 문서 갱신 직후 오답의 원인으로 모델 가중치 변경·temperature·컨텍스트 창 축소를 고르는 선택지 → 샘플 3 오답. 문서 갱신과 직접 연결되지 않는다
