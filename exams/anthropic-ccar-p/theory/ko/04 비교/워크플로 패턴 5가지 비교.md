# 워크플로 패턴 5가지 비교

| | [[프롬프트 체이닝]] | [[라우팅]] | [[병렬화(섹셔닝·투표)]] | [[오케스트레이터-워커]] | [[평가자-최적화자]] |
|---|---|---|---|---|---|
| 구조 | 고정 순서의 단계 | 분류 후 한 경로로 | 동시 실행 후 합침 | 중심 LLM이 동적 분배 | 생성 ↔ 평가 반복 |
| 하위 작업 | 미리 고정 | 범주별 고정 | 미리 고정 | 실행 중 결정 | 같은 작업 반복 |
| 맞는 상황 | 고정 하위 작업으로 나뉨 | 범주가 뚜렷하고 분류가 정확 | 속도(섹셔닝)·신뢰도(투표) | 하위 작업을 예측할 수 없음 | 명확한 기준 + 반복 개선 가치 |
| 공식 예 | 문구 작성 → 번역 | 쉬운 질문 → 작은 모델 | 응답과 별도 가드레일 검사 | 여러 파일 수정 코딩 | 문학 번역 |
| 대가 | 지연 증가 | 오분류 위험 | 호출 수 증가 | 비용·복잡도 | 반복만큼 지연·비용 |

**판별 순서**: ① 하위 작업이 미리 정해지나? → 아니면 오케스트레이터-워커 ② 입력 범주별로 처리가 다른가? → 라우팅 ③ 독립 작업을 동시에? → 병렬화 ④ 순차 단계? → 체이닝 ⑤ 평가 기준으로 반복 개선? → 평가자-최적화자

> [!question]- 요청마다 수정해야 할 파일 수와 종류가 다른 코딩 작업은?
> 오케스트레이터-워커. 하위 작업을 실행 중에 정해야 한다.

> [!question]- 사용자 응답을 만들면서 부적절한 요청인지도 확인해야 한다. 한 프롬프트에 둘 다 넣을까?
> 아니다. 병렬화(섹셔닝)로 별도 인스턴스가 검사하는 편이 낫다고 공식 글은 설명한다.
