# 도메인 3　통합

**English** Domain 3: Integration  
**日本語** 分野3：統合

도메인 3 (19%) · 목표 8개

Claude를 도구·데이터·다른 시스템과 연결하는 도메인으로 비중이 가장 크다(19%). 공식 샘플 1(필요 없는 도구 제거 = 최소 권한)이 이 도메인에 속한다.

## 목표 3.1

**도구·에이전트 구성을 기능 비대화 관점에서 평가한다**

> [!quote]- 공식 원문 (English / 日本語)
> Evaluate tool/agent configuration for capability bloat
>
> ツールやエージェントの構成を、機能の肥大化の観点から評価する

역할에 필요 없는 도구·권한은 제거한다. 도구가 많고 겹치면 선택 정확도도 떨어진다(30~50개 초과).

관련 카드: [[기능 비대화와 최소 권한]] · [[도구 설계 원칙]] · [[탐지 통제 vs 예방 통제]] · [[도구 검색 도구]] · [[프로그래밍 방식 도구 호출]]

## 목표 3.2

**인증·인가 요구사항을 분석해 보안 공백을 찾는다**

> [!quote]- 공식 원문 (English / 日本語)
> Analyze authentication and authorization requirements to identify security gaps
>
> 認証と認可の要件を分析し、セキュリティ上のギャップを特定する

에이전트가 누구의 권한으로 무엇을 할 수 있는지 확인하고, 인가는 도구·데이터 계층에서 기술적으로 강제한다.

관련 카드: [[기능 비대화와 최소 권한]] · [[인증과 인가의 공백]] · [[프롬프트 인젝션]] · [[MCP 커넥터]] · [[Claude Code 설정 우선순위]]

## 목표 3.3

**정확도-지연 트레이드오프를 평가하고 구성 결정의 근거를 제시한다**

> [!quote]- 공식 원문 (English / 日本語)
> Evaluate accuracy-latency trade-offs and justify configuration decisions
>
> 精度とレイテンシのトレードオフを評価し、構成に関する決定の根拠を示す

체이닝·thinking·큰 모델은 정확도를 올리고 지연을 늘린다. 기준선을 측정하고 SLA와 비교해 근거를 제시한다.

관련 카드: [[모델 선택 트레이드오프]] · [[사고의 연쇄와 확장 사고]] · [[프롬프트 캐싱]] · [[정확도-지연 트레이드오프]] · [[Message Batches API]]

## 목표 3.4

**관측 가능성 과제를 분석하고 대규모 모니터링 전략을 선택한다**

> [!quote]- 공식 원문 (English / 日本語)
> Analyze observability challenges and select monitoring strategies at scale
>
> オブザーバビリティの課題を分析し、大規模環境でのモニタリング戦略を選択する

비결정적 에이전트는 트레이싱 없이는 원인을 알 수 없다. 내용 대신 패턴을 보는 방식으로 개인정보도 지킨다.

관련 카드: [[관측 가능성과 모니터링]]

## 목표 3.5

**적절한 청킹·인덱싱 전략을 갖춘 RAG 파이프라인을 설계한다**

> [!quote]- 공식 원문 (English / 日本語)
> Design a RAG pipeline with appropriate chunking and indexing strategies
>
> 適切なチャンキング戦略とインデックス作成戦略を備えたRAGパイプラインを設計する

청크 크기·경계·겹침을 정하고, 맥락 손실은 컨텍스트 기반 검색으로 보완한다. 작은 지식 베이스는 RAG 없이 전체 투입 + 캐싱.

관련 카드: [[RAG 파이프라인 설계]] · [[청킹 전략]] · [[컨텍스트 기반 검색]]

## 목표 3.6

**데이터 모양과 질의 패턴에 맞는 검색 전략을 적용한다**

> [!quote]- 공식 원문 (English / 日本語)
> Apply retrieval strategies matched to data shape and query pattern
>
> データの形状とクエリパターンに合った検索戦略を適用する

의미 질의는 임베딩, 정확한 식별자는 BM25, 둘을 합쳐 재랭킹. 표·DB는 구조화 질의 도구가 맞다.

관련 카드: [[컨텍스트 기반 검색]] · [[검색 전략과 하이브리드 검색]]

## 목표 3.7

**연결 프로토콜을 평가하고 적절한 통합 메커니즘(MCP, API/CLI, 에이전트 간)을 선택한다**

> [!quote]- 공식 원문 (English / 日本語)
> Evaluate connection protocols and select the appropriate integration mechanism (MCP, API/CLI, agent-to-agent)
>
> 接続プロトコルを評価し、適切な統合メカニズム（MCP、API/CLI、エージェント間）を選択する

MCP는 재사용 가능한 표준 연결, API/CLI는 직접 제어, 에이전트 간은 위임. MCP 커넥터의 제약(도구 호출만, 원격 HTTP만)도 판단 요소.

관련 카드: [[통합 메커니즘 선택(MCP·API·CLI·A2A)]] · [[코드 실행과 MCP]] · [[MCP(모델 컨텍스트 프로토콜)]] · [[MCP 커넥터]] · [[헤드리스 모드(-p)]] · [[Claude Code MCP 범위]]

## 목표 3.8

**점진적 탐색과 일괄 컨텍스트 전략을 비교 평가한다**

> [!quote]- 공식 원문 (English / 日本語)
> Evaluate progressive discovery vs. monolithic context strategy
>
> 段階的ディスカバリーと一括型コンテキスト戦略を比較評価する

도구·지식이 크고 가변적이면 점진적 탐색(스킬, 도구 검색, 코드 실행), 작고 안정적이면 일괄 투입 + 캐싱.

## 이 도메인의 카드
- [[기능 비대화와 최소 권한]] — 역할에 필요 없는 도구·권한을 에이전트 구성에서 제거해 공격 표면 자체를 없앤다. 도구가 많을수록 선택 정확도도 떨어진다.
- [[도구 설계 원칙]] — 에이전트용 도구는 API를 그대로 감싸기보다 고효과 워크플로 단위로 적게 만들고, 이름·응답·오류를 에이전트가 쓰기 쉽게 설계한다.
- [[인증과 인가의 공백]] — 누가 요청하는지(인증)와 무엇을 할 수 있는지(인가)를 에이전트·도구·데이터 경계마다 확인해, 에이전트가 사용자 권한보다 넓게 행동하는 공백을 찾는다.
- [[정확도-지연 트레이드오프]] — 더 큰 모델·더 많은 추론·더 많은 단계는 정확도를 올리지만 지연을 늘린다. 요구 지연을 측정한 뒤 근거를 들어 구성을 정한다.
- [[관측 가능성과 모니터링]] — LLM 시스템은 같은 입력에도 결과가 달라지고 실패 원인이 여러 층에 있다. 트레이싱·지표·평가를 조합해 원인을 찾을 수 있게 만든다.
- [[RAG 파이프라인 설계]] — 문서를 청크로 나눠 인덱싱하고, 질의 시 관련 청크를 검색해 프롬프트에 넣어 답하게 하는 구조. 검색 단계 품질이 답의 품질을 좌우한다.
- [[청킹 전략]] — 문서를 검색 단위(청크)로 나누는 방법. 크기·경계·겹침에 따라 검색 품질이 달라지고, 청크가 원래 맥락을 잃는 문제가 있다.
- [[컨텍스트 기반 검색]] — 각 청크 앞에 문서 전체를 참고한 짧은 맥락 설명을 붙인 뒤 임베딩과 BM25 인덱스를 만드는 Anthropic의 RAG 개선 기법.
- [[검색 전략과 하이브리드 검색]] — 질의 패턴과 데이터 모양에 맞춰 의미 검색(임베딩)·정확 일치 검색(BM25)·구조화 질의·재랭킹을 조합한다.
- [[통합 메커니즘 선택(MCP·API·CLI·A2A)]] — 외부 시스템을 Claude에 연결할 때 재사용·표준화(MCP), 직접 제어(API/CLI 도구), 에이전트 간 위임(A2A) 중 요구에 맞는 것을 고른다.
- [[점진적 탐색 vs 일괄 컨텍스트]] — 필요한 정보·도구를 실행 중에 찾아 불러오는 점진적 탐색과, 처음부터 모두 컨텍스트에 넣는 일괄 방식 중 데이터 크기·변동성·지연 요구로 고른다.
- [[도구 검색 도구]] — 수백~수천 개 도구 정의를 미리 다 싣지 않고, Claude가 필요한 도구만 검색해 불러오게 하는 기능.
- [[프로그래밍 방식 도구 호출]] — Claude가 도구를 하나씩 호출해 결과를 컨텍스트로 받는 대신, 코드 실행 환경에서 코드로 여러 도구를 조율하고 최종 결과만 받는 방식.
- [[코드 실행과 MCP]] — MCP 도구를 코드 API(파일)로 노출하고, 에이전트가 파일 시스템을 탐색해 필요한 도구 정의만 읽고 코드로 호출하는 방식.
- [[MCP(모델 컨텍스트 프로토콜)]] — AI 에이전트를 외부 시스템(도구·데이터)에 연결하는 오픈 표준. 한 번 구현하면 여러 서버·클라이언트와 연결된다.
- [[MCP 커넥터]] — MCP 클라이언트를 직접 구현하지 않고 Messages API 요청에서 원격 MCP 서버에 연결하는 베타 기능.
