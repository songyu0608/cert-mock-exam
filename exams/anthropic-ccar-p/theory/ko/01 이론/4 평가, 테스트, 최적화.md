# 도메인 4　평가, 테스트, 최적화

**English** Domain 4: Evaluation, Testing & Optimization  
**日本語** 分野4：評価、テスト、最適化

도메인 4 (16%) · 목표 6개

평가와 최적화 도메인이다. 공식 샘플 3(문서 갱신 뒤 오답 → 검색/인덱싱 먼저 조사)이 이 도메인에 속한다.

## 목표 4.1

**평가 지표(정확도, 지연, 비용, 안전성, 보안)를 정의한다**

> [!quote]- 공식 원문 (English / 日本語)
> Define evaluation metrics (accuracy, latency, cost, safety, security)
>
> 評価指標（精度、レイテンシ、コスト、安全性、セキュリティ）を定義する

정확도·지연·비용·안전성·보안 다섯 축을 측정 방법과 목표값으로 정한다.

관련 카드: [[비즈니스 문제 정의와 성공 기준]] · [[평가 지표 정의]]

## 목표 4.2

**혼합 방법론으로 평가 데이터셋과 테스트 프레임워크를 설계한다**

> [!quote]- 공식 원문 (English / 日本語)
> Design evaluation datasets and test frameworks using mixed methodologies
>
> 複数の方法論を組み合わせて、評価データセットとテストフレームワークを設計する

실제 분포 + 엣지 케이스로 평가셋을 만들고, 코드·LLM·사람 채점을 섞는다. 소수 케이스로 바로 시작한다.

관련 카드: [[평가 데이터셋 설계]] · [[채점 방식(코드·LLM·사람)]]

## 목표 4.3

**A/B 테스트와 반복 개선을 수행한다**

> [!quote]- 공식 원문 (English / 日本語)
> Conduct A/B testing and iterative improvements
>
> A/Bテストと反復的な改善を実施する

같은 평가셋으로 한 번에 한 변수만 바꿔 비교하고, 운영에서는 일부 트래픽으로 검증한다.

관련 카드: [[평가자-최적화자]] · [[A-B 테스트와 반복 개선]]

## 목표 4.4

**시스템 문제(프롬프트 실패, 할루시네이션, 모델 부적합)를 진단한다**

> [!quote]- 공식 원문 (English / 日本語)
> Diagnose system issues (prompt failure, hallucinations, model mismatch)
>
> システムの問題（プロンプトの失敗、ハルシネーション、モデルの不適合）を診断する

무엇이 바뀌었는지와 증상을 연결해 원인 층(프롬프트·검색·모델·도구)을 좁힌다.

관련 카드: [[모델 선택 트레이드오프]] · [[RAG 파이프라인 설계]] · [[시스템 문제 진단]] · [[할루시네이션 완화]] · [[디버깅과 운영 문제 해결 지원]] · [[인용(Citations)]]

## 목표 4.5

**토큰 사용량, 지연, 비용-성능 트레이드오프를 최적화한다**

> [!quote]- 공식 원문 (English / 日本語)
> Optimize token usage, latency, and cost-performance trade-offs
>
> トークン使用量、レイテンシ、コストとパフォーマンスのトレードオフを最適化する

캐싱, 배치(50%), effort·모델·라우팅, 출력·도구 응답 축소, 스트리밍으로 품질을 지키며 줄인다.

관련 카드: [[라우팅]] · [[컨텍스트 윈도우와 토큰 관리]] · [[프롬프트 캐싱]] · [[도구 설계 원칙]] · [[정확도-지연 트레이드오프]] · [[비용·지연 최적화 레버]] · [[Message Batches API]] · [[프로그래밍 방식 도구 호출]]

## 목표 4.6

**로깅·관측 가능성 도구로 시스템 성능을 모니터링한다**

> [!quote]- 공식 원문 (English / 日本語)
> Monitor system performance using logging and observability tools
>
> ロギングツールとオブザーバビリティツールを使用してシステムのパフォーマンスをモニタリングする

usage 토큰·지연·오류·비용·평가 점수를 수집하고 트레이싱으로 원인을 추적한다.

관련 카드: [[관측 가능성과 모니터링]]

## 요약
- 평가 설계 3원칙: 과제 특화, 자동화, 질보다 양
- 채점: 코드(빠름·신뢰) > LLM(신뢰성 검증 후) > 사람(가능하면 회피)
- 문서 갱신 뒤 오답 → 검색/인덱싱(샘플 3)
- [[공식 샘플 문제 3문항]]

## 이 도메인의 카드
- [[평가 지표 정의]] — 정확도·지연·비용·안전성·보안(안내서의 5개 축)을 사용 사례에 맞는 측정 방법과 목표값으로 정한다.
- [[평가 데이터셋 설계]] — 실제 과제 분포와 엣지 케이스를 담은 평가셋을 만들고, 자동 채점·LLM 채점·사람 검토를 섞어(혼합 방법론) 테스트한다.
- [[채점 방식(코드·LLM·사람)]] — 평가 채점은 가장 빠르고 신뢰할 수 있고 확장 가능한 방법을 고른다. 코드 채점 → LLM 채점 → 사람 채점 순으로 검토한다.
- [[A-B 테스트와 반복 개선]] — 프롬프트·모델·검색 설정 변경을 같은 평가셋과 실제 트래픽에서 비교해, 측정된 근거로 채택하고 반복한다.
- [[시스템 문제 진단]] — 증상과 무엇이 바뀌었는지를 근거로 원인 층(프롬프트·검색·모델·도구·데이터)을 좁힌다.
- [[할루시네이션 완화]] — 근거 없는 내용을 사실처럼 만드는 현상을 "모른다" 허용, 직접 인용, 인용 검증 등으로 줄인다. 완전히 없앨 수는 없다.
- [[비용·지연 최적화 레버]] — 품질을 지키며 토큰·지연·비용을 줄이는 레버: 캐싱, 배치, 모델·effort 조정, 라우팅, 출력·컨텍스트 축소, 스트리밍.
- [[Message Batches API]] — 즉시 응답이 필요 없는 대량 요청을 비동기로 처리하고 모든 토큰을 50% 할인받는 API.
- [[인용(Citations)]] — 문서를 근거로 답할 때 각 주장을 뒷받침하는 원문 구절을 응답에 함께 반환하는 API 기능.
