## 1. 파운데이션 모델(FM)
- 방대한 데이터로 미리 훈련한 거대한 트랜스포머 모델. 미세 조정하거나 새 앱에 그대로 적용
- 대표 FM: GPT, DALL-E(OpenAI), Claude(Anthropic), BERT(Google), Llama, Segment Anything(Meta)
- 강의에 나온 Bedrock 모델: Jurassic-2(AI21, 다국어), Claude(대화·Q&A), Stable Diffusion(이미지), Llama, **Amazon Titan**(요약·생성·Q&A·**임베딩**)
- 모델 목록은 계속 바뀐다 (Amazon Nova, Mistral, Cohere 등)

## 2. FM을 쓰는 두 가지 길
| | [[SageMaker JumpStart]] | [[Amazon Bedrock]] |
|---|---|---|
| 방식 | Studio에서 모델이 로드된 노트북을 열어 시작 | 생성형 AI FM을 위한 **API** |
| 모델 | Hugging Face(Falcon, Flan, BloomZ, GPT-J), Stable Diffusion, Alexa 다국어 LLM | 사전 구축 모델, 미세 조정한 모델, 가져온 모델. 타사 모델도 AWS로 청구 |
| 인프라 | 모델을 **직접 배포·관리**(제어 가능) | **서버리스**, 관리 없음 |

> [!tip] 시험 포인트
> "인프라 관리 없이 API로 여러 FM 사용" → **Amazon Bedrock**

## 3. Bedrock API, 모델 액세스, 플레이그라운드
| 엔드포인트 | 역할 | 대표 API |
|---|---|---|
| bedrock | 모델 관리·배포·훈련 | |
| bedrock-runtime | 모델 추론 | Converse, ConverseStream, InvokeModel, InvokeModelWithResponseStream |
| bedrock-agent | 에이전트·지식 기반 관리 | |

- 플레이그라운드(채팅·텍스트·이미지)에서 직접 시험, 사용자 지정·가져온 모델 평가에도 유용

## 4. 모델 맞춤화 4가지 → [[비교 - 모델 맞춤화 4가지]]
| 방법 | 가중치 변경 | 필요한 데이터 | 비용 | 이럴 때 |
|---|---|---|---|---|
| **프롬프트 엔지니어링** | 없음 | 예시 몇 개 | 가장 낮음 | 빠르게 품질 개선 |
| **RAG** | 없음 | 외부 문서·DB | 낮음~중간 | 최신·사내 정보, 환각 감소 |
| **미세 조정** | 있음 | **레이블 있는** 프롬프트-응답 쌍 | 높음 | 특정 작업·말투·도메인 |
| **지속적인 사전 훈련** | 있음 | **레이블 없는** 대량 텍스트 | 가장 높음 | 도메인 지식 자체를 주입 |

> [!tip] 시험 포인트
> - 최신 정보를 자주 반영, 재훈련 없이 → **RAG**
> - 레이블 있는 데이터로 특정 작업 성능 향상 → **미세 조정**
> - 레이블 없는 사내 문서로 도메인 적응 → **지속적인 사전 훈련**

### 미세 조정 (Fine-tuning)
- 기존 LLM을 내 데이터로 추가 훈련 → 긴 프롬프트가 필요 없어져 **장기적으로 토큰 절약**
- 미세 조정한 모델도 다른 모델처럼 쓰고, 다시 미세 조정 가능
- 용도: 특정 성격·말투의 챗봇, 훈련 시점 이후의 최신 데이터, 독점 데이터(과거 이메일, 지원 기록), 특정 작업(분류, 사실 판단)

### Bedrock 사용자 지정 모델
- **미세 조정**: 강의 기준 Titan, Cohere, Meta 모델. 텍스트는 prompt-completion 쌍을 S3에, 이미지는 S3 경로와 설명 쌍. 민감 데이터는 **VPC와 PrivateLink**로 보호
  - `{"prompt": "환불은 언제까지 되나요?", "completion": "구매 후 7일 이내에 가능합니다."}`
- **지속적인 사전 훈련**: 레이블 없이 사내 문서를 그대로. 지식이 모델에 들어가므로 프롬프트에 넣을 필요 없음
  - `{"input": "2026년 상반기 신제품 라인업은 세 가지 모델로 구성된다."}`
- SageMaker 모델, S3의 Hugging Face 가중치 모델도 **가져오기** 가능

## 5. RAG (검색 증강 생성) → [[Bedrock 지식 기반]]
LLM에게 치르게 하는 **오픈북 시험**. 기억에만 기대지 않고 외부 DB에서 재료를 찾아 프롬프트에 넣는다.
```
① 질문 → ② 검색(벡터 DB) → ③ 증강(질문 + 찾은 규정) → ④ 생성(근거로 답변)
```
- 구조: **리트리버**(질의 인코더 + 문서 DB)가 후보를 찾아 **생성기**에 건넴

| 장점 | 한계 |
|---|---|
| 미세 조정보다 빠르고 저렴하게 새·독점 정보 반영 | 결국 "세상에서 가장 복잡한 검색 엔진" |
| 정보 갱신 = DB 업데이트 | 프롬프트 템플릿에 매우 민감 |
| 벡터 저장소로 시맨틱 검색 | 비결정적, 여전히 환각 가능 |
| 훈련받지 않은 내용의 환각 방지 | 검색 결과의 관련성에 매우 민감 |
| "AI 검색"을 쉽게 | 모델을 훈련하는 것이 아님 |

### RAG용 데이터베이스
- 그래프 DB(Neo4j): 상품 추천, 관계 검색
- Elasticsearch/[[Amazon OpenSearch Service]]: 전통적 텍스트 검색(TF-IDF), 벡터 DB로도
- 함수·도구 API: LLM이 질문에서 구조화된 쿼리를 만들게 함 (`"방수 등산화" → {"category":"등산화","feature":"방수"}`)
- **벡터 DB**: 대부분의 RAG가 사용

### 임베딩과 벡터 DB
- 임베딩: 수백~수천 차원의 벡터. 의미가 비슷하면 가깝다. Titan 같은 임베딩 모델로 계산
- 벡터 검색: 검색어를 임베딩 → **가장 가까운 상위 N개(K-최근접 이웃)**
- AWS 벡터 DB: OpenSearch Service·Serverless, MemoryDB, RDS/Aurora PostgreSQL의 **pgvector**, Kendra

### Bedrock 지식 기반
- 구성: 데이터 원본(S3, 웹 크롤러, Confluence, Salesforce, SharePoint) → **청킹** → **임베딩 모델**(Cohere, Titan) → **벡터 저장소**
- 벡터 저장소 기본값: **OpenSearch Serverless** (그 외 MemoryDB, Aurora, MongoDB Atlas, Pinecone, Redis Enterprise Cloud)
- 사용: 문서와 채팅(자동 RAG), **에이전트에 연결**(에이전틱 RAG), 앱에 직접 통합

> [!tip] 시험 포인트
> Bedrock 지식 기반의 기본 벡터 저장소 → **Amazon OpenSearch Serverless**

## 6. 가드레일 · 프롬프트 관리 · Flows
### [[Bedrock 가드레일]]
- 프롬프트(입력)와 응답(출력) **모두** 필터링
- 콘텐츠 필터, 단어 필터, 주제 필터(거부할 주제), 욕설 차단, **PII 제거·마스킹**, 차단 메시지 설정
- 에이전트와 지식 기반에도 적용
- **컨텍스트 근거 검사**: **근거성**(컨텍스트와 일치) + **관련성**(질의와 관련) → 환각 방지

### [[Bedrock 프롬프트 관리]]
- 재사용할 프롬프트 저장·공유, 버전 관리
- 변수는 **이중 중괄호** `{{도시}}에서 보낼 {{일수}}일짜리 일정`
- 프롬프트 변형(모델·추론 구성별), Prompt Builder, 도구·캐싱 연결, Flow 안에서 사용

### [[Bedrock Flows]]
- 프롬프트·모델 등을 사슬처럼 연결 (예전 "Prompt Flows")
- **노드와 연결**(조건부 가능), Flow Builder 또는 JSON
- 예: 입력(고객 문의) → 프롬프트 노드(분류) → 조건 노드 → 지식 기반 노드 / 다른 프롬프트 → 출력

## 7. LLM 에이전트 → [[Bedrock 에이전트]]
LLM에게 **도구**를 쥐여 주면, 어떤 도구를 어떤 목적으로 쓸지 스스로 판단한다.
- **메모리**: 대화 기록과 외부 데이터 저장소
- **계획**: 질문을 하위 질문으로 나누게 하는 지침
- **도구**: 도구 API에 제공한 함수 (Bedrock에서는 Lambda). 도구마다 붙인 프롬프트가 사용법 안내

### 에이전트는 어떤 도구를 쓸지 어떻게 알까
- **작업 그룹(Action Group)**: 도구 정의 단위. 언제 쓸지 설명 + Lambda 파라미터(이름·설명·유형·필수)
- **파라미터 설명**이 중요: LLM이 이를 보고 값을 뽑고, 부족하면 되묻는다
- OpenAPI 스키마 또는 콘솔 표로 정의
- 지식 기반도 "언제 쓸지" 프롬프트로 연결 → **에이전틱 RAG** (RAG도 도구 중 하나)
- 코드 인터프리터(선택): 직접 코드를 짜서 답하거나 차트 생성

### 멀티 에이전트
- 도구가 너무 많거나 로직이 복잡할 때 → 전문 에이전트로 나눔
- **관리자 패턴**: 오케스트레이터가 쪼개 워커에 맡기고 합성기가 합침 (예: 여러 언어 동시 번역)
- 결정이 단순하면 결정적 워크플로가 낫다

### 워크플로 패턴 4가지
| 패턴 | 설명 |
|---|---|
| **라우팅** | 라우터 LLM이 전문 에이전트 하나만 골라 호출 (한 번의 분류) |
| **병렬화** | 섹셔닝(독립 하위 작업 동시), 투표(여러 모델로 같은 일) |
| **프롬프트 체이닝** | 정해진 단계, 앞 LLM 출력을 다음이 처리, 중간 **게이트** |
| **평가자-최적화자** | 한 LLM이 생성, 다른 LLM이 평가·피드백, 반복 |

### 메모리
- **단기**: 세션 안 대화 기록, 이벤트 단위 (메모리 내, ElastiCache, MemoryDB, DynamoDB)
- **장기**: 추출한 인사이트(세션 요약, 선호, 알려 준 사실), 메모리 레코드와 "전략" (DynamoDB, RDS, AgentCore Memory, Mem0, 지식 기반)

## 11. Bedrock AgentCore → [[Bedrock AgentCore]]
AI 에이전트를 **대규모로 배포·운영**하는 서버리스 서비스. Docker·ECR·ECS를 직접 다룰 필요 없음. **어떤 프레임워크와도** 동작(OpenAI Agents SDK, LangGraph, CrewAI 등, Strands 지원이 가장 좋음)

| 구성 요소 | 역할 |
|---|---|
| **런타임** | 서버리스 엔드포인트. 스타터 툴킷이 CodeBuild로 ECR 배포. CloudWatch "GenAI Observability" |
| **메모리** | 단기(세션 안 이벤트), 장기(메모리 레코드·전략) |
| **기본 도구** | 브라우저 도구, 코드 인터프리터(Python·JS·TS, 격리된 컨테이너) |
| **게이트웨이** | API, Lambda, OpenAPI, Smithy를 **MCP 도구**로. OAuth, 시맨틱 도구 선택 |
| **아이덴티티** | **에이전트 자신의** 신원. 자격 증명 저장, OAuth 2.0 (Google, GitHub, Slack, Salesforce, Atlassian) |
| **정책** | 게이트웨이와 통합, **Cedar** 언어, 코드 바깥에서 평가, **기본 거부**, 적용 모드·로그 전용 모드 |
| **평가** | 정확성, 유용성, 간결성, 충실성, 도구 선택 정확도, 유해성, 고정관념 등 + 사용자 지정 평가자 |

- `agentcore import-agent`: Bedrock 에이전트를 Strands·LangGraph 코드로 변환해 이전 (AWS가 이전 권장)

## 12. Strands Agents → [[Strands Agents]]
- Amazon의 **오픈 소스 Python 에이전트 SDK**
- AWS와 긴밀하지만 AWS에 묶이지 않음. 멀티모달, **MCP 지원**
- 기본 도구: boto3, 지식 기반 RAG·메모리, Python·HTTP·셸·파일, 에이전트 스웜, Polly
- `@tool` 데코레이터로 도구 정의 → `Agent(tools=[...])`
- 에이전트 루프: 입력 → LLM 추론·도구 선택 → 도구 실행(반복) → 응답

> [!warning] 헷갈림 주의
> - [[Bedrock 에이전트]]: 콘솔에서 구성하는 관리형 에이전트
> - [[Strands Agents]]: 에이전트를 **만드는** SDK
> - [[Bedrock AgentCore]]: 에이전트를 **운영하는** 인프라

## 파트 핵심 요약
> [!summary] 시험 직전 체크
> - 최신·사내 정보 → RAG · 레이블 데이터 → 미세 조정 · 레이블 없는 문서 → 지속적인 사전 훈련
> - 임베딩 모델 + 벡터 저장소 → 지식 기반 (기본 OpenSearch Serverless)
> - 유해 콘텐츠·주제·PII 차단, 근거성 검사 → 가드레일
> - 도구 = 작업 그룹(Lambda) · RAG도 도구(에이전틱 RAG) · 대규모 운영 → AgentCore
> - 온디맨드 / 50% 저렴 → 배치 / 약정·보장 → 프로비저닝된 처리량
> - 비공개 연결 → PrivateLink · 암호화 → KMS · 프롬프트·응답 기록 → 모델 호출 로깅
